# PadBridge の設計判断

既存ソフトの調査は [existing-solutions.md](existing-solutions.md) にある。ここには、自作する中で決めたことと、その理由を残す。

## 音声入力は Mac の Typeless を iPad から起動する

- ユーザーの要件は「Typeless で音声入力すること」。Apple の音声認識などで代わりにしてはいけない。
  - 2026-10-17 に一度、合意なく iPad 側の SpeechAnalyzer (Apple の音声認識) に置き換えて強く叱責された。
- iPad のマイクの音を Mac の Typeless に入れるには、仮想オーディオデバイス (BlackHole や自作の AudioServerPlugIn) が要る。これは端末全体を汚すので不可。
- iOS 版の Typeless は App Store で「iPhone 専用」と表示されている (2026-10 時点)。
- ユーザーが選んだ方式は次のとおり (2026-10-17)。
  - iPad の Typeless ボタンで、Mac の Typeless の音声入力ショートカットを押す。
  - 録音は Mac 側のマイクで行う。
  - Mac に何も入れずに、Typeless の全機能 (文脈の読み取りなど) が使える。
- iPad 版の Typeless に切り替える案は、Mac の Typeless を使うという取り決めに反するので出さない (2026-10-17 に調べかけて強く否定された)。

### 蓋を閉じた Mac では、iPad のマイクを一時的な入力デバイスにする

- Mac を閉じたまま iPad から操作すると、Typeless が「マイクがない」と言って録音が始まらない (2026-10-17 の報告)。Apple silicon と T2 の Mac のノートは、蓋を閉じると内蔵マイクをハードウェアで切り離し、root 権限のソフトでも戻せない ([Apple Platform Security](https://support.apple.com/guide/security/hardware-microphone-disconnect-secbbd20b00b/web))。このとき、この Mac の入力デバイスは内蔵マイクしかなかった。
- ユーザーが選んだのは、iPad のマイクの音を「Host が動いている間だけの一時的なマイク」として Mac に見せる方式 (2026-10-17)。ドライバ (HAL プラグイン) は入れない。
  - iPad は Typeless のボタンを押している間だけマイクの音を取り、48kHz・モノラル・16 ビットのまま操作用の接続で送る (`WireMessage.audio`)。
  - Mac では、届いた音を自分のプロセスで鳴らし、自分の出力だけを取り出すミュートのプロセスタップ (`CATapDescription`、`muteBehavior = .muted`) を作る。タップだけを入力に持つ集約デバイス「PadBridge iPad マイク」を作ると、他のアプリから入力デバイスとして見える。出力のサブデバイスを入れると、出力デバイスとしても一覧に出てしまう。
  - **このデバイスは Mac の既定の入力になれない**。タップだけの集約デバイスは `kAudioDevicePropertyDeviceCanBeDefaultDevice` が 0 で、既定の入力に設定しても、ほかのアプリからは内蔵マイクのままに見える (2026-10-17 に確かめた)。既定の入力は切り替えない。
  - 利用者に Typeless の設定を変えさせる作りは「ゴミ仕様」「こっちに指示を出すな」と否定された (2026-10-17)。そこで Host が、iPad がつながった 5 秒後に、Typeless の `selectedMicrophoneDevice` をこのデバイスにする (`TypelessMicrophoneSetup`)。
    - Typeless の中身 (app.asar) を読んで確かめたこと: 設定は electron-store で、外からの書き換えを読み直す `watch` は使っていない。動いている間に書き換えても上書きされるので、Typeless を終了させてから書き換え、起動し直す。選んだマイクは今のマイクの一覧から deviceId で探し、なければ null (自動検出) に戻るので、iPad がつながっていないときは内蔵マイクで聞き取れる。
    - 蓋を閉じると Typeless が「マイクがない」と言う理由も中身で分かった: マイクが「自動検出」のときだけ蓋の開閉を 3 秒ごとに見ており、閉じていると既定の入力 ('default') を使わず、録音するデバイスがなくなる。特定のマイクを選んでいれば、蓋の開閉に関係なくそれを使う。
    - 選んだマイクが一覧にないときは自動検出として扱うだけで、`selectedMicrophoneDevice` を null に書き戻さない。一覧は `devicechange` のたびに取り直す。そのため、Typeless が iPad のつながっていないときに起動しても、補助アプリがデバイスを作り直しても、選んだままになる。
    - 値は、Typeless 自身が設定に書いたマイクの一覧の項目をそのまま使う (deviceId は Chromium が作る値なので、自分では作れない)。書き換えるのはこの 1 項目だけで、ほかの項目が変わらないことを写しで確かめた。
    - 聞き取りの途中では終了させない。選ぶのは、選んだマイクが自動検出 (null か deviceId が `default`) のときだけ (`TypelessMicrophoneChoice`)。利用者が特定のマイクを選んでいれば、その選択として残す。初めは一度だけ設定して UserDefaults に記録していたが、それだと Typeless を入れ直したり設定が消えたりしたあと二度と選ばれず、iPad に設定の手順を出すことになるのでやめた。
    - 最初は聞き取りの間だけ既定の入力を切り替えていたが、Typeless は内蔵マイクで録音していた。coreaudiod の記録では、既定の入力をこのデバイスにした直後に、Typeless の入力は BuiltInMicrophoneDevice で始まっていた。
    - 内蔵マイクをサブデバイスに加えた集約デバイスなら既定になれるが、チャンネル 1 が内蔵マイク、2〜3 がタップの順に並ぶ。Chromium が先頭のチャンネルを読むと、蓋を閉じた内蔵マイクの無音を拾うので採らなかった。
    - Host は、iPad から聞き取りを始めたあと、Typeless が録音しているデバイスを `kAudioProcessPropertyDevices` (入力側) で読む。このデバイスでなければ、Typeless の設定をし直し (自動検出のときだけ)、利用者が別のマイクを選んでいれば iPad に知らせる。
      - Typeless がこのデバイス (タップだけの集約デバイス) で録音しているときは、この一覧が空になる (内蔵マイクのときは BuiltInMicrophoneDevice が入る)。空を「別のマイク」と見なして、正しく聞き取れているのに iPad に警告を出していた (2026-10-17 に利用者が気づいた)。空のときは分からないものとして知らせない。
    - Typeless がこのデバイスを選んだままなので、iPad がつながったまま Mac で直接 Typeless を使うと、無音で録音されてしまう (補助アプリは iPad から話している間しか音を流さないため)。そこで補助アプリは、iPad から話していない間にこのデバイスが読まれたら (`kAudioDevicePropertyDeviceIsRunningSomewhere`)、Mac の既定の入力の音を別の `AVAudioEngine` で取り込んで流す。この通知は集約デバイスでもすぐ届く (プロセスの入力状態と違い、待たずに使える) ことを確かめた。
    - 流すのを既定の入力から変えない (2026-10-18 に検討して見送った)。蓋を閉じたこの Mac では既定の入力が内蔵マイク (ハードウェアで切り離されて無音) のままなので、外付けの USB マイクを選ぶ案を考えた。
      - Typeless の「自動検出」も、外付けのマイクへ自分では切り替えない (app.asar を読んだ)。自分で切り替えるのは、蓋が開いていて内蔵マイクが使えるときに推奨のマイクへ移すときだけ (`preferredBuiltInMicId`)。録った音が無音のときは、ほかのマイクを開いて音の大きさを測り、「より良いマイク」を知らせて選ばせるだけ (1 日 1 回まで)。補助アプリが外付けのマイクを選ぶと、Typeless 自身もしない推測をすることになる。
      - 音を取らずに読める値では、マイクとして使える入力を見分けられなかった。この Mac の入力は、DL-Dock (DisplayLink のドックの差し込み口、USB・2 チャンネル・差し込みの検出なし、出力は別のデバイス)、fifine Microphone (USB・1 チャンネル・差し込みの検出なし、ヘッドホン端子の出力あり)、内蔵マイク。種類・差し込みの状態・出力の有無・チャンネル数のどれも、何も挿していないドックの差し込み口と本物のマイクの違いを表さない。
      - iPad からの聞き取りのあと Typeless がまだ読んでいる間に流し始めると、その続きに Mac のマイクの音が混ざる。読むのが一度止まるまでは流さない (`PassThroughGate`)。
      - 録音の許可がないとタップのミュートが効かず、Mac のマイクの音がスピーカーから流れるので、そのときは流さない。
      - 常に Mac のマイクを取り込んでおけば話し始めが欠けないが、マイク使用中の表示が出続けるので、読まれている間だけ取り込む。
      - 取り込みはタップではなく `AVAudioSinkNode` で行う。この Mac で測ると、タップは 4800 フレーム (100ms) ごとに 1 秒 10 回、シンクは 512 フレーム (約 10ms) ごとに 1 秒 94 回渡し、エンジンの開始はどちらも 0.04 秒だった。Typeless は自分のショートカットで止めた瞬間に読むのをやめるので、ためている分が話し終わりから切れる。シンクにして、ためる量を 30ms にした。Mac の内蔵マイクは 48kHz・モノラルで送る形と同じなので変換しない。
      - 蓋を閉じていると、内蔵マイクは形式 (48kHz・1 チャンネル) は見えるが、値はすべて 0 になる。
      - 一時的な読み手でこのデバイスを 1.5 秒読み、読み始めた瞬間に流し始め、読み終えたらやめること、48kHz で途切れずに届くことを確かめた (2026-10-17)。
  - iPad がつなぎ直すたびに補助アプリを止めて起動し直すと、デバイスを作り直して点検し終えるまで (約 1.5 秒) iPad のマイクを使えず、Typeless もマイクの一覧を取り直す。接続が切れても 60 秒は補助アプリを残し、その間につなぎ直したらそのまま使う。
  - 2026-10-17 の時点で、iPad との接続は Wi-Fi のネットワーク (en0) ではなく Wi-Fi の直接通信 (awdl0) を通っていた (`includePeerToPeer`)。awdl はチャンネルを行き来するので遅れが揺れやすく、切れることもある。ただ、ルーターが端末どうしの通信を遮る設定だと awdl でしかつながらないので、外してはいない。つなぎ直しの原因を追えるよう、Host は接続ごとに経路を記録する。
    - 同じ日の 23:58 のつなぎ直しでは en0 を通った。この環境ではどちらの経路でもつながり、接続ごとに Network.framework が選ぶ (Mac の en0 から `_companion-link._tcp` で iPad が見えなかったのは、iPad がそれを出していなかっただけだった)。
  - `AVAudioNode` のタップは 100〜400ms ごとにしか音を渡さない (ヘッダーの `installTapOnBus` の説明。1024 フレームを頼んでも 100ms になる) ので、iPad の音は 100ms の塊で届く。初めは 80ms たまったら鳴らしていたが、塊より短いと少し遅れて届くたびに途切れる。今は 150ms たまってから鳴らし、3 秒を超えたら古い音を捨てる (`PCMJitterBuffer`)。途切れた回数は聞き取りごとに記録に出す。
  - 初めは聞き取りを始めたらすぐ鳴らしていたので、Typeless がデバイスを読み始めるまで (ショートカットを押してから数百 ms) の声が誰にも届かず、話し始めが切れていた。今は、デバイスが読まれている間 (`kAudioDevicePropertyDeviceIsRunningSomewhere`。別のプロセスが読み始めても通知はすぐ届くことを確かめた) だけ鳴らし、それまではためておく。そのため補助アプリは、聞き取りの間は自分でデバイスを読まない。
  - 完了のショートカットは初め 0.25 秒待って押していたが、ためている音が多いと話し終わりが切れる。今は、iPad で止めたら Host が補助アプリに知らせ (`microphoneRelayFinish`)、補助アプリは止めた直前の塊が届くまで 0.2 秒待ってから、そこまで書き込んだ音を鳴らし終えたら返す (`microphoneRelayFinished`)。Host はそれを受けてから押す。iPad は Mac で Typeless が止まるまでマイクの音を送り続ける。
- 許可について、次のことが分かった (2026-10-17)。
  - プロセスタップには「システムオーディオの録音」(`kTCCServiceAudioCapture`) の許可が要る。ターミナルから動かした Host では Ghostty の許可として求められ、Ghostty は理由の説明 (`NSAudioCaptureUsageDescription`) を持たないので、macOS は尋ねずに断る。このとき、タップのミュートも効かない (試した音がスピーカーから鳴った可能性がある)。
  - Host のバンドルの中に入れた補助アプリ「PadBridge Mic」を LaunchServices で起動すると、許可は「PadBridge Host」のものとして求められる。Host をターミナルから動かしたままでよく、Host 自身をアプリとして起動し直して画面収録などの許可を取り直す必要がない (蓋が閉じているので、取り直す間に画面が映らないと何もできなくなる)。
  - 画面を持たない補助アプリでは、Core Audio は許可の有無を確かめるだけで尋ねない (`preflight=yes`)。公開の API がないので、AudioCap などと同じく TCC の `TCCAccessPreflight` と `TCCAccessRequest` を直接呼んで尋ねる。
  - **タップを含む入力デバイスを読むには、読む側のアプリにも「マイク」と「システムオーディオの録音」の両方の許可が要る。** 2026-10-17 に次のとおり確かめた。
    - マイクだけ許可された Ghostty から読むと、`AudioDeviceStart` が `nope` で失敗した (coreaudiod が Ghostty の `kTCCServiceAudioCapture` を確かめ、未許可だった)。
    - システムオーディオの録音だけ許可された補助アプリから読むと、無音だった (`kTCCServiceMicrophone` が未許可)。
    - Typeless の Info.plist にはマイクの説明しかないので、Typeless は自分ではこの許可を求めない。システム設定の「画面とシステムオーディオの録音」→「システムオーディオ録音のみ」に、利用者が Typeless を加える必要がある。
    - 許可がないとき、Typeless は「PadBridge iPad マイク」を開けはするが、中身は無音になり、聞き取りは続く (2026-10-17 の「音声入力が動かない」の原因)。tccd は Typeless の確認に authValue=0、authReason=8 (理由の説明がない) を返し、「Refusing authorization request for service kTCCServiceAudioCapture and subject Sub:{now.typeless.desktop}」を記録した。断ったことは許可の一覧に残らないので、Typeless は一覧に自動では載らず、「＋」で加える必要がある。
    - アプリから他のアプリの許可を前もって読む方法はない。`TCCAccessPreflightWithAuditToken` は、権限のない呼び出し元には実際の許可と違う値 (許可されているマイクも「拒否」) を返した。
    - そこで Host は、iPad のマイクで聞き取りが始まった 1 秒後に、直近 5 秒の tccd の記録から上の拒否の行を探す。あれば iPad に手順を知らせ、Mac で「画面とシステムオーディオの録音」の設定を開く。なければ知らせを消す。
    - 初めは「iPad から始めたのに 1 秒たっても聞き取りが始まらない」ことも読めない印にしていたが、誤りだった。Typeless は聞き取りを止めてから文字にして貼り付け終えるまで (数秒) ショートカットを受け付けず、続けて話し始めるとこれに当たる。2026-10-17 に、止めて 3.7 秒後に始めたときに設定の画面を開いてしまい、ミラーリングの画面に出た。今は読めない印は tccd の拒否の行だけにし、始まらないときは 1 秒ごとに 4 回まで押し直す。その間は iPad にマイクを止めさせず、補助アプリが声を 6 秒までためておくので、遅れて始まっても話し始めは落ちない。
      - Typeless の中身 (xstate の状態機械) で確かめた: 止めたあとの `finishing` (文字起こしの仕上げ) では、ショートカット (`PRIMARY_KEY.DOWN`) は「まだ仕上げ中」の知らせ (`showFinishingAlert`) を出すだけで、ためて後で始めはしない。仕上げが終わる (`WEBSOCKET.REFINE_COMPLETED`) と `idle` に戻り、押せば始まる。そのため押し直しても余計に始まったり止まったりしない。
        - この知らせは「前の聞き取りを処理中」の警告を 5 秒出すもので、前の聞き取りを取り消す (`ESC`、記録は `dismissed`) のは、知らせの中の「キャンセル」を人が押したときだけ。押し直しても、前に話した分は消えない。
        - 仕上げの長さの上限は、文字起こしで 20 秒、音声コマンドで 30 秒 (`VOICE_TRANSCRIPT_REFINE_TIMEOUT_MS`・`VOICE_COMMAND_REFINE_TIMEOUT_MS`、長い録音は録音の長さ) で、過ぎると `FATAL_TRANSCRIPTION_TIMEOUT` になる。押し直すのは約 5 秒までで、補助アプリがためておける声 (6 秒) に合わせている。それより仕上げが長引いたときは、iPad の表示を戻して押し直してもらう。
      - 同じく、聞き取りを始めて 1 秒後から 5 秒間、声があるかを見ており、なければ自分で止める (`RECOVERABLE_NO_SPEECH_DETECTED`)。声とみなすのは、8 ビットの波形で 128 から 1 以上離れた値 (振れ幅で約 0.0078、-42dBFS) が 1 つでもあるとき。iPad の声は話すと最大 0.12〜0.25 で十分に上回り、話していないときの雑音 (約 0.0006) は下回る。iPad の声を Typeless が読み始めるまでためておくのは、この点でも要る (読み始めたときに話し始めから流れる)。
      - ショートカットを押し続けると `long_pressing` (「押し続けず押すだけ」の知らせ) になり録音を止めるので、Host は押してすぐ離す。
  - Typeless (Chromium) にこのデバイスをマイクとして数えさせるには、次の 2 つが要った (2026-10-17、「使えない」と報告されて調べた)。聞き取りの間に Typeless の「システムオーディオの録音」の確認が一度も起きず、Typeless の設定のマイクの一覧にもこのデバイスがなかったことから、内蔵マイクを開いていたと分かった。
    - タップを公開にする (`isPrivate = false`)。既定の非公開のタップは作ったプロセスにしか見えず、ほかのアプリからは集約デバイスの入力が 0 本に見える。
    - 補助アプリの出力を止めない。出力を止めたまま作ったタップや、出力が止まっている間は、集約デバイスが入力を持たない。Typeless は聞き取りの間だけ入力が現れても、マイクの一覧を作り直さない。iPad の声を鳴らすのは聞き取りの間だけにし、それ以外は無音を流す。
    - 直したあと、Typeless の設定のマイクの一覧に「PadBridge iPad マイク」が加わった。
  - 補助アプリは、終わる前にデバイスを消し終えるのを待つ。待たずに終わると、デバイスが Mac に残る。
  - 補助アプリが無音を流し続けている間は、coreaudiod が Mac のアイドルスリープを止める (`pmset -g assertions` に `BuiltInSpeakerDevice.context.preventuseridlesleep` が出る)。iPad がつながっている間だけなので、閉じた Mac を iPad から使う用途ではそのままにしている。
  - 最初は、補助アプリが自分で鳴らした小さな音 (20kHz) を「PadBridge iPad マイク」そのものから読んで経路を確かめていた。上のとおり補助アプリにはマイクの許可がなく必ず無音になるので、この読み方はやめた。今は、システムオーディオの録音の許可だけで読める点検専用の非公開の集約デバイスで、タップが音を運んでいるかを測る (許可が付いたときに 1 回。マイクの許可もあれば「PadBridge iPad マイク」そのものも測る)。
- 作った集約デバイスとタップは、作ったプロセスが終わっても HAL に残る。補助アプリは、起動したときに前の残りを消し、Host との接続が切れたら自分のものを消して終わる。名前で探して消すと、入れ替わりに起動した補助アプリのデバイスまで消してしまうので、終わるときは自分が作ったものだけを消す。
- 音声入力の経路を別のエージェントに読ませて直したこと (2026-10-18)。
  - 補助アプリが起動直後の点検 (約 1.5 秒) などで遅れ、聞き取りの準備の返事が待ち時間 (1.5 秒) を過ぎると、その回は「iPad の声を使っていない」とみなし、止めるときに話し終わりを流し終えるのを待たずに Typeless を止めていた (ためた話し終わりが切れる)。待ち時間を過ぎて届いた「準備できた」も、その聞き取りの途中なら反映する。
  - Typeless のマイクの設定のために Typeless を終了させてから起動し直すまでの間に iPad から始めると、終了しかけた Typeless にショートカットが届かないか、Host が別に起動してしまう。その間はショートカットを押すのを待たせ (最大 15 秒)、終了させる直前に聞き取りが始まっていないかを確かめ直す。
  - 前の聞き取りが止まったのに見張り (0.2 秒ごと) が気づく前に開始を押すと、あとから前の「止まった」が届き、iPad が始めさせたことを忘れていた。忘れると iPad が離れたときに Typeless を止めず、聞き取りが残る。押してから 1 秒の間に届いた「止まった」では忘れない。単体テストで、直す前の判断にすると落ちることを確かめた。
  - iPad のマイクを始められなかったとき (電話のあと、ほかのアプリがマイクを使っているとき) は、黙って Mac に始めさせていた。許可がないときと同じく「Mac のマイクで聞き取ります」と知らせる。
  - 新しくつないだら、「iPad の声を使っている」を初めからにする。前の接続の値で、Mac で直接話したときに Typeless の設定を確かめにいっていた。
  - Typeless・補助アプリ・マイクを実際に動かす確かめは、利用者の聞き取りと Mac のマイクを使うことになるので、単体テストとビルドまでにしている。
  - 直していない指摘: 聞き取りの途中で補助アプリがつながったり起動し直したりしたときに、補助アプリに聞き取りを頼み直さないこと (Typeless は始めたときに開いたマイクを使い続けるので、頼み直してもその回には効かない)。iPad が離れてから 60 秒の間に補助アプリが強制終了されたときのデバイスの残り (その間は補助アプリを起動し直し、起動した補助アプリが残りを消す)。
- 補助アプリは Host とループバックの接続でつなぐ。Host は起動のたびに合言葉を渡し、合言葉を言わない接続は切る (10 秒待っても言わない接続も切る)。
- 補助アプリと Host の起動・終了を読み直して直したこと (2026-10-18、別のエージェントに読ませた指摘から):
  - 既定の出力の機器が変わってチャンネル数やサンプルレートが変わると、補助アプリの音を鳴らすエンジンは自分で止まる (`AVAudioEngineConfigurationChange` の説明のとおり)。止まったままだとタップが無音になり、iPad で話しても Typeless に何も届かず、Host も気づかない。知らせを受けたらエンジンを動かし直す。出力の機器を替えるのは Mac 全体の設定を変えることになるので、ビルドまでにしている。
  - 補助アプリが後始末をするのは、Host との接続が切れたときと SIGTERM だけだった。アクティビティモニタの「終了」やログアウト (Apple Event)、SIGINT・SIGHUP で終わるとデバイスとタップが残る。終わる直前 (`applicationWillTerminate`) と SIGINT・SIGHUP でも消す。Host の起動時にも、残ったデバイスとタップを探して消す。探す処理を、何も消さない形でこの Mac で動かし、どのデバイスの UID も読めて、今は残りがないことを確かめた。
  - Host が先に終わっていると、補助アプリの接続は失敗ではなく待ち (`.waiting`) になり、補助アプリが残り続けうる。待ちも終わる合図にした。
  - 補助アプリを起動できなかったとき、iPad がつなぎ直すまで起動し直さなかった。3 秒おきに 3 回まで起動し直す。補助アプリが落ちたあとすぐ起動し直していたので、落ち続けると起動を繰り返し続けていた。2 秒待つ。
  - Typeless のマイクの設定を書き換えるとき、利用者が自分で終了させていた Typeless まで起動していた。動いていたときだけ起動し直す。
  - Host の「再起動」は、1 秒待ってから開いていた。古い Host が終わるのが遅れると、古い方を前に出すだけで終わり、Host が 1 つも残らない (蓋を閉じた Mac では iPad からつなげなくなる)。古い Host のプロセスが終わるのを待ってから開く。同じスクリプトを、代わりのプロセスと開く代わりの echo で動かし、終わるまで (3 秒) 待ってから開くことを確かめた。
    - それでも、終わった直後に開くと `open` が `_LSOpenURLsWithCompletionHandler() failed with error -600` で開けずに終わり、Host が 1 つも残らないことがある (2026-10-18、Host を入れ替えたときに 1 度起きた)。開いて 1 秒後に `pgrep -x` で新しい Host が動いているかを確かめ、動いていなければ 10 回まで開き直す。`open` の終了コードは man に書かれていないので、プロセスで確かめる。自作の何もしない常駐アプリと、最初の 2 回は開かずに失敗する偽の `open` でこのスクリプトを動かし、3 回目で開き直して新しいプロセスが動くことを確かめた。
  - 直していない指摘: 合言葉が起動の引数に載り、同じ Mac のほかのプロセスから読める (同じ Mac で動くものを信用しない作りにはしていない。iPad との通信もペアリングなし)。

### Typeless のショートカットは「押し続ける」のではなく「1 回押す」

- 設定ファイルのキー名は `keyboardShortcut.pushToTalk` だが、**押すたびに開始と完了が切り替わる**方式。押し続けると、聞き取りは始まらず「Typeless ショートカット」の使い方の案内 (「話すには一度押してください…」) が出るだけ。
  - 最初はキーを押し続けて実装し、この案内を聞き取り中と取り違えて「動いた」と判定していた。ユーザーには一度も正しく起動していなかった。
- Mac は、iPad から「開始」「完了」が届くたびに、ショートカットを 50ms だけ押して離す。iPad のボタンは、タップで開始と完了を切り替える使い方と、押している間だけ話す使い方の両方に対応する (どちらも Mac では 1 回押しになる)。
- 合成する修飾キーのイベントには、実際のキーボードと同じく次のビットを載せている。
  - 左右を区別するビット (左 Control は `0x1`)
  - 合成ではない実入力であることを示すビット (`0x100`)
- ショートカットは、押すたびに `~/Library/Application Support/Typeless/app-settings.json` を読み直す。書き換えはしない。
- Typeless が動いていなければ、押す前に起動する。Typeless はショートカットを本体のプロセスのキーのイベントタップ (セッションと HID の 2 つ、キーの押下・離し・修飾キーの変化を見る) で拾い、本体から画面側へ `global-keyboard` として送っている。タップができるまでは押しても届かないので、`CGGetEventTapList` で Typeless のタップが現れるまで (最大 10 秒) 待ってから押す。初めは起動を終えてから決め打ちで 1.5 秒待っていた。
  - それでも画面側の用意が間に合わずに届かなかったときは、聞き取りが始まらないので押し直しで拾う。押し直しを数え始めるのは押したときから。初めは iPad から要求が届いたときから数えていて、Typeless の起動を待つ間に押し直しの 5 秒を使い切り、始まる前に iPad の表示を戻してしまう作りだった。

### Typeless の動作確認の方法

- 窓が出たかどうかでは判定できない。聞き取り中の小さなピル (✕・波形・✓) も使い方の案内パネルも、同じ窓 (750x500) に描かれるため。
- 2026-10-17 に窓を撮影して比べたところ、不透明な暗い部分の高さは、ピルが 64px、案内パネルが 298px だった。
- 実際に文字になるかを、Mac の `say` で確かめることはできない。Typeless の音声取得にかかるエコーキャンセルが、Mac 自身のスピーカーの音を消してしまう。
- 1 回押すと Typeless のマイク入力が始まり、もう 1 回押すと止まることを、macOS の audiomxd の記録 (`input_running`) で確かめた (2026-10-17)。

### iPad のボタンの表示は、Typeless の実際の状態に合わせる

- 最初は iPad と Mac がそれぞれ「開始を送ったか」だけを覚えていた。Typeless が自分で聞き取りを終えたり、Mac 側で ✕ を押したりすると覚えとずれる。次の「完了」でショートカットを押すと逆に聞き取りが始まり、「Typeless の状態と iPad の赤・青が逆になる」と報告された (2026-10-17)。
- Typeless は聞き取りの状態を外へ公開していない。そこで、聞き取っている間だけマイクを使うことを利用して、CoreAudio のプロセスの入力状態 (`kAudioProcessPropertyIsRunningInput`) で判定する (`TypelessMonitor`)。
  - Typeless は Electron 製で、マイクを使うのは本体ではなく `now.typeless.desktop.helper` (Typeless Helper)。バンドル ID の先頭が `now.typeless.desktop` のプロセスをまとめて見る。
  - CoreAudio のプロセス `now.typeless.desktop.helper` の PID は 2204 だった。audiomxd が聞き取り中に `input_running: true`、完了後に `false` と記録した「Typeless Helper(2204)」と同じプロセスであることを、PID で照らし合わせた (2026-10-17)。
  - プロセスの入力・出力状態の値は正しく変わるが、`AudioObjectAddPropertyListenerBlock` の変化の通知は来なかった。自分のプロセスで、音の出ない出力を 1 秒流して確かめた (2026-10-17)。このため、iPad がつながっている間だけ 0.2 秒ごとに読み直す。
- Mac はショートカットを押す前に実際の状態を見て、すでに求められた状態なら押さない (`TypelessToggle`)。押してからマイクが動き出すまで 0.1〜0.2 秒かかる。押してから 1 秒の間は、押した結果を今の状態とみなす。
- iPad は押した直後に求めた状態を先に見せる。そのあと Mac から状態 (`voiceInputState`) が届いたら、それに合わせる。Typeless がショートカットに反応しなかった場合は状態が変わらず知らせが来ないので、Mac は要求から 1 秒後に必ず今の状態を送る。
- iPad が裏に回ったときや接続が切れたときに止めるのは、iPad から始めた聞き取りだけ。iPad が自動でロックされたときに、Mac で直接話している聞き取りを止めてしまわないため。

## 通信: ペアリングも暗号化もしない

- 最初は TLS-PSK (Mac が発行する 10 文字のペアリングコード) で、暗号化と相互認証をしていた。
- ユーザーから「ペアリングコードは邪魔」と言われ、廃止した (2026-10-17)。認証の鍵をリポジトリに埋め込んでも公開リポジトリでは意味がないので、TLS ごと外して素の TCP にしている。**同じ LAN の誰でも Mac を操作できる**ことは README に明記した。
- Mac は Bonjour (`_padbridge._tcp`) で広告する。iPad は、前回つないだ Mac か、見つかった Mac が 1 台だけならそこへ自動でつなぐ。
- iPad でこのアプリにローカルネットワークが許可されていないと、`NWBrowser` は `.waiting(.dns(kDNSServiceErr_PolicyDenied))` で止まり、Mac が 1 台も見つからない。そのときは「Mac が見つかりません」(Mac 側を疑わせる文) ではなく、許可が要ることと iPad の設定を開くボタンを出す。
  - 判定は [TN3179](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy) の `NWBrowser` の例と同じ。あとで許可されると、システムが自動でやり直す。初めての許可の確認を出している間も、返事を待たずに断ることがあるとあるので、そのときは確認の後ろにこの知らせが出て、許可すると消える。
  - 判定は `LocalNetworkAccess` にまとめ、TN3179 の値 (-65570) で止まったときだけ許可がないとみなすことを単体テストで確かめた。値を別のエラーに変えるとテストが落ちる。
  - OS が実際に断ったときの画面は出していない。TN3179 のとおりシミュレータはこの許可に対応しておらず、この iPad は許可済みで、Mac で断らせると利用者の画面に許可の確認が出て設定にも記録が残るため。出すには利用者の iPad でこの許可を切る必要がある。
- 接続は**操作用と映像用の 2 本**に分けた。1 本にまとめると、映像の送信が詰まったときにクリックやキー入力まで待たされるため。
- Mac は、送信待ちが 4 件以上たまったら、取り込んだフレームを符号化する前に捨てる。符号化したあとで捨てると、参照フレームが欠けて映像が壊れる。
- 知らない種類のメッセージや、知らない操作 (JSON の知らないケース) が届いても、接続は閉じずにそのメッセージだけ飛ばし、記録に残す。メッセージの区切りは framer が長さで切り出しているので、1 件を読み飛ばしても後ろはずれない。初めは解釈できないものが来たら接続を閉じていたが、Mac と iPad の片方だけを新しいビルドにすると (2026-10-17 に Host だけが古いまま動いていたことがある)、新しい方が送るものを古い方が受け取るたびに切れ、つなぎ直しを繰り返すことになる。
- 相手が切断を知らせずに消えたとき (圏外、スリープ、iPadOS が裏のアプリの通信を止めたとき) は、TCP のキープアライブと再送の打ち切りで気づく。無通信が 2 秒続いたら 2 秒おきに確かめ、4 回返事がなければ切る。送っている最中は確かめが送られないので、再送に 10 秒返事がなければ切る。初めはキープアライブを始めるまでの 2 秒だけを決めていたが、間隔と回数は macOS の既定 (`net.inet.tcp.keepintvl` 75 秒、`keepcnt` 8 回) のままで、気づくまで約 10 分かかっていた。その間 iPad は止まった映像を映したまま、つなぎ直さない。

## つなぐ・つなぎ直す流れを読み直して直したこと

- 2026-10-18 に、別のエージェントに接続の流れ (iPad のつなぎ直し、Host の待ち受けと取り込み) を読ませ、指摘をコードと照らして直した。
- 取り込みを始めている途中 (`startCapture` を待つ間) に止められると、止める処理はまだ始まっていない取り込みに効かず、取り込みが動き続けていた (画面収録の表示も消えない)。始め終えたところで止められていたら止め直す。作り直したあとの古い取り込みからの失敗の知らせで、新しい取り込みが使っている映像の接続を閉じないようにもした。取り込みを実際に動かすと利用者の画面を取り込むことになるので、ビルドまでにしている。
- iPad は、つながった時点でつなぎ直す間隔を 0.5 秒に戻していた。つながってすぐ Mac に切られることが続くと、0.5 秒おきにつなぎ直し続ける。welcome を受け取ったときに戻す。映像の接続も、張り直す間隔を 5 秒まで延ばしていき、映像の形式が届いたら戻す。シミュレータで、代わりの Host が名乗りを受けてすぐ切るようにして測った。直したあとの間隔は、操作の接続が 0.6・1.1・2.1・4.2・5.3・5.2 秒、映像の接続が 0.5・1.1・2.1・4.1・5.3・5.2 秒。
- Host の待ち受け (`NWListener`) が失敗の状態になると、Host を起動し直すまで iPad からつなげなかった (蓋を閉じた Mac では致命的)。2 秒待って作り直す。
- iPad が映像の接続を張り直すとき、Host は画面の構成の読み直しの予約まで取り消していた。Mac が目覚めて画面の構成が変わったのと同じ頃に iPad がつなぎ直すと、古い画面の大きさのまま映していた。映像を止めても、読み直しは取り消さない。
- つないだまま名乗らない接続が、Host にいつまでも残っていた。10 秒で閉じる。実際の Host に、何も送らない TCP の接続をつないで、10.7 秒後に閉じられることを確かめた (iPad がつながっていないことを確かめてから)。
- 直していない指摘: 前回の Mac が見つからず、ほかに Mac が 1 台だけ見つかると、そちらに自動でつなぐ (Mac を 2 台使う家に限る。Mac の Bonjour の名前が「(2)」付きに変わったときにも自動でつなぎ直せるので、今のままにする)。映像の接続の名乗りが今の操作の接続と同じ iPad からかを見ていない (1 台で使う前提)。

## 裏に回っても切らない

- ユーザーから「バックグラウンドで切れるのは論外」と言われた (2026-10-17)。
- iPadOS は、裏に回ったアプリを数秒で止める。そこで接続中は、`UIBackgroundModes: audio` と `.playAndRecord` + `.mixWithOthers` のオーディオセッションで、無音を流し続ける (Typeless で話すときに iPad のマイクも使うので、録音もできる種類にしておく。あとから切り替えると流している無音が止まる)。音は出ず、他のアプリの音楽なども止めない。
- 裏にいる間は、映像用の接続だけ閉じる (電池と通信量を抑えるため)。前面に戻ったら、映像用の接続を張り直してキーフレームから描き直す。
- 映像を送っている間だけ、Host が `PreventUserIdleDisplaySleep` のアサーションを持つ。iPad で見ているだけで操作しない間に、Mac の画面が「ディスプレイをオフにする」の時間 (この Mac は 10 分) で眠り、映らなくなるのを防ぐ。Amphetamine などが動いていなくても見続けられる。iPad が裏に回って映像の接続を閉じると放す。
  - このアサーションは、もう眠っている画面を起こさない。iPad が裏にいる間に画面が眠ると、前面に戻っても何も映らない (ScreenCaptureKit は画面が変わらないとフレームを出さない)。映し始めるときに `IOPMAssertionDeclareUserActivity` で操作があったと知らせて起こす (この Mac は Amphetamine が画面を眠らせていないので、ふだんは起きない場面)。
- 操作用の接続が切れたら、一覧画面に戻さず、その場で 0.5 秒から 5 秒までの間隔で張り直し続ける。
- 実機で、ホーム画面に 20 秒移っても Mac 側に切断が記録されず、戻ると映像だけが再要求されることを確かめた (2026-10-17)。

## iPad でコピーした文字を Mac に入れる

- 特殊キーの列の最後に、iOS のペーストボタン (`UIPasteControl`) を置いた。押すと、入力先 (`DirectTypingUIView`) の `paste(itemProviders:)` に文字が渡り、`insertText` で Mac の入力欄に入れる (下の「Mac 側で文字を入れる方法」)。キーを 1 つずつ打つのではないので、日本語や絵文字もそのまま入る。
- 自分で `UIPasteboard` を読む `paste(_:)` は、キーボードの上の段のペーストから呼ばれても、iOS が「ペーストを許可」を尋ねた (2026-10-18、シミュレータ)。尋ねている間はアプリのメインスレッドが止まる。`pasteConfiguration` を持たせてシステムから渡される形にしても、キーボードの上の段からは尋ねられた。`UIPasteControl` からは尋ねられず、代わりの Host に `insertText("こんにちは https://example.com/?a=1 👋")` が届いた。
- キーボードの上の段の取り消し・やり直し・ペーストは外した (`inputAssistantItem` の項目を空にする)。手元の文書は削除キーを繰り返させるための飾りで取り消すものがなく、そのペーストは許可を尋ねる。
- `UIPasteControl` は iOS が別に描くので、列に付けたダークの見た目 (`overrideUserInterfaceStyle`) に従わず、`systemGray5` を渡すと明るい灰色で描かれた。ほかのキーの実際の色 (#262629) を直接渡している。

## 操作パネルを黒い帯に置く

## iPadOS に取られるハードウェアキーボードのショートカット

- シミュレータ (iPad Air 11 インチ M4、iOS 26.5) で、⌘ と英数字・記号の組み合わせ 44 通りを押し、Mac の画面のビューに届くかを調べた (2026-10-18)。XCUITest の `typeKey` で押した。
  - 何もしていない状態では、⌘B・⌘E・⌘F・⌘G・⌘I・⌘M・⌘N・⌘O・⌘Q・⌘R・⌘U・⌘- の 12 通りで、⌘ だけが届いて文字が届かなかった (2 回とも同じ)。iPadOS 26 のメニューバーの項目 (太字・検索・新規・開く・しまう・終了など) と重なる。
  - `UIKeyCommand` を `wantsPriorityOverSystemBehavior` 付きで宣言すると、⌘B・⌘E・⌘F・⌘G・⌘I・⌘U・⌘- は押したキーがそのまま `pressesBegan` に届くようになった (宣言した動作は呼ばれない)。⌘M・⌘N・⌘O・⌘Q・⌘R は宣言しても届かない。⌘Tab・⌘Space・⌘H は iPadOS のアプリ切り替え・検索・ホームが受け取る。
  - ⌘M・⌘O・⌘Q・⌘R の文字のキーは、アプリへの入口 (`UIApplication.sendEvent`) にも来なかった (⌘ の押し離しだけが来る。⌘Q では ⌘ も取り消しで終わる)。iPadOS がアプリの外で受け取っているので、アプリからは受け取れない。代わりに「…」の「Mac のショートカット」から送る。
  - アプリの標準のメニューを `buildMenu` で外すと、かえって ⌘A・⌘C・⌘V・⌘X・⌘Z・⌘, も届かなくなり、宣言と組み合わせるとアプリが落ちた。外す方法は採らない。
  - Mac の画面のビューと直接入力の入力先の両方で、⌘・⇧⌘・⌥⌘・⌃⌘ と英数字・記号の組み合わせを宣言している。宣言した動作が呼ばれたときは、そのキーを修飾キー付きで送る。
  - 1 回目の起動直後や、⌘Tab・⌘Space で iPadOS の画面が開いた直後は、次のキーが届かないことがある。比べるときは、起動後に普通のキーを 1 回押してから始め、iPadOS の画面を開くショートカットは最後に押す。
- ⌘. は届くが、iPadOS はキーの情報から ⌘ を外して渡す (修飾キーが 0)。Mac では . だけが打たれていた。Host は修飾キーの押し離しを覚えているので、修飾キーでないキーには押されている修飾キーを載せる (`HeldModifiers.keyEvent`)。試験用の組み立てで、⌘ を押している間の . に ⌘ のフラグ (0x100000) が付き、離したあとは付かないことを確かめた。
  - 修飾キーが押されたまま残ると、そのあとのキーがすべてショートカットになってしまう。⌘Tab と ⌘Space のあとも ⌘ の押し離しが対になって届くことを、シミュレータで確かめた。

## 英数・かなのどちらが効いているかを示す

- iPad のキーボードで日本語を打つときに、Mac の日本語入力が英数とかなのどちらかを、特殊キーの列の英数・かなのキーの色で示す。Host が今の入力ソースを読み、変わるたびに `macInputMode` で知らせる。
- 入力ソースの分け方 (`MacInputMode`): キー配列そのもの (ABC など) と日本語入力の英字 (`com.apple.inputmethod.Roman`) は英数、日本語入力のひらがな・カタカナ・半角カナ (`com.apple.inputmethod.Japanese`・`.Katakana`・`.HalfWidthKana`) はかな、全角英字や他の言語の入力はどちらでもない。ID は、この Mac に入っている日本語入力 (ローマ字入力・かな入力) の入力ソースから読んだ (2026-10-18)。有効な入力ソースは ABC とローマ字入力のひらがなで、Host と同じ読み方でそれぞれ英数・かなになった。
- 入力ソースが変わった知らせ (`kTISNotifySelectedKeyboardInputSourceChanged`) は分散通知で届く。AppKit はアプリが前面にない間、分散通知を止める ([suspended](https://developer.apple.com/documentation/foundation/distributednotificationcenter/suspended))。既定の登録では、止まっている間の知らせは前面に来るまでまとめて持ち越される (SDK のヘッダーの `NSNotificationSuspensionBehaviorCoalesce`)。Host はメニューバーの常駐アプリで、メニューを開いたあと前面から外れると止まるので、`deliverImmediately` で登録する。
  - 試験用のアプリで確かめた (2026-10-18)。一度も前面に来ていないアプリは止まっていない (`suspended` が false) ので、AppKit が前面から外したときと同じく `suspended` を true にした (前面に出して外すと、利用者のアプリから入力を奪うため)。別のプロセスから知らせを送ると、既定の登録には 3 秒待っても届かず、止めるのをやめたときに届いた。`deliverImmediately` の登録にはすぐ届いた。
  - 同じプロセスに両方の登録があると、`deliverImmediately` の側に届いた時点で持ち越していた知らせもまとめて届く (SDK のヘッダーのとおり)。比べるときは 1 回に 1 通りだけ登録する。
- シミュレータで、代わりの Host から「かな」、12 秒後に「英数」を知らせると、かなのキー、英数のキーの順に青くなった (VoiceOver の値も「入力中」が移る)。

## 音声入力の流れを読み直して直したこと

- 2026-10-18 に、別のエージェントに音声入力の流れ (iPad のマイク、Host の押し直し、補助アプリ) を読ませ、指摘を一つずつコードと照らして直した。
- Typeless が動いていないときに始めると、Host は押すと決めた時刻を覚えてから Typeless の起動を待っていた (最大 20 秒)。待つ間に iPad で離すと、完了の判断のときには覚えた時刻から 1 秒を超えていて、まだ録音していない Typeless の状態を見て「止める必要がない」と判断し、押さなかった。Typeless は録音したまま残る。起動を待つのを、押すと決める前にした。
  - 試験用の組み立てで、Typeless の代わり (起動に 2 秒、開始の 0.3 秒後に録音が始まる) を使って確かめた。直す前は 1 回しか押されず録音が残り、直したあとは 2 回押されて止まった。キーは Mac へ送らず記録しただけ。
- iPad で離してすぐ (Typeless が止まったのを Host が知るまでの 0.3〜0.6 秒以内に) また押すと、前の聞き取りの終わりの知らせが新しい要求のあとで iPad に届き、iPad は始めたばかりのマイクを止めていた。Host も同じ知らせで、補助アプリの新しい聞き取りの準備を消していた。iPad から始めさせて、まだ Typeless が聞き取りを始めていない間は、聞き取りの終わりを知らせず、準備も消さない。始まらなければ、押し直しのあとで知らせる。
- 補助アプリの返事を待つ間 (最大 1.5 秒) に離すと、遅れて届いた返事で Typeless を始めていた。押し直しの途中で切れたときも、残りの押し直しで始めていた。どちらも、その時点で新しい要求が来ていれば (切れたときも新しい要求とみなす) 何もしない。
  - 要求の番号と、始めさせて確かめていない要求は、Kit の `VoiceInputRequests` にまとめて単体テストで固めた。
- 補助アプリの返事の待ち時間切れが前の要求のものでも、次の要求の返事を待つのをやめていた。待ち時間切れに要求の番号を持たせた。
- Typeless のマイクが「自動検出」のままのときに Host が設定を書き換える処理は、録音が止まった瞬間に Typeless を終了させていた。止めたあとに文字にして貼り付ける数秒の間で、その結果が失われる。8 秒続けて録音していないときだけ進め、2 分録音が続くなら終了させない。同時に 2 つ走らないようにもした。
- iPad のマイクのエンジンは、AirPods をつなぐ・外すなどの経路の変更や、電話・Siri による中断で止まる。止まっても始め直さず、話しても Mac に無音しか届いていなかった。止まったら同じ送り先で始め直す。シミュレータのマイクは Mac の既定の入力 (この Mac では内蔵マイク) を録るので、始め直しはビルドまでにしている。
- 止めたとき、補助アプリにたまっている iPad の声が鳴らし始めのたまり具合 (150ms) に届いていないと、残りは鳴らないまま、鳴らし終えるのを待つ処理が 7 秒の時間切れまで待ち、その間 Typeless は聞き取りを続けていた (iPad を裏に回した直後に止めたときなど)。止めたら、たまりきっていなくても残りを鳴らす (`PCMJitterBuffer.playRemaining`)。単体テストで、たまりきる前に呼ぶと残りがすぐ鳴ることを確かめた。
- 直していない指摘: 補助アプリの処理の列が塞がっていると最初の 100ms が捨てられうること (Mac のマイクの音を流しているときなどに限る)。
- 押し直しが Typeless の「始めている途中」に当たると止めてしまうのでは、という指摘は、Typeless の中身 (xstate の状態機械) を読んで当たらないと分かった。`idle` で押すと `initializingForTapOrHold` に移り、入ったときにマイクを動かす (`startRecording`)。この間の押下 (`PRIMARY_KEY.DOWN`) は受け取る処理がなく、離した知らせ (`PRIMARY_KEY.UP`) は「始めている途中に離した」を覚えるだけ。始め終えると聞き取り (`recording_active.handsFree`) に移り、そこで初めて押下が止める操作になる。そのときはもうマイクが動いているので、Host は押し直さない。

## 映像

- ScreenCaptureKit で映す画面 (iPad で選ばれた画面、なければメインディスプレイ) を取り込み、VideoToolbox の HEVC で符号化する (作れない Mac では H.264)。低遅延レート制御を使い、プロファイルは HEVC Main (H.264 は ConstrainedHigh)、フレームの並べ替えはしない。
- 2026-10-18 に H.264 から HEVC に替えた。1920x1080 で 1 フレームに 2 ピクセルずつ流れる文字の画面を 60 フレーム、同じ 8.3Mbps で符号化して復号し、元との輝度の PSNR を比べると、H.264 は平均 27.4dB、HEVC は 39.6dB だった (この Mac、M5)。1 フレームを渡してから出てくるまでは、60fps で渡して H.264 が平均 5.3ms・最大 24.0ms、HEVC が平均 5.6ms・最大 14.5ms で、遅れは変わらない。
  - 映像の形式 (`VideoFormat`) に方式を持たせ、パラメータセットは H.264 の SPS・PPS、HEVC の VPS・SPS・PPS を順に送る。iPad は届いた方式で `CMVideoFormatDescription` を作るので、Host が H.264 に落としても映る。iPadOS 26 が動く iPad はどれも HEVC を復号できるので、iPad から対応を知らせる仕組みは足していない。
  - 送る形式が変わったので、Host と iPad アプリは一緒に入れ替える (片方だけ古いと、映像の形式を読めない)。
  - 単体テストで、HEVC と H.264 のどちらも、実際に送る大きさで符号化から復号まで通ることを確かめている。シミュレータでは、代わりの Host が HEVC で符号化した試験用の絵 (文字と四隅の色) が、iPad アプリの画面に向きも正しく映った。
  - 低遅延のエンコーダを 10 個同時に作ると、`VTCompressionSessionCreate` から戻らなくなった (テストを並列に走らせたとき。止まったプロセスのスタックで確かめた)。Host は 1 つずつしか作らないので、テストを順に走らせる。
- iPad 側は `AVSampleBufferDisplayLayer` に圧縮したまま渡して復号させる。
- ScreenCaptureKit は画面が変わらないとフレームを出さない。そのため、要求に応じたキーフレームと、念のための 30 秒ごとのキーフレームで回復点を作る。
  - 2026-10-18 までは 5 秒ごとだった。受け取りの返事付きで送るようになり、途中で失われるフレームはなく、iPad は描けなくなったら自分でキーフレームを頼むので、定期のものは保険でよい。大きなキーフレームは遅い回線で遅れの山になる。途切れずにスクロールする模様を本物のエンコーダで 40 秒送り、受け手を絞って比べた。10 Mbps・iPad の大きさでは、遅れが 100 ms を超えたフレームが 5 秒ごとで 34〜35 枚 (最大 359 ms)、30 秒ごとで 14 枚 (最大 231 ms)。5 Mbps・1920x1080 では 44 枚 (最大 414 ms) と 16 枚 (最大 290 ms)。届いた枚数も 30 秒ごとの方が 5% ほど多かった。
- 実機の iPad (2360x1640) では、2360x1532、14 Mbps で配信している。
- 取り込む大きさは、iPad の画素数と長い辺どうし・短い辺どうしで比べて決める (`CaptureSize.fitting`)。以前は横向きの 2360x1640 と縦横そのままで比べていたので、縦に置いた 1080x1920 のディスプレイは 922x1640 に縮んでいた。iPad を縦にすれば 1080x1920 のまま映せるので、縮めずに送る。古い比べ方に戻すと単体テストが落ちることを確かめた。
- 符号化から復号までの単体テストは、実際に送る大きさ (1920x1080、2360x1532、1080x1920、1326x2360) と Host と同じビットレート (`CaptureSize.bitRate`) で行う。ビットレートを 4Mbps に決め打ちしていたときは、大きな画面で 10 フレーム中 1〜2 フレームを低遅延のレート制御が落とした (縦横どちらの向きでも同じ)。Host の式なら 10 フレームとも届いた。
- 取り込みの大きさは始めたときに決まるので、Mac の解像度やメインディスプレイが変わると、映像が縮んだり別の画面を映したりして、触った位置とずれる (タッチの座標は毎回そのときのメインディスプレイで直すため)。Host は `NSApplication.didChangeScreenParametersNotification` を受けたら、メインディスプレイの ID・大きさ・画素数が取り込みを始めたときと違うときだけ、同じ映像の接続のまま取り込みと符号化を作り直す。iPad は新しいキーフレームと一緒に届く映像の形式で大きさを読み直す。蓋を閉じたこの Mac でも、メインディスプレイは内蔵の 1 台で、大きさ (1800x1169、3600x2338) は変わらないので、余計に作り直すことはない。
  - 外部ディスプレイに対応してからは、比べる相手をメインディスプレイではなく映している画面にした。通知を受けたら 0.5 秒待ってから画面の一覧を読み直し、映す画面を決め直す。

### 遅い回線での映像の送り方 (2026-10-18)

- 以前は、`MessageChannel` の送り待ち (`contentProcessed` がまだ来ていない数) が 4 以上のときに、符号化する前にフレームを捨てていた。`contentProcessed` は OS の送信バッファに入った時点で来るので、バッファが何秒分も吸い込むまで間引きが始まらない。
  - ループバックで受け手が 10 Mbps でしか読まないようにし、60 KB のフレームを 60fps で送ると、遅れは 0.3 秒から 3.3 秒まで増え続けた。本物のエンコーダで重い映像 (毎フレーム全体が変わる模様) を iPad の大きさ (2360x1532、14.5 Mbps) で送っても、10 Mbps の回線で遅れが 2.3 秒まで増え続けた。
- 今は iPad が、映像用の接続で受け取ったフレームごとに返事 (`videoFrameReceived`) を返し、Host は返事の来ていないフレームが 3 枚 (`VideoFlowControl.maxInFlight`) になったら、次のフレームを符号化せずに捨てる。遅れは、およそその枚数を送る時間に収まる。
  - iPad は Host に求められたとき (`acknowledgeVideoFrames`、映像の接続を受けたときに送る) だけ返事をする。返事を知らない古い Host に、知らないメッセージを毎フレーム送らないため。返事が一度も来ない古い iPad アプリには、前と同じく送り待ちの数で間引く。
  - 返事が 2 秒来なければ待つのをやめる (`stallTimeout`)。返事は描く前に返し、描く時間で Host を待たせない。
  - シミュレータの試験アプリ (本物の iPad の画面のファイルをそのまま組んだもの) で、代わりの Host が求めたときは 5 枚すべてに返事が来て、求めないときは 1 つも来ないことを確かめた。
- 捨てた割合からビットレートも変える (`BitRateController`)。詰まったまま同じ大きさで送ると、間引かれて動きがカクつくため。
  - 2 秒ごとに見直し、捨てた割合が 1 割以上なら 0.6 倍に下げ、捨てない窓が 3 つ続いたら 1.25 倍に上げる (上限は `CaptureSize.bitRate`、下限は 1.5 Mbps)。1 秒ごとだと、窓を切り替えたときのような大きな 1 枚を送る間に捨てた分 (5 Mbps で約 9 枚、15%) だけで下げてしまった。キーフレームの返事を待っている間に捨てた分も数えない。
  - 回線が埋まっていた間に届いた量 (前の返事のときにはもう送っていたフレームの、前の返事からの時間) から回線の速さを見積もり、その 85% より下げない。それ以上縮まない映像では、ビットレートを下げてもエンコーダがフレームを落として合わせるだけで、枚数が減る (見積もりを入れる前は 5 Mbps の回線で 1.8 Mbps まで下げ、毎秒 5〜6 枚になった)。
  - 符号化を続けたまま `kVTCompressionPropertyKey_AverageBitRate` を変えると、6 枚ほどで 1 枚が小さくなることを単体テストで確かめた (1280x720 で 20 Mbps から 2 Mbps に下げ、約 40 KB から 8〜12 KB)。
- ビットレートを上限の 7 割より下げたら「回線が遅いため、画質を下げています」、8.5 割まで戻したら「画質を戻しました」を iPad に 3 秒出す (`videoQuality`)。知らせは種類 (画面・画質) ごとに持ち、画面を替えた知らせで画質の知らせが消えないようにした (同時に送ると両方出て、2 秒と 3 秒でそれぞれ消えることをシミュレータで確かめた)。Host は新しい映像の接続を受けたら、下げたかどうかを初めからにする (新しい取り込みは上限から始まるので、続けて下げたときの知らせが出なくなっていた)。映像がぼやけた理由が分からないため。境目で揺れて何度も出ないよう、下げたと決める値と戻したと決める値を離し、Host は同じことを続けて送らない。シミュレータの試験アプリで、代わりの Host が送った 2 つの知らせが出て、3 秒で消えることを確かめた。画面の切り替えの知らせと同じ仕組みにまとめたので、そちらも出て消えることを確かめ直した。
- iPad の「…」の「接続の状態」に、Mac が 2 秒ごとに送る映像の状態 (`videoStats`: 形式・大きさ・今のビットレートと上限・往復の遅れ) と、その間に iPad に届いた枚数と量を出す (2026-10-18)。記録を読むのは不具合の報告があったときだけにしているので、遅い・カクつくと感じたときに、回線のせいかを iPad で見られるようにした。
  - Mac のメニューにも、iPad へ送っている映像の状態を 1 行で出す (`VideoStats.summary`)。iPad で遅い・粗いと言われたときに、Mac の前でも回線のせいかを見られるように。書き方は単体テストで固め、メニューの見た目は画面に出さずに描いて、折り返しても読めることを確かめた。
  - 往復の遅れは、受け取りの返事が届いたとき、届いたうちの最後のフレームを送ってからの時間を 2 割ずつ混ぜてならしたもの。返事を返さない古い iPad では出さない。
  - シミュレータの試験アプリで、代わりの Host が送った状態 (HEVC・1920x1080・8.0 Mbps・上限 14.5 Mbps・42 ms) がそのまま出ることを確かめた。
  - 別のエージェントの指摘で直したこと。映像を止めると、届いた量の数え始めが止めた時刻のまま残り、戻った直後の枚数を止めていた時間で割っていた (1 分裏にいると毎秒 1 枚ほどと出る)。止めたら数え始めを空に戻す。映像を止めた直後に届いた状態で、止める前の値を出し直していたので、映像がない間は捨てる。往復の遅れは、取り込みを作り直した直後は測れていないだけなのに「この Mac は測らない」と出ていたので、作り直しで引き継ぎ、測れていない間は「測っています」と出す。止めた取り込みのエンコーダから遅れて出たフレームは、同じ接続で作り直した取り込みの映像に混ぜない。
- iPad が低電力モードのときや、本体が熱い (`thermalState` が serious 以上) ときは、映像を毎秒 30 枚にしてもらう (`videoFrameRate`、2026-10-18)。長く使うときの復号と描画の電池と熱を抑えるため。iPad はつないだときに 60 でなければ頼み、状態が変わったら頼み直す。Mac は取り込みの間隔とエンコーダの想定を作るときに決めるので、作り直す (返事の状態とビットレートは引き継ぐ)。「接続の状態」に毎秒の上限を出す。
  - 熱さが serious と fair の境で揺れると、頼み直すたびに Mac が取り込みを作り直し、映像が途切れる (別のエージェントの指摘)。減らすのは serious 以上になったとき、戻すのは nominal まで冷えたときにした。
  - シミュレータでは低電力モードを切り替えられないので、試験アプリの写しだけ低電力モードとして動かし、つないですぐ (映像の接続より先に) 30 枚を頼むことと、「接続の状態」に減らしていると出ることを確かめた。Mac が取り込みの間隔を変えるところは、利用者の画面を取り込むことになるので、ビルドまでにしている。
- 別のエージェントに読ませて直したこと (2026-10-18)。
  - キーフレームの返事を待つ間を数えない判断は、返事が来たことのある iPad だけにする。返事を返さない古い iPad アプリでは、覚えているキーフレームが消えず、見直しがほぼ止まっていた。最初の返事が来るまでは間引かないので、最初のキーフレームで捨てたと数えることもない。
  - 映す画面を替えるたびに取り込みを作り直すので、返事を返す iPad かどうかと、下げたビットレートが失われていた。遅い回線では、最初の返事を待つ間に送り待ちが積み上がる。同じ映像の接続なら、前の取り込みから引き継ぐ。
  - 回線の限界付近では、6 秒ごとに 1.25 倍へ上げて詰まり、下げる、を 8 秒周期で繰り返していた。下げたときに見積もった回線の速さの 95% を天井にし、天井までは上げ、超えるのは捨てない窓が 6 つ (12 秒) 続いたときに 1.1 倍だけ試す。重い映像・iPad の大きさ・10 Mbps で 40 秒流すと、詰まる回は 20 秒あまりに 1 度になり、それ以外は遅れ 56〜66 ms・毎秒 15 枚で落ち着いた。
- 本物のエンコーダと Kit の部品を ScreenStreamer と同じ順に組み、受け手が決めた速さでしか読まないループバックで比べた結果 (毎秒届いた枚数、遅れの平均)。
  - 100 Mbps の回線: 前と同じ (1 枚も捨てず、ビットレートも変えない)。
  - 重い映像、iPad の大きさ、10 Mbps: 前は毎秒 17 枚・遅れ 1.8〜2.1 秒で増え続けた。今は毎秒 15〜16 枚・57 ms。
  - 重い映像、1920x1080、5 Mbps: 前は毎秒 15 枚・遅れ 2.6〜4.0 秒。今は毎秒 12〜13 枚・65〜97 ms。
  - スクロールする軽い映像、iPad の大きさ、10 Mbps: 前は毎秒 60 枚・10 ms。今は毎秒 56 枚・5 ms (大きな 1 枚を送る間の数枚を捨てる)。

## Mac の画面のロック (2026-10-18)

- ロック中に iPad から操作できるかを、利用者の Mac をロックせずに一次情報で調べた。
  - Apple の DTS (Quinn) は、ScreenCaptureKit はログインした GUI のセッションで使えるので動くはずだが、ロック解除の画面には特別なセキュリティの制限がいくつもあり、それに当たるかもしれない、と答えている ([Apple Developer Forums 756908](https://developer.apple.com/forums/thread/756908))。ログイン前 (pre-login) では ScreenCaptureKit は使えない。
  - 開発者の報告では、ロックされると ScreenCaptureKit は取り込みを止め、解除しても自分では戻らない ([opendisplay #296](https://github.com/peetzweg/opendisplay/issues/296))。ロック中は macOS が取り込みを断る ([claude-human](https://github.com/drkostas/claude-human))。
  - ロック画面にパスワードを打てている claude-human は、合成したキーの出来事ではなく、Karabiner の DriverKit の仮想キーボード (root で動く補助) を使っている。合成した出来事が届かないところでも、本物のキーボードとして扱われるから、としている。ドライバを入れる作りは採らない (Mac 全体の状態を変えるため)。
- そこで、ロック中に解除はできないものとして、次の 2 つをする。
  - Host は loginwindow のロックと解除の知らせ (`com.apple.screenIsLocked`・`com.apple.screenIsUnlocked`、分散通知を `deliverImmediately` で受ける) を受け、iPad に `macScreenLocked` で知らせる。iPad は「Mac の画面がロックされています」を出す。iPad がつないだ時点のロックは、セッションの情報 (`CGSessionCopyCurrentDictionary`) の `CGSSessionScreenIsLocked` で読む。ロックされていないこの Mac では、このキーはなかった。
  - 解除されたら、映像の接続があれば取り込みを作り直す。
- iPad の知らせは、代わりの Host が送ったロックと解除で出て消えることをシミュレータで確かめた。
- Host の見張り (`ScreenLockMonitor.swift`) は、ファイルをそのまま写して知らせの名前だけ試験用の固有の名前に替え、分散通知を止めた状態 (前面にない常駐アプリと同じ) で、別のプロセスから送ったロックと解除がその順に届くことを確かめた。本物の名前で送らないのは、画面のロックに合わせて自分もロックするアプリ (パスワード管理など) にも届くため。名前は、この Mac (macOS 26.2、25C56) の loginwindow の実行ファイルに `com.apple.screenIsLocked` と `com.apple.screenIsUnlocked` の両方が入っていることで確かめた。解除での作り直しは、画面の切り替えや映像の枚数の変更と同じ `startStreamer(on:)` を呼ぶ。実際にロックして解除する流れは、利用者の Mac をロックすることになるので動かしていない。

## 外部ディスプレイ

- 2026-10-18 に「Mac が外部ディスプレイにつながっているときの対応」を求められた。このとき Mac は蓋を閉じて外部ディスプレイ 2 台につながっていた (メインの VG258 と、その左の 1920x1080)。メインディスプレイしか送らなかったので、左の画面にあるものは iPad から見ることも触ることもできなかった。
- iPad の「…」に「映す画面」を出し、1 台ずつ選んで映す。複数の画面をまとめて 1 枚にする方式は採らなかった。ScreenCaptureKit のフィルタは 1 台の画面しか取り込めず、画面ごとの取り込みを合成することになる。しかも iPad では 2 台分が横に並んで小さくなるので、結局拡大して使うことになる。
- 画面の一覧は Host が読んで iPad に送る (`ControlMessage.displays`)。並べ方と置き場所の判定は Kit の `RemoteDisplay` にまとめ、単体テストで固めた。
  - 名前は `NSScreen.localizedName` から読む。この Mac の左の画面は名前が空だったので (`system_profiler` でも「Display」とだけ出る)、空なら「名前のない画面」とし、メインディスプレイから見た置き場所 (中心どうしのずれが大きい向き) を必ず添えて見分けられるようにした。
  - `NSScreen` はメインスレッドで読む。Host のサーバーは自分のキューで動くので、メインスレッドで一覧を作ってから受け取る。
  - ミラーリングの 2 台目以降 (`CGDisplayMirrorsDisplay` が 0 でない) は同じものが映るので除く。
- 選ばれた画面は、`CGDisplayCreateUUIDFromDisplayID` の UUID で Host の設定に覚える。外れているあいだはメインディスプレイを映し、つなぎ直されたらまた選ばれた画面を映す。蓋を開けたり閉じたりして内蔵の画面が出入りしても、外部ディスプレイを選んでいればそれを映し続ける。
- タッチの位置は、映している画面の `CGDisplayBounds` の上の割合として届く。この Mac で、送る代わりに記録する試験用の組み立てに Host の `InputInjector.swift` を入れて確かめた (2026-10-18)。左の画面 (-1920, 0, 1920, 1080) の右端 (割合 1) は x=0 になり、メインの左端にあたるので、ポインタが隣の画面へ移ってしまった。映像の外の黒い帯を触ると割合は 1 に丸められるので、実際に起きる。そこで右端と下端は、画面の内側に 1 ポイント入れる (直したあとは -1 と 1079)。
- 選び直したときは、ポインタを新しい画面の中央へ動かす。接続したときは動かさない。
  - 画面ごとに操作スペースを持つ設定 (この Mac は `com.apple.spaces` の `spans-displays` が 0) では、Mission Control はポインタのある画面にだけ効く ([MacMost](https://macmost.com/23-tips-for-using-desktop-spaces-on-your-mac.html))。
  - 3 本指の払いで合成する Dock のスワイプがどの画面に効くかは、Apple の資料 ([操作スペース](https://support.apple.com/guide/mac-help/work-in-multiple-spaces-mh14112/mac)) に書かれていない。確かめるには利用者の Mac で操作スペースを切り替えるしかないので、ポインタを映している画面に置き、ポインタで決まる場合でも映している画面に効くようにした。
- アプリが前に出たら (`NSWorkspace.didActivateApplicationNotification`)、そのアプリの手前のウィンドウ (`kAXFocusedWindowAttribute`) の位置を読み、重なりの一番大きい画面が映している画面と違えば、そちらを映す。iPad のアプリ切替で選んだアプリが、映していない画面にあって見えないままになるのを防ぐ。
  - Mac を直接使っている人の操作でも前に出るので、このときはポインタを動かさない。
  - 手前のウィンドウがないとき (デスクトップを触った Finder など) は追わない。別の画面のウィンドウを代わりに選ぶと、触った画面から離れてしまうため。
  - 位置の読み方は、試験用の組み立てで確かめた (2026-10-18)。自分の透明でマウスを受けないウィンドウを両方の画面に置き、Host と同じ読み方で読むと、置いた位置 (左の画面の (-1720, 150, 400, 300) と、メインの (200, 150, 400, 300)) がそのまま返り、15 と 16 に割り当たった。前に出していないアプリは手前のウィンドウを持たない (`kAXErrorNoValue`) ので、確かめにはウィンドウの一覧から取ったものを使った。`NSApplication` の起動を済ませていない組み立てでは、AppKit がアクセシビリティの問い合わせに答えない (`kAXErrorNotImplemented`)。
- 映す画面が替わったら、iPad の上に「(画面の名前) を映しています」を 2 秒だけ出す。前に出たウィンドウを追って Mac が替えたときに、操作していない画面が急に替わった理由が分かるように。つないだときは出さない。代わりの Host から Mac が替えた知らせを送り、シミュレータで出て 2 秒で消えることを確かめた (2026-10-18)。
- 一度に映すのは 1 台なので、画面をまたいでウィンドウをドラッグできない。代わりに「…」の「手前のウィンドウを移す」で、手前のアプリの手前のウィンドウ (システム全体の `kAXFocusedApplicationAttribute` から) を選んだ画面へ移し、その画面を映す。
  - 新しい位置と大きさは Kit の `RemoteDisplay.moved` で決める。元の画面での寄せ方の割合を保ち、移す先に収まらなければ縮める。範囲は `NSScreen.visibleFrame` (メニューバーと Dock を除く) を画面の座標に直したもの。大きさを先に変えてから動かす。
  - アプリの「ウインドウ」メニューの「(画面の名前)に移動」を押す方法もあるが、項目の名前が言語やアプリによって違い、持たないアプリもあるので、ウィンドウの位置を直接変える。
  - 試験用の組み立てで、自分の透明なウィンドウを Host と同じやり方で動かして確かめた (2026-10-18)。メインの (1020, 368, 800, 532) は左の画面の (-900, 368) へ、左の画面の (-1820, 68, 600, 432) はメインの (100, 68) へ移った。自分のウィンドウをアクセシビリティで動かすと AppKit が呼んだスレッドで処理するので、試験ではメインスレッドから動かす (別のスレッドからだと AppKit の検査で止まる。Host が動かすのは別のアプリのウィンドウなので当たらない)。
  - iPad の「…」→「手前のウィンドウを移す」→「名前のない画面 (メインの左)」で、代わりの Host に `moveFrontWindow(toDisplay: 15)` が届くことをシミュレータで確かめた。代わりの Host を前の Kit のまま動かすと、新しい知らせを読めずに捨てる (新しい版の知らせは読み飛ばす作り)。
- 別のエージェントにこの日の差分を読ませ、指摘を確かめて直した (2026-10-18)。
  - 映す画面が ScreenCaptureKit の一覧にないと、取り込みを始められず映像の接続を閉じていた。iPad は 0.5 秒後につなぎ直すので一覧が追いつけば戻るが、CoreGraphics には見えても取り込めない画面では黒いまま繰り返す。メインディスプレイに落として映すようにした。
  - メニューを開いている間に外れた画面を選ぶと、iPad は先にその画面を映したことにし、Host は黙って無視していた。Host が今の画面を知らせ直すようにした。
  - 続けてアプリを切り替えると、前のアプリのウィンドウの問い合わせが後から返り、手前にないアプリの画面へ切り替わりうる。アプリが前に出るたびに数を増やし、古い結果は使わない。
  - 画面を外した直後、Host が映す画面を替えるまで (0.5 秒の待ちとメインスレッドの往復)、`CGDisplayBounds` は大きさ 0 を返し、タッチが (-1, -1) へ行っていた。大きさ 0 ならメインディスプレイの上として扱う。試験用の組み立てで、ない画面 (999) へのタッチが (0, 0)・(1919, 1079)・(960, 540) になることを確かめた。
  - 同じ機種を同じ側に 2 台並べると、名前も置き場所も同じになる。左から番号 (「DELL U2720Q 1 (メインの右)」) を付ける。
  - 大きさを変えられないウィンドウは、縮めた大きさで計算した位置に置くとはみ出す。実際の大きさを読み直して移す先に収め、位置を変えられなければ大きさを戻す。
  - 「最後に映した画面を覚える」ので、選んだ画面が外れている間に別の画面のウィンドウを追うと、覚える画面もそちらに替わる、という指摘もあった。README に書いたとおりの動きなので、変えていない。
  - 高さ 0 の入力ビューでも、キーボードの位置の知らせで映像の範囲が縮むのでは、という指摘は、シミュレータで確かめた。Mac の画面のビューが入力先の間に届いた知らせは、どれも画面の外 (上端 820) で、範囲は縮まない。
- 画面の下端から上へ払ったときの Dock は、⌃F3 (Dock にフォーカスを移動) で出す。Dock は 1 台の画面にしかなく、⌃F3 はその画面に出すので、映していない画面にあると iPad では見えないまま Dock にキーボードの入力が移る。そこで iPad は ⌃F3 のキーではなく `showDock` を送り、Host が Dock のある画面を映してから ⌃F3 を押す。
  - Dock のある画面は、ウィンドウサーバーが持つ Dock の範囲 (`SLSGetDockRectWithReason`) と、その範囲に一番合う画面 (`SLSCopyBestManagedDisplayForRect`) で決める。どちらも SkyLight の非公開の関数で、[yabai](https://github.com/asmvik/yabai) の `display_manager_dock_display_id` と同じ読み方。リンクせずに `dlsym` で探し、見つからなければ画面を替えずに ⌃F3 だけ押す。
  - 最初は、ウィンドウの一覧で Dock の層 (20) にある Dock のウィンドウの位置から決めていた。この Mac では (0, 0, 1920, 1080) でメインを指していたが、ウィンドウサーバーの Dock の範囲は (-1550, 1080, 1179, 0) で、左の画面の下端に隠れていた (2026-10-18)。Dock の層のウィンドウは Dock の帯そのものではなかった。Dock を動かさずに、2 つの読み方を見比べて分かった。
  - 隠れている Dock の範囲は高さ 0 で画面の端に載る (下なら画面の下端の y)。重なりの大きさでは決められないので、画面の選び方もウィンドウサーバーに任せる。
  - [DockAnchor](https://github.com/bwya77/DockAnchor) は Dock のアクセシビリティのウィンドウの位置で見分けているが、この Mac で読むとウィンドウの一覧は空だった (隠れているときに読めないとみられる)。
  - Dock を映している画面へ動かす方法 (ポインタを下端に押し付ける) は採らなかった。合成したポインタの動きで Dock が移るか分からず、確かめるには利用者の Dock を動かすことになるため。
  - シミュレータで下端から払うと、800pt から始めたときは代わりの Host に `showDock` が届いた。816pt からだとシミュレータの OS が受け取り、アプリに届かなかった (ホームインジケータの範囲)。
- どの画面を映すか (覚えている画面が外れたらメイン、戻ったらまた覚えている画面、外れた画面を選ばれたら知らせ直す、取り込めなければメインに落とす) と、iPad に知らせ直すかは、Kit の `DisplaySelection` で決める。Host はその結果に合わせて、取り込み・タッチを届ける画面・拡大の範囲を替えるだけにした。別のエージェントの指摘はこの判断の取り違えに集まっていたので、順に起きる場面を単体テストで固めた。
- iPad 側も別のエージェントに読ませ、指摘をシミュレータで再現してから直した (2026-10-18)。
  - 画面を替えると、替えた知らせで映像を置き直したあとに新しい画面の大きさが届く。大きさが変わっても置き直していなかったので、映像のレイヤーは前の画面の縦横比の枠のまま残った。代わりの Host で 1800x1169 から画面を替えて 1920x1080 を送ると、レイヤーは (0, 26.8, 1180, 766.3) のままだった。16:9 から縦に長い画面へ替えると、映像が枠の中に縮んで描かれ、触った位置とずれる。大きさが変わったら置き直すようにし、1920x1080 から 1800x1169 へ替えたときに (0, 78.1, 1180, 663.75) から (0, 26.8, 1180, 766.3) へ置き直されることを確かめた。
  - 「操作の一覧」を開いている間も、Mac の画面のビューが入力先のままなので、ハードウェアキーボードのキーが Mac へ送られていた (シミュレータで z を押すと届いた)。上に何かを出している間は押したキーを送らない。離したキーは送る。押している途中で入力先が替わると押したまま残り、Host のキーのリピートが止まらなくなるため。対応する押下のない離鍵は Mac では何も起こさない。
  - 画面を替える前に拡大の範囲の頼みが待っていると、替えた直後に古い範囲が送られうる。画面が替わったら、拡大を戻すのと一緒に全体を頼み直す。
  - つなぎ直している間に「映す画面」で選ぶと、Mac に届かないのに iPad の表示だけ替わっていた。つながっている間だけ受け付ける。英数・かなの表示も、つなぎ直すまで消す。
  - ペーストの直後に打った文字が先に届きうること、Mac から古い画面の知らせが届いて一瞬戻ることも指摘されたが、どちらも最後は正しい状態になり、起きる間も短いので直していない。
- 画面を替えると、拡大していた範囲は意味がなくなる。Host は送る範囲を全体に戻し、iPad も拡大を戻して全体を頼み直す。画面を替える前に iPad が頼んだ範囲が後から Host に届いても、そのあとの全体の要求で上書きされる。
- iPad の側は、画面を出さないシミュレータ (iPad Air 11 インチ M4、iOS 26.5) で確かめた (2026-10-18)。iPad アプリの本物の画面のファイルを組み、接続先だけを 127.0.0.1 で待ち受ける代わりの Host にした。代わりの Host は Bonjour で広告しないので、利用者の iPad の一覧には出ない。
  - 「…」に「VG258 (メイン)」と「名前のない画面 (メインの左)」が出て、選ぶとチェックが移り、代わりの Host に `selectDisplay` と全体の範囲の要求が届いた。
  - 代わりの Host が 1 台だけの一覧を送ると「映す画面」の項目は消え、iPad は映している画面が替わったとみて全体を頼み直した。
  - メニューは下の操作パネルから上へ開くので、iOS の決まりで項目は下から並ぶ (ボタンに近い方が先頭)。左から並べた先頭の「名前のない画面」がボタンのすぐ上に来る。

## Mac の音を iPad で鳴らす

- 初めは「Mac の音は iPad に送らない」を既知の制約にしていた。2026-10-18 に、iPad の「…」から入れる切り替えとして加えた。既定は切ってあり、入れなければ前と同じ動きになる。
- Host は、iPad が頼んでいる間だけ、補助アプリを除く全プロセスの出力をまとめる非公開のプロセスタップ (`CATapDescription(stereoGlobalTapButExcludeProcesses:)`) を作り、タップだけを入力に持つ非公開の集約デバイスを IOProc で読む。
  - `muteBehavior` は `.mutedWhenTapped`。読んでいる間だけ Mac で鳴らさないので、Host が落ちてタップが残っても Mac の音は消えない。
  - 補助アプリは、iPad の声と、Mac で直接話すときの Mac のマイクの音を鳴らしている。除かないと、Mac で話した声が iPad で鳴る。補助アプリのプロセスのオブジェクトは音を出し始めるまで現れず、起動し直すと変わるので、プロセスの一覧が変わるたびに見直してタップを作り直す。macOS 26 の `bundleIDs` で除く方法もあるが、除く側のタップでの効き方を確かめていないので使っていない。
  - 出力先の機器が変わるとタップの形式 (サンプルレート) も変わるので、`kAudioTapPropertyFormat` が変わっても作り直す。出力デバイスは集約デバイスに入れず、出力先が変わるたびに作り直さずに済むようにした。
- 送る形は 48kHz・ステレオ・16 ビット (約 1.5Mbps) で、20ms ごとの塊にする。すべて 0 の塊は送らないので、何も鳴っていない間は通信しない。映像の送信が詰まっても待たされないよう、操作用の接続で送る。送信待ちが 25 件 (0.5 秒分) を超えたら捨てる。
  - 2026-10-18 から、iPad が求めたら塊ごとに Opus の 1 パケット (128 kbps、平均 320 バイトほど) にして送る (`macAudioCodec(.opus)` → `macAudioOpus`)。無圧縮の 1.5 Mbps は 5 Mbps の回線の 3 割にあたり、映像の取り分を削るうえ、送信バッファでの遅れも大きくなるため。
    - AudioToolbox の Opus は、1 パケットを 20ms (960 フレーム) にでき、塊 1 つを渡すとその場で 1 パケットが出る。先頭の遅れは 312 フレーム (6.5ms)。AAC-ELD (10ms・先頭 240 フレーム) も作れたが、塊の長さと合う Opus にした。AAC-LC は先頭の遅れが 2112 フレーム (44ms) あるので使わない。
    - 求める形式は、iPad が「鳴らす」を送る前に毎回送る。知らない古い Host は読み飛ばして無圧縮で送り、求めない古い iPad アプリには Host が無圧縮で送る。iPad は Opus を戻せないときは無圧縮を求める。
    - iPad は、切断したときもためた音を捨て、次につないだときに前の音が鳴らないようにする。戻す側を作り直せなかったときは前のものを使い続ける (Mac にはもう Opus を頼んでいるので、なくすと無音になる)。
    - 単体テストで、左だけに鳴らした 440Hz を 1 秒、塊ごとに符号化して戻し、左の実効値が元と 0.05 以内、右がほぼ無音になることを、macOS と iOS のシミュレータの両方で確かめた (iPad で戻せるかを確かめるため)。再生の部品 (`MacAudioPlayer`) にパケットを渡し、手で回すエンジンで描いた音も、左の実効値が元と 0.05 以内、右がほぼ無音で、鳴らすのをやめて再開したあとも同じだった (macOS と iOS のシミュレータ。`feedOpus` を止めると左が 0 になってテストが落ちることも確かめた)。シミュレータの試験アプリは、「Opus で」を「鳴らす」の前に送った。音を流す試験はしない (シミュレータの音は Mac のスピーカーから出る)。
- iPad は、裏に回っても止められないよう無音を流しているのと同じエンジンに `AVAudioSourceNode` をつないで鳴らす。awdl の揺れで途切れないよう 100ms たまってから鳴らし、0.5 秒より遅れたら古い音から捨てる。
- iPad のマイクで聞き取っている間は鳴らさない。iPad のスピーカーの音をマイクが拾い、Mac の音が Typeless に入るため。
- iPad が裏に回っている間は Mac で鳴らす。接続は裏でも続くので、iPad をしまったまま Mac を開くと、Mac が無音のままになるため。
- 2026-10-18 に、iPad がつながっていない間に検証用のクライアントで確かめた。
  - タップの形式は 48kHz・2ch・Float32 (交互) で、変換は形式を変えるだけだった。頼んでから最初の塊が届くまで 0.13 秒。
  - 聞こえない 20kHz・0.01 の音を鳴らすと、届いた音の最大は 0.0102 だった。
  - 補助アプリが起動して点検の音 (0.01) を 1.5 秒鳴らしている間に、届いた塊は 0 だった。補助アプリは起動から約 0.2 秒で、デバイスを作る前に除かれていた。何も鳴っていない間も届かなかった。
  - iPad 側は、AVAudioEngine を手で回す単体テストで、左右の振り分け、たまってから鳴らすこと、マイクを使っている間は鳴らさないことを確かめた。左右を入れ替えるとテストが落ちることも確かめた。
  - iPad のアプリ全体は、画面なしで起動した iOS シミュレータ (iPad Air 11-inch (M4)) で確かめた。起動引数 `-playsMacAudio YES` で入れた状態にすると、つないですぐ Mac の音を頼んだ。点検の音は 0.5 秒 (約 25 塊) しか鳴らしていないのに、止めるまでの約 4.6 秒で 212 塊を送った。シミュレータのアプリが鳴らした音を Host の全体のタップがまた拾い、回り続けたためで、受け取って鳴らすところまで動いていると分かる (Mac のスピーカーは読んでいる間は消音されるので、聞こえない)。
  - 久しぶりに起動した直後のシミュレータで、一度だけ `BackgroundAudio` のエンジンの開始が落ちた (`AURemoteIO::Initialize` で音声サーバーへの問い合わせが時間切れになり、`abort`)。Mac の音を足す前のビルドと今のビルドを、起動直後のシミュレータで 2 回ずつ動かしても再現しなかったので、変更によるものではない。

### Mac の音と補助アプリの音の経路を読み直して直したこと

- 2026-10-18 に、別のエージェントに Mac の音と補助アプリの音の経路を読ませ、指摘をコードと照らして直した。
- 浮動小数の音を 16 ビットに直すとき、`min(max(x, -1), 1)` は NaN をそのまま通し、`Int16(NaN)` で実行時に止まる。Host は Mac のすべてのアプリの音を読むので、どこかのアプリが NaN を鳴らすと Host が落ちる。補助アプリが Mac のマイクの音を流すところも同じ。`PadAudio.int16` で NaN を無音にした。止まることは単独の組み立てで確かめ (`Fatal error: Float value cannot be converted to Int16 because it is either infinite or NaN`)、守りを外すと単体テストが同じ理由で落ちることも確かめた。
- 通信が詰まって一度に届くと、ためる場所が 0.5 秒分であふれる。古い音を 1 つずつ捨てていたので、そのあと送る速さと鳴らす速さが同じなら 0.5 秒遅れたままだった。Mac の音だけ、あふれたら鳴らし始めのたまり具合 (100ms) まで一気に減らす。iPad の声は Typeless に全部聞かせたいので、今までどおり 1 つずつ捨てる。
- 切ったあとや裏に回ったあとも、送られている途中の音 (最大 25 塊、0.5 秒分) が届き、たまると鳴っていた。鳴らす設定のときだけ受け取る。
- 出力先を替えた直後などに作り直しが失敗すると、取り込みは動かないまま、Mac のスピーカーにも iPad にも音が出なくなる (切り替えも直らない)。2 秒おきに 5 回まで作り直す。作り直しを確かめるには取り込みを実際に失敗させる必要があり、この Mac で取り込みを作ると Mac の音が鳴らなくなるので、ビルドまでにしている。
- 直していない指摘: 何も鳴っていない塊を送らないので短い無音が縮む (設計どおり、通信量を優先)。IOProc のスレッドでメモリを確保している (今のところ途切れは出ていない)。補助アプリが許可の確認で 1.5 秒止まる間の点検音の混入 (許可が会話中に下りた場合に限る)。

## タッチの読み替え

- 指の操作は UIKit のジェスチャー認識を並べず、`TouchInterpreter` という 1 つの状態機械で判定する。認識器を並べていた頃、実機で次の 2 つが起きた。
  - `isMultipleTouchEnabled` が既定の false のままで 2 本目の指が届かず、2 本指スクロールが成立しなかった。
  - 長押しの成立と同時に右クリックしていたため、「押して少し待ってからドラッグ」が右クリックになった。
- ユーザーの指摘で、長押しせずに払う操作はドラッグではなくスクロールにした (iPad の普段の操作に合わせた)。ドラッグは長押ししてから動かす。指を離したあとは `ScrollMomentum` で慣性スクロールする。
- トラックパッドやマウスのクリック (`UITouch.type == .indirectPointer`) は状態機械を通さず、押下と解放をそのまま送る。マウスのつもりで長押しして右クリックになるのを防ぐため。
- 入力の経路を別のエージェントに読ませて直したこと (2026-10-18)。
  - 2 本指でしばらくスクロールしてから親指や手のひらが触れると、3 本指の払い (Mission Control やスペースの切り替え) になっていた。スクロールの開始から 0.25 秒を過ぎて触れた 3 本目は無視してスクロールを続ける。指をずらして置く人の 3 本指の払い (1 本目が動き出した直後に残りの指が触れる) は今までどおり。直す前の動きにすると単体テストが落ちることを確かめた。
  - ペンやマウスのボタンを押している間に触れた指や手のひらを、離すまで無視する。押したままのボタンに、指の位置への移動やクリックが割り込んでいた。UI テストからはペンと指を同時に触れさせられないので、ビルドまで。
  - 押したままのキーを離すよう Mac に頼むのを、裏に回ったときだけでなく、前面のまま入力先を失ったとき (`.inactive`: コントロールセンター、Spotlight など) にもする。離した知らせがこのアプリに届かず、⌘ が Mac に残ると、以降のキーがすべてショートカットになる。シミュレータの UI テストからはコントロールセンターも Siri も出せなかったので、ホームに戻るとき (active → inactive → background) に、inactive でも頼みが届くことで確かめた。
  - 文字の挿入を、値か選択の位置のどちらかが変われば成功とみなす。選んだ文字を同じ文字で置き換えると値が変わらず、失敗とみなして打ち直し、二重に入っていた。試すと利用者が使っているアプリの入力欄に文字が入るので、ビルドまで。
  - 押したキーを、Host の記録 (debug) に中身ごと出していた。パスワードも打つので出さない。
  - 受け取った位置 (`NormalizedPoint`) も 0〜1 に丸める。iPad は送る前に丸めているが、範囲の外の値が届くと Mac は隣の画面の見えない位置を押す。
  - 直していない指摘: キーボードを出したまま回すと、キーボードの位置が回す前の寸法で計算されうること (回すとキーボードの位置の知らせも届き直す)。画面を替えた直後の一瞬、前の画面の縦横比で触った位置を直しうること (新しい画面の形式が届けば直る)。
- トラックパッドやマウスを使うと、iPadOS の丸いポインタと、映像に描かれた Mac のポインタが両方見えていた。Mac の画面の上では iPadOS のポインタを隠す (`UIPointerInteraction` で `UIPointerStyle.hidden()`)。形 (I ビーム・手など) は Mac 側にしかないため。上下や左右の黒い帯と、拡大した映像がキーボードの下に回り込んだところでは、iPadOS のポインタを出す。映像を映していない間 (つないだ直後、画面の切り替えや映像の張り直しの間) も出す (2026-10-18)。
  - 映像が届く前は、映像の範囲が画面全体として計算される (大きさが分からないので画面いっぱいに置く)。範囲だけで決めていたので、Mac のポインタがまだ見えないのに iPadOS のポインタも消えていた (別のエージェントの指摘)。iPad のセッションに「映像を映しているか」を持たせ、映像の形式が届いたら立て、映像の接続を張り直す・止めるときに下ろす。
  - UI テストの `hover()` はホバーの出来事を作るだけで (偽の Host に届いた位置は、重ねた位置によらず左上の 1 点だった)、ポインタの範囲を尋ねる処理は呼ばれない。シミュレータで iPadOS のポインタを動かすには Mac のマウスを取り込む設定が要り、利用者のポインタを奪うので使わない。代わりに、試験アプリの写しの中で範囲の要求 (`UIPointerRegionRequest`) を作って位置を入れ、本物の画面の配置で委譲先に渡した。映像があると中央は映像の範囲 (1180x820 の画面で y=78〜742) を返して形は `hidden`、上下の帯は範囲なし。映像が来ない代わりの Host では、中央も範囲なしだった。実機のポインタでは試していない。
- Apple Pencil (`.pencil`) も同じく、押下と解放をそのまま送る (2026-10-18)。初めは指と同じ状態機械を通しており、触れて動かすとスクロールになり、文字の範囲選択や描く操作には長押しが要った。Sidecar も Pencil はクリックとドラッグで、指はスクロールなので、それに合わせた。クリックの回数は Host の `ClickCounter` が数えるので、続けて触れるとダブルクリックになる。
- Typeless ボタンは UIKit の `UIButton` にしている。SwiftUI の `GestureState` は、システムに押下を奪われたキャンセルと指を離したことを区別できないため。キャンセルされたときは、押しっぱなしに切り替えて聞き取りを続ける。
- 合成したクリックには macOS がクリック回数を付けてくれないので、`ClickCounter` で自前で数える。
- 修飾キーを単体で送るときは、イベントの種類を `flagsChanged` にしないと、アプリが Command などを認識しない。
- 合成するキーイベントのフラグは、実際の Mac のキーボードに合わせる (`KeyboardMapping.eventFlags`)。
  - 矢印キーには Fn (`0x800000`) とテンキー (`0x200000`) のビットを付ける。この Mac の Mission Control のショートカットは、修飾キー `0x240000` (Control+テンキー) で登録されていて、テンキーのビットがない Control+↑ には反応しない。
  - Home・End・F キーなどには Fn のビットを、修飾キーには左右を区別するビットを付ける。
- 2 本指で広げたり縮めたりすると、iPad の上で Mac の画面を拡大する (`ScreenZoom`、5 倍まで)。Mac の文字は iPad では小さいため。
  - 2 本指の間隔の変化が 24pt を超え、かつ中心の移動より大きいときだけ拡大とみなす。それ以外は今までどおりスクロール。いったんスクロールと決まったら、途中で拡大には変えない。
  - 指の中心の下にある映像の位置が動かないよう拡大し、指が動いた分だけずらす。映像が画面より大きい向きでは、端に余白が出ないよう押さえる。1.05 倍まで縮めたら等倍に戻す。
  - タップやスクロールは、拡大した映像の位置を基準に Mac の座標へ直す。シミュレータで 2 倍のピンチ 1 回分を流し込み、映像の位置 (-790,-410、2360x1640) とタップの座標 (中央 0.585, 0.500、右寄り 0.710, 0.500) が計算どおりになることを確かめた (2026-10-17)。
  - XCUITest の `pinch` は、2 本の指を 4pt ほどの間隔から 28pt ほどまでしか広げず、実際の指の動きと違う。判定は単体テストで、画面への反映は動作を直接流し込んで確かめる。
  - 拡大しても文字がぼやけないよう、拡大が 0.2 秒落ち着いたら、見えている範囲 (余白 15%、画面と同じ縦横比、1/128 刻み) を Mac に頼む (`VideoRegion`)。Mac は拡大している間だけ画面を元の解像度で取り込み、その範囲を切り出して iPad の解像度で送る。映像の大きさは変わらないので、符号化をやり直さずに済む。
    - 切り出しは `VTPixelTransferSession` で行う。切り出す範囲を直接指定する項目はなく、元のフレームに clean aperture を付けて `kVTScalingMode_CropSourceToCleanAperture` で使わせる。範囲は画面の中心からのずれで、右と下が正。四隅を塗り分けたフレームで確かめた (2026-10-17)。
    - フレームごとに写っている範囲を付けて送り、iPad はそのとおりの位置に置く。取り込みの設定を変えている途中のフレームも、その範囲で正しく置ける。タッチの座標は画面全体を基準に直すので、切り出しとは関係なく変わらない。
    - 本物の ScreenStreamer をループバックでつないで確かめた。範囲を変えると、その範囲を付けたフレームがキーフレームから届き、映像の大きさは 2360x1532 のまま変わらなかった。iPad 側は、範囲付きのフレームが届いたときの置き場所と、2 倍に拡大したときに頼む範囲が計算どおりになることをシミュレータで確かめた。
- 3 本指で払うと、トラックパッドと同じ操作をする。iPadOS の 4・5 本指のジェスチャーとぶつからないよう、3 本指にしている。
  - 左右は操作スペースの切り替え。トラックパッドが出すのと同じ Dock スワイプのイベント (種類 30、HID 種別 23) を、開始・途中・終了の 3 つ合成して切り替える。欄の番号と値は [InstantSpaceSwitcher](https://github.com/jurplel/InstantSpaceSwitcher) (MIT) の macOS 26 以前向けの実装に合わせた。macOS 27 では追加の欄が要る。
    - 最初は Control+←/→ を送っていて、2026-10-17 18:23 に「3 本指スワイプで画面が動かない」と報告された。Dock の記録では、このとき切り替えは起きていない。原因は、利用者が使っていた Host が、矢印キーに Fn とテンキーのビットを付ける修正の前のビルドのまま動いていたこと (iPad アプリだけ入れ替えて Host を再起動していなかった)。修正後の Host では、18:39 にバーの ⌃+→/← でも約 1 秒かけてスペースが移ることを Dock の記録で確かめた。
    - それでも Dock スワイプのままにしているのは、切り替えが 0.05〜0.17 秒と速く、ショートカットの設定にも左右されないため。
    - 教訓: Host と iPad アプリの片方だけを入れ替えると、古い側の動作を見て誤った原因を立ててしまう。変更を入れたら、利用者が使っている Host も必ず入れ替える。
  - 上は Mission Control、下はアプリケーションウインドウ。この 2 つは登録値 (`[65535, 126/125, 2359296]`) があり、Control+↑/↓ で動くことを確かめたので、ショートカットのまま送る。
- Dock は、iPad で Dock を出すのと同じく、画面の下端 (24pt 以内) から上へ 30pt 払うと出す。
  - この Mac は Dock を自動的に隠している。カーソルを画面の下端に置けば出るが、指のタップはクリックになり、カーソルを下端に止めておく操作がない。「Dock にアクセスできない」と報告された (2026-10-17)。
  - 出すのには「Dock にフォーカスを移動」のショートカット (登録値 8、`[65535, 99, 262144]` = Control+F3、有効) を送る。Mission Control の Control+↑ と同じシステムのショートカットの仕組みで動く。
    - Control+F3 は、自動的に隠している Dock も出す ([macmost](https://macmost.com/using-the-mac-dock-with-only-your-keyboard.html))。
    - SDK の `NSEvent.h` では、Fn のビット (`1 << 23`) は「いずれかのファンクションキーが押されている」ときに付く。実際のキーボードで Control+F3 を押したときと同じく、合成する F3 にも Fn のビットを付けている。
  - 下端の近くでも、タップと横への払いはいつもどおりクリックとスクロールにする。キーボードを出してビューが縮んでいる間は、ビューの下端が画面の下端ではないので受けない。
- 合成したキーの押下は macOS が繰り返してくれない。そのため、iPad のハードウェアキーボードで ⌫ や矢印を押し続けても 1 回しか効かなかった。Mac 側で、押されたまま離されていないキーを、Mac のキーのリピートの設定 (`NSEvent.keyRepeatDelay`・`keyRepeatInterval`) どおりに繰り返す (`KeyRepeat`)。実際のキーボードと同じく、最後に押したキーだけを繰り返し、繰り返しのイベントには自動リピートの印 (`keyboardEventAutorepeat`) を付ける。
  - この Mac の値は、繰り返し始めるまで 0.25 秒、間隔 0.033 秒だった。Host と同じ手順で ⌫ の繰り返しのイベントを作り (送らずに) 調べた。AppKit からは、押し続けによる入力 (`isARepeat` が true) で、文字は U+007F に見える。
- ハードウェアキーボードの Command+Tab は iPadOS が先に受け取るので、バーのボタンで代わりにする。タップのたびに Command を押したまま Tab を送り、1 秒タップがなければ Command を離して確定する。
- Mac 側は押されている修飾キーを覚えておき (`HeldModifiers`)、クリック・ドラッグ・スクロールのイベントにも載せる。載せないと、ハードウェアキーボードの ⌘ を押しながらタップしても ⌘クリックにならない。
- バーの修飾キー (`ModifierLatch`) は、押すと次の 1 回にだけ効き、続けて 2 回押すと固定される。クリックやドラッグには `PointerModifierHold` で、押す前に修飾キーを押し、離したあとで離す。
- 直接入力では、英数字と空白はキーとして送り、記号は文字として挿入する。記号は Mac 側の配列 (US と JIS) でキーの位置が違うので、キーで送ると別の記号になる。
  - ただし、どちらの配列でも同じ位置にある - , . / (と Shift の ! ?) はキーとして送る。この Mac の ABC 配列でキーコードを変換し、それぞれ - , . / ! ? になることを確かめた。macOS のローマ字入力の規則 (`CoreJapaneseEngine.framework` の `RomajiRule_Default.txt`) では、- は「ー」になる。文字として挿入すると Mac の日本語入力を通らず、かなモードでも「ー」「、」「。」にならない (「伸ばし棒が打てない」と報告された、2026-10-17)。
  - 英字配列のキーボードでは - が記号の面にしかないので、特殊キーの列に「ー」(- のキー) を置いた。
- 特殊キーの列は、横にずらせる `UIScrollView` の中にある。既定 (`delaysContentTouches`) では、スクロールかどうかを見極める間キーの押下が遅れる。そのため、短く押すと押した表示がほとんど出ず、「押した感覚がない」と言われた (2026-10-17)。押下はすぐに届くようにし、押している間は色と大きさを変え、キーボードのクリック音 (`playInputClick`) も鳴らす。iPad には触覚フィードバックの仕組みがないので、振動は使えない。
  - 押下をすぐに届けると、列を横へずらそうとキーの上から触れただけで、押した瞬間のキーが送られてしまう (シミュレータで確かめた)。そのため、キーを送るのは指を離したとき (押し続けたら 0.4 秒後から繰り返し) にし、押した瞬間は表示と音だけにする。横へずらすとタッチは取り消されるので、キーは送られない。
- ソフトウェアキーボードの削除キーを押し続けても、1 回しか消えなかった (2026-10-17 の報告)。直接入力の受け口が `UIKeyInput` だけだと、キーボードが削除を繰り返さないため。`hasText` を常に true にしても変わらない。
  - 画面を出さないシミュレータ (iOS 26.5) で、本体とは別の試験アプリを使い、削除キーを 3 秒押し続けて確かめた (2026-10-17)。`UIKeyInput` だけの受け口では `deleteBackward` は 1 回だった。`UITextInput` を備えて中身の変わらない文書を見せると 25 回で、どれも 1 文字分の `deleteBackward` だった。隠した `UITextView` に番兵の文字を入れる方式も試した。こちらも繰り返すが、途中から単語単位でまとめて消すので、Mac へ送る削除の数に直す手間が要る。
  - そこで、受け口に `UITextInput` を足し、文書は手元に持たずに常に同じものを見せる。`editingInteractionConfiguration` は `.none` にして、iPadOS の 3 本指の編集ジェスチャーが Mac のデスクトップ切り替えとぶつからないようにする。
  - 見せる文書は改行の繰り返しにする。最初に試した「a 」の繰り返しでは、キーボードが末尾を単語と空白とみなした。そのため空白を 2 回打つと、文書の空白をピリオドに置き換えようとした (`replace`)。改行だけの文書では、打ったとおりの `insertText` と `deleteBackward` しか届かないことを、同じシミュレータで確かめた。
- iPad のキーボードは英字配列に固定し、日本語は Mac 側の日本語入力で変換する。iPad 側で変換して文字を送る入力欄は、操作が二重になるのでやめた。iPad のソフトウェアキーボードには Mac の日本語入力を切り替えるキーがないので、特殊キーの列に JIS キーボードの英数・かなを置いている。

### 入力の層を読み直して直したこと

- 2026-10-18 に、別のエージェントに入力の層 (タッチの読み替え、拡大、キーボード、文字の挿入) を読ませ、指摘を単体テストやシミュレータで再現してから直した。
- 長押しでドラッグしている間に、別の指 (手のひらや画面の端のシステムのジェスチャー) だけが取り消されると、判定をやめていた。ドラッグしている指を離しても左ボタンを離さず、Mac で押されたまま残る (以後の移動がすべてドラッグになる)。単体テストで再現し、ドラッグしている指でない指が取り消されたときはドラッグを続けるようにした。
- 指を大きく開いた位置から始めたピンチは、1 回ごとの倍率が小さく (指の間隔が約 480pt を超えると 1.05 未満)、等倍に戻す判定に毎回かかって拡大が始まらなかった。2% ずつ 10 回広げても等倍のままだったのを単体テストで再現した。等倍に戻すのは縮めているときだけにした。
- 特殊キーの列で ⇧ を 1 回だけ効かせて ← を押し続けると、最初の 1 回でラッチが外れ、繰り返しは修飾キーなしの ← になって選択が解けていた。シミュレータで、直す前は 16 回中 1 回だけ ⇧ 付き、直したあとは 16 回とも ⇧ 付きだった。押し始めに効いていた修飾キーを覚えて繰り返しにも使う。
- iPadOS に取られて離した知らせが届かなかったキーがあると、Host は離すまで繰り返し続ける。繰り返しは 30 秒で打ち切る。iPad は裏に回るときに `releaseHeldInput` を送り、Host は押したままのキーとボタンを離す (Typeless は止めない)。
  - 最初は映像の接続が閉じたら離していた。映像の接続は、取り込みの失敗や iPad の張り直しのように、iPad が前に出たまま閉じることもあり、ドラッグや ⌘ を押している途中で Mac 側だけが離れてしまう (今日の変更をまとめて読み直させたときの指摘)。裏に回ったことを iPad から知らせるようにした。シミュレータでホームに戻すと、代わりの Host に `releaseHeldInput` が届いた。試験用の組み立てで、打ち切り (組み立てでは 1 秒に縮めた) のあと押下が出ないこと、離す処理で左ボタン・←・⇧ が離されることを確かめた。
- 拡大している間にキーボードの出し入れや回転で映す範囲が変わっても、見えている範囲を頼み直していなかった (縁が黒くなりうる)。映す範囲が変わったら頼み直す。
- 文字の挿入のアクセシビリティの問い合わせに時間の上限がなく、応答しないアプリで入力の列 (マウス・キー) ごと何秒も止まりえた。0.5 秒にした。
- つなぎ直したときに、iPad がクリックに付ける修飾キーを押したつもりのまま残していた。切れたら忘れる。
- 今日の変更をまとめて別のエージェントに読み直させ、次の取りこぼしを直した。
  - 「操作の一覧」を出している間に押したキーは送らないようにしたが、⌘ との組み合わせは優先して受け取ると宣言したショートカットの動作に回り、Mac に届いていた (シミュレータで ⌘W が届いた)。宣言した動作の側でも、上に何かを出している間は送らない。
  - 少しだけ広げた途中で、指を動かすだけの更新 (倍率 1) が来ると等倍に戻っていた。広げているか動かすだけのときは戻さない。
  - Host を止めたあとでも、待ち受けの作り直しの予約が残っていると作り直していた (「再起動」で新旧が Bonjour の名前を取り合う)。止めたあとは作り直さない。作り直しで待ち受けを作れなかったときも、もう一度作り直す。
- 直していない指摘: キーと文字の挿入 (記号や日本語) が混じった一度の入力で、アクセシビリティの挿入がキーより先に反映されうること (普通に打つ速さでは起きない。キーとアクセシビリティは経路が別で、順序を揃えるには挿入の作りを変える必要がある)。Electron 系のアプリで挿入の反映が遅れたときに二重に入りうること (今のところ二重入力は報告されていない)。ペンでドラッグ中に手のひらがタップになったとき。Caps Lock の切り替え。

## 画面の構成

- 最初は画面下に、キー・修飾キー・入力欄・送信・Typeless などのボタンを 1 列に並べていた。使う頻度も場面も違うものが同じ重さで並び、Mac の画面も狭くなるので、ユーザーから強く否定された (2026-10-17)。
- 今は使う場面ごとに置き場所を分けている。
  - Mac の画面は全面に出す。
  - いつでも使うもの (Enter・Typeless・キーボード・アプリ切替・切断) は、隅に浮かぶ小さな操作パネルにまとめる。
    - Enter は、Typeless で話したあとにキーボードを出さずに送れるよう、パネルの先頭に置いた (ユーザーの要望、2026-10-17)。
    - アプリ切替のアイコンは、最初の `square.on.square` がコピーのボタンに見えると言われたので、`rectangle.2.swap` にした。
  - パネルのボタンでキーボードを閉じると、キーボードは消えるが、Mac の画面の表示領域が縮んだまま戻らないと報告された (2026-10-17)。OS のキーボードを閉じるキーでは戻る。
    - 入力先を外すのが SwiftUI の更新 (`updateUIView`) の途中だからと考え、入力先の付け外しを `DispatchQueue.main.async` で更新のあとへ回した。
    - ところが、画面を出さないシミュレータ (iPad Air 11 インチ、iOS 26.5、実機と同じ 820x1180pt) で本物の画面を組んで確かめると、元のコードでも SwiftUI の余白は戻った (縦 1180 → 829 → 1180)。
    - 映像の範囲を UIKit の `keyboardLayoutGuide` から決めるように変えて調べた。すると、パネルのボタンで閉じたあと、ガイドは特殊キーの列の高さ 52pt を残したまま (1128) 戻らなかった。同じときのキーボードの通知 (`keyboardWillHide` など) は、正しく画面の外 (上端 1180) を知らせていた。特殊キーの列 (`inputAccessoryView`) を付けた入力欄をプログラムから外すと、キーボードの位置の追跡にこの食い違いが残る。実機の SwiftUI の余白が戻らなかったのも、これと同じとみている。
    - そこで、Mac の画面のビューはキーボードの余白を無視して全面に置き、映像の範囲はキーボードの通知が知らせる位置から自分で決める。シミュレータで、横・縦とも開く・閉じるを 3 回ずつ繰り返し、閉じるたびに全面に戻ることを確かめた (横 820 → 346 → 820、縦 1180 → 791 → 1180)。
  - この変更で、`updateUIView` の中で `isActive` を読まず、後で動く処理の中でだけ読むようにしてしまった。SwiftUI は読まれた値にしか依存を記録しないので、ボタンで切り替えても `updateUIView` が呼ばれず、**キーボードがまったく出なくなった**。
    - 「キーボードが出なくなった」と報告された (2026-10-17)。本物の画面を組んだシミュレータで、開く操作 3 回がすべて失敗することを再現した。
    - `updateUIView` の中で値を読んで後の処理へ渡すように直した。そのあと、横向き・縦向きとも開く・閉じるを 3 回ずつ繰り返し、高さが戻ることを確かめた (横 820 → 346 → 820、縦 1180 → 791 → 1180)。
    - 最初に作った簡略な再現では起きなかった。親の画面がボタンの文字のために同じ値を読んでいて、依存が記録されていたため。再現は本物の画面で行う。
  - シミュレータでは、OS の「キーボードを非表示」を一度押すと、そのあとはどの入力欄を有効にしてもキーボード本体が画面の外に置かれたままになった。普通の `UITextField` をタップしても、`reloadInputViews` を呼んでも戻らない。実機の iPad では、キーボードを隠したあとに入力欄をタップすれば出るので、シミュレータ側の現象とみている。
  - キーを打つときだけ使うもの (esc・Tab・修飾キー・矢印・英数/かな) は、キーボードの上の列 (`inputAccessoryView`) に出す。
  - iPhone では、縦向きは操作パネルが下の黒い帯に収まる。横向きは Mac の画面 (16:9) の左右に約 80pt の帯ができるが、横長のパネル (約 250pt) は入らず、Mac の画面の隅に重なる。パネルを縦に並べて帯に入れる案は見送った (2026-10-18)。帯のうち約 62pt は Dynamic Island 側の安全領域で、縦に並べたパネル (約 248pt) はその側では Dynamic Island に隠れる。パネルはドラッグで隅を替えられる。iPhone 17 のシミュレータと代わりの Host で、横向き・縦向きとメニューを撮って確かめた。
- iPad から送るキーの並び (`RemoteKeys`・`AppSwitcher`) と、Mac で合成するキーの種類とフラグ (`MacKeyEvent`) は Kit にまとめ、単体テストで固めている。実際の端末を操作するテストは、利用者の作業を乗っ取るので走らせない。
- Mission Control の開閉は、Dock 自身の記録 (`com.apple.dock:missioncontrol` の mode の変化) で確かめられる。

## Swift 6 とオーディオのスレッド

- アプリのターゲットは既定でメインアクターに属する (`SWIFT_DEFAULT_ACTOR_ISOLATION: MainActor`)。メインアクターのメソッドの中で書いた処理 (クロージャ) もメインアクターに属するとみなされる。
- それを AVFAudio の `installTap` に渡すと、AVFAudio が自分のスレッドから呼んだ時点で、Swift の実行時の検査 (`dispatch_assert_queue`) に止められてアプリが落ちる。「マイクボタンを押したらクラッシュする」と報告された (2026-10-17)。
- オーディオのスレッドから呼ばれる処理は、`nonisolated` な場所 (静的メソッドや `nonisolated` なクラス) で作る。シミュレータで、直す前のコードでは Typeless のボタンを押すとアプリが止まり、直したあとは止まらないことを確かめた。マイクの許可の返事のように別のスレッドから返る完了処理も、メインアクターの上で `await` して受け取る。

## 権限

- Mac 側に必要なのは、アプリ単位の許可 3 つ (ローカルネットワーク・画面収録・アクセシビリティ) だけ。
- Host の実行ファイルをターミナルから直接起動すると、画面収録とアクセシビリティの許可はターミナル (Ghostty) から引き継がれる。ただしローカルネットワークの許可は引き継がれず、mDNSResponder がアプリのバンドル ID ごとに判断する。許可が保留の間は Bonjour の広告が止まる。

## 検証の方針

- 検証は単体テスト (`just test`) とビルドで行う。判断の中身 (タッチの読み替え、キーの並び、修飾キー、ショートカットの解釈、通信、映像の符号化と復号) は Kit の純粋なロジックにして、そこをテストする。
- 利用者の Mac や iPad のマウス・キー・窓・アプリを動かすテスト (端末を操作する E2E、実機の UI テスト) と、利用者の操作を見張って確かめるやり方はとらない。利用者の作業を乗っ取るので、2026-10-17 に強く否定された。以前置いていた `Tools/E2E`・`Tools/DeviceProbe`・`Apps/PadUITests` は取り除いた。
  - 「次に使われたら記録を読む」ためにログを繰り返し読む見張りを常駐させるのも、利用者の操作の監視にあたる。2026-10-18 に、見張りで Mac の音が使われたのを知り、そのとき鳴っていたプロセスを調べようとして、強く否定された。実機でしか分からないことは、シミュレータや iPad がつながっていない時間のプローブで再現できる形にして確かめる。
- Host の入力の処理は、`InputInjector.swift` などを試験用に組み、Mac へ送る `post(tap:)` だけを記録に差し替えて確かめる。そこへ iPad から届く操作を流し込めば、Mac を動かさずに、作られるイベントの並び・時刻・フラグが分かる。2026-10-17 に、キーのリピート、Dock の ⌃F3、Typeless のショートカットを押すかどうかをこの方法で確かめた。
- iPad の画面の不具合は、画面を出さないシミュレータで、本物の画面のファイルをそのまま組んだ試験アプリで再現する。接続先はどこにもつながらない宛先に差し替えて、利用者の Host には接続しない。部品を簡略にした再現では、起きる条件が変わってしまうことがある (キーボードが出なくなった件)。
- 補助アプリや Host を入れ替える前に、聞き取りの最中でないことを記録で確かめる。2026-10-17 22:59 に、利用者が話し始めた 2 秒後に補助アプリを起動し直してしまい、既定の入力が途中で戻ってその回の聞き取りが無駄になった。
  - 2026-10-18 から `just deploy-host` で入れ替える。Typeless のプロセスがマイクを使っている間 (`Scripts/TypelessIdle.swift`) と、Host にループバック以外の接続 (iPad) がある間は入れ替えず、入れ替えたら新しい Host が動いたと確かめるまで開き直す (終わった直後の `open` が -600 で開けないことがあった)。聞き取り中を装った確認と、iPad の awdl の接続を含む `lsof` の行で、入れ替えないことを確かめた。`just run-host` は、Host が動いていると古い方を前に出すだけで、新しいビルドを起動しない。
  - iPad アプリは `just deploy-pad <ID>` で入れ替える。入れるとアプリが落ちるので、iPad が Host につながっている間は入れない。つながっているかの判断 (`Scripts/pad-connected.sh`) は、偽の `lsof`・`pgrep` で、awdl の接続があれば 0、ループバックだけなら 1 を返すことを確かめた。
- Mac の中の音の経路は、補助アプリが起動のたびに自分で点検して記録に出す (聞こえない 20kHz の小さな音を鳴らし、タップと「PadBridge iPad マイク」に届くかを測る)。聞き取りのたびにも、iPad から届いた音の長さ、鳴らした音の最大、デバイスの入力の最大を記録に出すので、どこで音が消えたかは利用者に試してもらわずに記録から分かる。
- 変更を入れたら、利用者が使っている Host と iPad アプリの両方を入れ替える。片方だけ入れ替えると、古い側の動作を見て誤った原因を立ててしまう (3 本指スワイプで一度起きた)。
