# PadBridge の設計判断

既存ソフトの調査は [existing-solutions.md](existing-solutions.md) にある。ここには、自作する中で決めたことと、その理由を残す。

## Mac に仮想マイクを入れない

- 当初は、iPad のマイク音声を Mac に送り、BlackHole などの仮想オーディオデバイス経由で Mac 版 Typeless に入れる案だった。
- しかし仮想オーディオデバイスはシステム全体に効くドライバで、端末全体の状態を汚す。ユーザーの方針で不採用にした。自作の AudioServerPlugIn も同じ理由で不採用。
- 代わりに、**音声認識は iPad で行い (SpeechAnalyzer + DictationTranscriber、端末内で処理)、確定した文字だけを Mac に送る**。Mac 版の Typeless には入らないが、「iPad のマイクで Mac に音声入力する」という目的は満たせる。
- iOS 版の Typeless は iPhone 専用 (App Store の表示で確認、2026-10)。iPad のキーボードで使える音声入力なら、画面下の入力欄からも送れる。

## Mac 側で文字を入れる方法

- 第 1 候補は、アクセシビリティ API で入力欄の選択範囲 (`kAXSelectedTextAttribute`) に書き込む方法。クリップボードを使わないので、ユーザーのクリップボードやクリップボード履歴を汚さない。
- 書き込みが成功を返しても、実際には反映しないアプリがある (Electron 製など)。そのため、値が変わったかを読み直して確かめ、変わっていなければ `CGEvent` の Unicode 文字列によるキー入力に切り替える。
- Mac が日本語入力モードのときにキー入力で送った文字がどう扱われるかは、2026-10-17 の E2E テストで確かめた。ことえり (ローマ字入力) が有効な状態でも、変換待ちの文字にならず、そのまま確定して入った。E2E テストは、入力ソースが日本語でなければテスト中だけ切り替え、終わったら必ず元に戻す。

## 通信

- 同じ LAN の中だけで使う前提で、Bonjour (`_padbridge._tcp`) で Mac を見つける。
- 暗号化と相互認証は **TLS-PSK** で行う。Mac が発行する 10 文字のペアリングコードから鍵を作る。証明書を配らなくて済むのが利点。
  - 調べた時点で、Network.framework で PSK による相互認証として手順が示されているのは TLS 1.2 の PSK 暗号スイート (Apple のサンプル「TicTacToe」と同じ方式)。QUIC は TLS 1.3 が前提で、PSK だけで成り立たせる手順が確立していなかったため、TCP を選んだ。
  - コードは 31 種の文字 × 10 桁 (約 49 ビット)。ハンドシェイクを盗聴されて総当たりされても、家庭内 LAN の脅威に対しては十分と判断した。
- 接続は **操作用と映像用の 2 本** に分けた。1 本にまとめると、映像の送信が詰まったときにクリックやキー入力まで待たされるため。
- Mac は、送信待ちが 4 件以上たまったら、取り込んだフレームを符号化する前に捨てる。符号化したあとで捨てると、参照フレームが欠けて映像が壊れる。

## 映像

- ScreenCaptureKit でメインディスプレイを取り込み、VideoToolbox の H.264 で符号化する。低遅延レート制御を使い、プロファイルは ConstrainedHigh、フレームの並べ替えはしない。
- iPad 側は `AVSampleBufferDisplayLayer` に圧縮したまま渡して復号させる。バックグラウンドから戻ると表示レイヤが壊れるので、そのときは中身を捨ててキーフレームを要求する。
- ScreenCaptureKit は画面が変わらないとフレームを出さない。そのため、5 秒ごとのキーフレームと、要求に応じたキーフレームで回復点を作る。
- 2026-10-17 の E2E テストでは、1230x800 の映像を約 50fps で受け取り、復号できた。

## 入力

- 座標は、Mac のディスプレイに対する 0〜1 の割合で送る。iPad 側は、縦横比を保って表示している映像の矩形を基準に換算する。
- 合成したクリックには macOS がクリック回数を付けてくれないので、`ClickCounter` で自前で数える。ダブルクリックの判定距離は、指のずれを見込んで 16pt にした。
- 修飾キーを単体で送るときは、イベントの種類を `flagsChanged` にしないと、アプリが Command などを認識しない。

## 権限と E2E テスト

- Mac 側に必要なのは、アプリ単位の許可 3 つ (ローカルネットワーク・画面収録・アクセシビリティ) だけ。
- Host の実行ファイルをターミナルから直接起動すると、画面収録とアクセシビリティの許可はターミナル (Ghostty) から引き継がれる。`just e2e` はこれを利用している。
- ただし、**ローカルネットワークの許可は引き継がれない**。mDNSResponder がアプリのバンドル ID ごとに判断し、許可が保留の間は Bonjour の広告を止める。
- E2E テストのクライアントもターミナルの権限で動く。そのため LAN 宛ての通信は、ターミナルのローカルネットワーク許可に縛られる。この状態では TCP の接続は成立するが、中身が届かず、TLS のハンドシェイクで止まる。そこで E2E テストは、Bonjour での発見までを確かめ、接続はループバックで行う。LAN 経由の接続は、実機の iPad で確かめる。
- E2E テストの Host には別の Bonjour 名を付ける (DEBUG ビルドだけの `-PadBridgeTestServiceName`)。普段使いの Host と同時に動かしても名前がぶつからない。
