# PadBridge の設計判断

既存ソフトの調査は [existing-solutions.md](existing-solutions.md) にある。ここには、自作する中で決めたことと、その理由を残す。

## 音声入力は Mac の Typeless を iPad から起動する

- ユーザーの要件は「Typeless で音声入力すること」。Apple の音声認識などで代替してはいけない。
  - 2026-10-17 に一度、合意なく iPad 側の SpeechAnalyzer (Apple の音声認識) に置き換えて強く叱責された。
- iPad のマイク音声を Mac の Typeless に入力するには、仮想オーディオデバイス (BlackHole や自作の AudioServerPlugIn) が必要になる。これは Mac 全体の環境を汚すので不可。
- iOS 版の Typeless は App Store で「iPhone 専用」と表示されている (2026-10 時点)。
- ユーザーが選んだ方式は次のとおり (2026-10-17)。
  - iPad の Typeless ボタンで、Mac の Typeless の音声入力ショートカットを押す。
  - 録音は Mac 側のマイクで行う。
  - Mac に何も追加せずに、Typeless の全機能 (文脈の読み取りなど) を使える。
- iPad 版の Typeless に切り替える案は、Mac の Typeless を使うという取り決めに反するので出さない (2026-10-17 に調べかけて強く否定された)。

### 蓋を閉じた Mac では、iPad のマイクを一時的な入力デバイスにする

- Mac の蓋を閉じたまま iPad から操作すると、Typeless が「マイクがない」と表示して録音が始まらない (2026-10-17 の報告)。Apple silicon と T2 搭載のノート Mac は、蓋を閉じると内蔵マイクをハードウェアで切り離し、root 権限のソフトウェアでも復帰できない ([Apple Platform Security](https://support.apple.com/guide/security/hardware-microphone-disconnect-secbbd20b00b/web))。このとき、この Mac の入力デバイスは内蔵マイクしかなかった。
- ユーザーが選んだのは、iPad のマイク音声を「Host が動いている間だけの一時的なマイク」として Mac に見せる方式 (2026-10-17)。ドライバ (HAL プラグイン) は入れない。
  - iPad は Typeless のボタンを押している間だけマイク音声をキャプチャし、48kHz・モノラル・16 ビットのまま操作用の接続で送る (`WireMessage.audio`)。
  - Mac では、届いた音声を自プロセスで再生し、自プロセスの出力だけを取り出すミュートのプロセスタップ (`CATapDescription`、`muteBehavior = .muted`) を作る。タップだけを入力に持つ機器セット「PadBridge iPad マイク」を作ると、他のアプリから入力デバイスとして見える。出力のサブデバイスを入れると、出力デバイスとしても一覧に表示されてしまう。
  - **このデバイスは Mac の既定の入力になれない**。タップだけの機器セットは `kAudioDevicePropertyDeviceCanBeDefaultDevice` が 0 で、既定の入力に設定しても、ほかのアプリからは内蔵マイクのままに見える (2026-10-17 に確認した)。既定の入力は切り替えない。
  - ユーザーに Typeless の設定を変更させる作りは「ゴミ仕様」「こっちに指示を出すな」と否定された (2026-10-17)。そこで Host が、iPad が接続した 5 秒後に、Typeless の `selectedMicrophoneDevice` をこのデバイスに設定する (`TypelessMicrophoneSetup`)。
    - Typeless の内部 (app.asar) を読んで確認したこと: 設定は electron-store で、外部からの書き換えを読み直す `watch` は使っていない。動作中に書き換えても上書きされるので、Typeless を終了させてから書き換え、再起動する。選択したマイクは現在のマイク一覧から deviceId で探し、見つからなければ null (自動検出) に戻るので、iPad が接続していないときは内蔵マイクで音声入力できる。
    - 蓋を閉じると Typeless が「マイクがない」と表示する理由も内部から分かった: マイクが「自動検出」のときだけ蓋の開閉を 3 秒ごとに確認しており、閉じていると既定の入力 ('default') を使わず、録音するデバイスがなくなる。特定のマイクを選んでいれば、蓋の開閉に関係なくそれを使う。
    - 選択したマイクが一覧にないときは自動検出として扱うだけで、`selectedMicrophoneDevice` を null に書き戻さない。一覧は `devicechange` のたびに取得し直す。そのため、iPad が接続していないときに Typeless が起動しても、ヘルパーアプリがデバイスを作り直しても、選択は維持される。
    - 設定する値は、Typeless 自身が設定に書いたマイク一覧の項目をそのまま使う (deviceId は Chromium が生成する値なので、自分では作れない)。書き換えるのはこの 1 項目だけで、ほかの項目が変わらないことをコピーで確認した。
    - 音声入力の途中では終了させない。設定するのは、選択中のマイクが自動検出 (null か deviceId が `default`) のときだけ (`TypelessMicrophoneChoice`)。ユーザーが特定のマイクを選んでいれば、その選択を尊重する。初めは一度だけ設定して UserDefaults に記録していたが、それだと Typeless の再インストールや設定の消失のあとは二度と設定されず、iPad に設定手順を表示することになるのでやめた。
    - 最初は音声入力の間だけ既定の入力を切り替えていたが、Typeless は内蔵マイクで録音していた。coreaudiod のログでは、既定の入力をこのデバイスにした直後に、Typeless の入力は BuiltInMicrophoneDevice で始まっていた。
    - 内蔵マイクをサブデバイスに加えた機器セットなら既定になれるが、チャンネル 1 が内蔵マイク、2〜3 がタップの順に並ぶ。Chromium が先頭のチャンネルを読むと、蓋を閉じた内蔵マイクの無音を拾うので採用しなかった。
    - Host は、iPad から音声入力を開始したあと、Typeless が録音しているデバイスを `kAudioProcessPropertyDevices` (入力側) で読む。このデバイスでなければ、Typeless の設定をやり直し (自動検出のときだけ)、ユーザーが別のマイクを選んでいれば iPad に通知する。
      - Typeless がこのデバイス (タップだけの機器セット) で録音しているときは、この一覧が空になる (内蔵マイクのときは BuiltInMicrophoneDevice が入る)。空を「別のマイク」と見なして、正しく音声入力できているのに iPad に警告を出していた (2026-10-17 にユーザーが気づいた)。空のときは判別不能として通知しない。
    - Typeless がこのデバイスを選んだままなので、iPad が接続したまま Mac で直接 Typeless を使うと、無音で録音されてしまう (ヘルパーアプリは iPad から話している間しか音声を流さないため)。そこでヘルパーアプリは、iPad から話していない間にこのデバイスが読み取られたら (`kAudioDevicePropertyDeviceIsRunningSomewhere`)、Mac の既定の入力の音声を別の `AVAudioEngine` でキャプチャして流す。この通知は機器セットでもすぐ届く (プロセスの入力状態と違い、待たずに使える) ことを確認した。
    - 流す入力を既定の入力から変えない (2026-10-18 に検討して見送った)。蓋を閉じたこの Mac では既定の入力が内蔵マイク (ハードウェアで切り離されて無音) のままなので、外付けの USB マイクを選ぶ案を検討した。
      - Typeless の「自動検出」も、外付けのマイクへ自動では切り替えない (app.asar を読んだ)。自動で切り替えるのは、蓋が開いていて内蔵マイクが使えるときに推奨のマイクへ移す場合だけ (`preferredBuiltInMicId`)。録音が無音だったときは、ほかのマイクを開いて音量を測り、「より良いマイク」を通知して選択させるだけ (1 日 1 回まで)。ヘルパーアプリが外付けのマイクを選ぶと、Typeless 自身も行わない推測をすることになる。
      - 音声をキャプチャせずに読める値では、マイクとして使える入力を判別できなかった。この Mac の入力は、DL-Dock (DisplayLink のドックの差し込み口、USB・2 チャンネル・接続検出なし、出力は別のデバイス)、fifine Microphone (USB・1 チャンネル・接続検出なし、ヘッドホン端子の出力あり)、内蔵マイク。種類・接続状態・出力の有無・チャンネル数のどれも、何も接続していないドックの差し込み口と本物のマイクの違いを表さない。
      - iPad からの音声入力のあと Typeless がまだ読み取っている間に流し始めると、その続きに Mac のマイクの音声が混ざる。読み取りが一度止まるまでは流さない (`PassThroughGate`)。
      - 録音の許可がないとタップのミュートが効かず、Mac のマイクの音声がスピーカーから流れるので、そのときは流さない。
      - 常に Mac のマイクをキャプチャしておけば発話の冒頭が欠けないが、マイク使用中の表示が出続けるので、読み取られている間だけキャプチャする。
      - キャプチャはタップではなく `AVAudioSinkNode` で行う。この Mac で測ると、タップは 4800 フレーム (100ms) ごとに 1 秒あたり 10 回、シンクは 512 フレーム (約 10ms) ごとに 1 秒あたり 94 回渡し、エンジンの開始はどちらも 0.04 秒だった。Typeless は自分のショートカットで止めた瞬間に読み取りをやめるので、バッファにためている分だけ発話の末尾が切れる。シンクにして、バッファ量を 30ms にした。Mac の内蔵マイクは 48kHz・モノラルで、送信形式と同じなので変換しない。
      - 蓋を閉じていると、内蔵マイクは形式 (48kHz・1 チャンネル) は見えるが、値はすべて 0 になる。
      - 一時的な読み取り側でこのデバイスを 1.5 秒読み、読み始めた瞬間に流し始め、読み終えたらやめること、48kHz で途切れずに届くことを確認した (2026-10-17)。
  - iPad が再接続するたびにヘルパーアプリを停止して再起動すると、デバイスを作り直してチェックし終えるまで (約 1.5 秒) iPad のマイクを使えず、Typeless もマイク一覧を取得し直す。接続が切れても 60 秒はヘルパーアプリを残し、その間に再接続したらそのまま使う。
  - 2026-10-17 の時点で、iPad との接続は Wi-Fi のネットワーク (en0) ではなく Wi-Fi の直接通信 (awdl0) を通っていた (`includePeerToPeer`)。awdl はチャンネルを切り替えるので遅延のジッターが大きく、切断されることもある。ただ、ルーターが端末間の通信を遮断する設定だと awdl でしか接続できないので、外してはいない。再接続の原因を追えるよう、Host は接続ごとに経路をログに記録する。
    - 同じ日の 23:58 の再接続では en0 を通った。この環境ではどちらの経路でも接続でき、接続ごとに Network.framework が選ぶ (Mac の en0 から `_companion-link._tcp` で iPad が見えなかったのは、iPad がそれを公開していなかっただけだった)。
  - `AVAudioNode` のタップは 100〜400ms ごとにしか音声を渡さない (ヘッダーの `installTapOnBus` の説明。1024 フレームを要求しても 100ms になる) ので、iPad の音声は 100ms のチャンクで届く。初めは 80ms 溜まったら再生していたが、チャンクより短いと少し遅れて届くたびに途切れる。今は 150ms 溜まってから再生し、3 秒を超えたら古い音声を破棄する (`PCMJitterBuffer`)。途切れた回数は音声入力ごとにログに出す。
  - 初めは音声入力を開始したらすぐ再生していたので、Typeless がデバイスを読み始めるまで (ショートカットを押してから数百 ms) の声が誰にも届かず、発話の冒頭が切れていた。今は、デバイスが読み取られている間 (`kAudioDevicePropertyDeviceIsRunningSomewhere`。別のプロセスが読み始めても通知はすぐ届くことを確認した) だけ再生し、それまではバッファにためておく。そのためヘルパーアプリは、音声入力の間は自分ではデバイスを読み取らない。
  - 完了のショートカットは初め 0.25 秒待って押していたが、バッファにためている音声が多いと発話の末尾が切れる。今は、iPad で停止したら Host がヘルパーアプリに通知し (`microphoneRelayFinish`)、ヘルパーアプリは停止直前のチャンクが届くまで 0.2 秒待ってから、そこまで書き込んだ音声を再生し終えたら応答する (`microphoneRelayFinished`)。Host はそれを受けてから押す。iPad は Mac で Typeless が止まるまでマイク音声を送り続ける。
- 許可について、次のことが分かった (2026-10-17)。
  - プロセスタップには「システムオーディオの録音」(`kTCCServiceAudioCapture`) の許可が必要になる。ターミナルから実行した Host では Ghostty の許可として要求され、Ghostty は理由の説明 (`NSAudioCaptureUsageDescription`) を持たないので、macOS は確認ダイアログを出さずに拒否する。このとき、タップのミュートも効かない (テストした音声がスピーカーから再生された可能性がある)。
  - Host のバンドルの中に入れたヘルパーアプリ「PadBridge Mic」を LaunchServices で起動すると、許可は「PadBridge Host」のものとして要求される。Host をターミナルから実行したままでよく、Host 自身をアプリとして起動し直して画面収録などの許可を取り直す必要がない (蓋が閉じているので、取り直す間にディスプレイが見えないと何もできなくなる)。
  - ウィンドウを持たないヘルパーアプリでは、Core Audio は許可の有無を確認するだけで要求しない (`preflight=yes`)。公開 API がないので、AudioCap などと同じく TCC の `TCCAccessPreflight` と `TCCAccessRequest` を直接呼んで要求する。
  - **タップを含む入力デバイスを読み取るには、読み取る側のアプリにも「マイク」と「システムオーディオの録音」の両方の許可が必要になる。** 2026-10-17 に次のとおり確認した。
    - マイクだけ許可された Ghostty から読むと、`AudioDeviceStart` が `nope` で失敗した (coreaudiod が Ghostty の `kTCCServiceAudioCapture` を確認し、未許可だった)。
    - システムオーディオの録音だけ許可されたヘルパーアプリから読むと、無音だった (`kTCCServiceMicrophone` が未許可)。
    - Typeless の Info.plist にはマイクの説明しかないので、Typeless は自分ではこの許可を要求しない。システム設定の「画面とシステムオーディオの録音」→「システムオーディオ録音のみ」に、ユーザーが Typeless を追加する必要がある。
    - 許可がないとき、Typeless は「PadBridge iPad マイク」を開くことはできるが、中身は無音になり、音声入力は続く (2026-10-17 の「音声入力が動かない」の原因)。tccd は Typeless の確認に authValue=0、authReason=8 (理由の説明がない) を返し、「Refusing authorization request for service kTCCServiceAudioCapture and subject Sub:{now.typeless.desktop}」をログに記録した。拒否した記録は許可の一覧に残らないので、Typeless は一覧に自動では載らず、「＋」で追加する必要がある。
    - アプリから他のアプリの許可を事前に読む方法はない。`TCCAccessPreflightWithAuditToken` は、権限のない呼び出し元には実際の許可と異なる値 (許可されているマイクも「拒否」) を返した。
    - そこで Host は、iPad のマイクで音声入力が始まった 1 秒後に、直近 5 秒の tccd のログから上の拒否の行を探す。あれば iPad に手順を通知し、Mac で「画面とシステムオーディオの録音」の設定を開く。なければ通知を消す。
    - 初めは「iPad から開始したのに 1 秒たっても音声入力が始まらない」ことも許可不足の判定材料にしていたが、誤りだった。Typeless は音声入力を停止してから文字に変換して貼り付け終えるまで (数秒) ショートカットを受け付けず、続けて話し始めるとこれに該当する。2026-10-17 に、停止して 3.7 秒後に開始したときに設定画面を開いてしまい、ミラーリング画面に表示された。今は許可不足の判定は tccd の拒否の行だけにし、開始しないときは 1 秒ごとに 4 回までショートカットを押し直す。その間は iPad にマイクを止めさせず、ヘルパーアプリが音声を 6 秒までバッファにためておくので、開始が遅れても発話の冒頭は欠けない。
      - Typeless の内部 (xstate の状態機械) で確認した: 停止後の `finishing` (文字起こしの仕上げ) では、ショートカット (`PRIMARY_KEY.DOWN`) は「まだ仕上げ中」の通知 (`showFinishingAlert`) を出すだけで、キューにためて後で開始することはない。仕上げが終わる (`WEBSOCKET.REFINE_COMPLETED`) と `idle` に戻り、押せば開始する。そのため押し直しても、余計に開始したり停止したりしない。
        - この通知は「前の音声入力を処理中」の警告を 5 秒表示するもので、前の音声入力を取り消す (`ESC`、ログは `dismissed`) のは、通知内の「キャンセル」を人が押したときだけ。押し直しても、前に話した分は消えない。
        - 仕上げの長さの上限は、文字起こしで 20 秒、音声コマンドで 30 秒 (`VOICE_TRANSCRIPT_REFINE_TIMEOUT_MS`・`VOICE_COMMAND_REFINE_TIMEOUT_MS`、長い録音は録音の長さ) で、過ぎると `FATAL_TRANSCRIPTION_TIMEOUT` になる。押し直すのは約 5 秒までで、ヘルパーアプリがバッファにためておける音声 (6 秒) に合わせている。それより仕上げが長引いたときは、iPad の表示を戻して押し直してもらう。
    - 同じく、音声入力の開始 1 秒後から 5 秒間、音声があるかを監視しており、なければ自分で停止する (`RECOVERABLE_NO_SPEECH_DETECTED`)。音声とみなすのは、8 ビットの波形で 128 から 1 以上離れた値 (振幅で約 0.0078、-42dBFS) が 1 つでもあるとき。iPad の音声は話すと最大 0.12〜0.25 で十分に上回り、話していないときの雑音 (約 0.0006) は下回る。iPad の音声を Typeless が読み始めるまでバッファにためておくのは、この点でも必要になる (読み始めたときに発話の冒頭から流れる)。
    - ショートカットを押し続けると `long_pressing` (「押し続けず押すだけ」の通知) になり録音を停止するので、Host は押してすぐ離す。
  - Typeless (Chromium) にこのデバイスをマイクとして認識させるには、次の 2 つが必要だった (2026-10-17、「使えない」と報告されて調べた)。音声入力の間に Typeless の「システムオーディオの録音」の確認が一度も発生せず、Typeless の設定のマイク一覧にもこのデバイスがなかったことから、内蔵マイクを開いていたと分かった。
    - タップを公開にする (`isPrivate = false`)。既定の非公開のタップは作成したプロセスにしか見えず、ほかのアプリからは機器セットの入力が 0 本に見える。
    - ヘルパーアプリの出力を止めない。出力を止めたまま作ったタップや、出力が止まっている間は、機器セットが入力を持たない。Typeless は音声入力の間だけ入力が現れても、マイク一覧を作り直さない。iPad の音声を再生するのは音声入力の間だけにし、それ以外は無音を流す。
    - 修正後、Typeless の設定のマイク一覧に「PadBridge iPad マイク」が追加された。
  - ヘルパーアプリは、終了する前にデバイスの削除が完了するのを待つ。待たずに終了すると、デバイスが Mac に残る。
  - ヘルパーアプリが無音を流し続けている間は、coreaudiod が Mac のアイドルスリープを止める (`pmset -g assertions` に `BuiltInSpeakerDevice.context.preventuseridlesleep` が表示される)。iPad が接続している間だけなので、蓋を閉じた Mac を iPad から使う用途ではそのままにしている。
  - 最初は、ヘルパーアプリが自分で再生した小さな音 (20kHz) を「PadBridge iPad マイク」そのものから読み取って経路を確認していた。上のとおりヘルパーアプリにはマイクの許可がなく必ず無音になるので、この方法はやめた。今は、システムオーディオの録音の許可だけで読み取れるチェック専用の非公開の機器セットで、タップが音声を運んでいるかを測る (許可が付いたときに 1 回。マイクの許可もあれば「PadBridge iPad マイク」そのものも測る)。
- 作成した機器セットとタップは、作成したプロセスが終了しても HAL に残る。ヘルパーアプリは、起動したときに前回の残りを削除し、Host との接続が切れたら自分のものを削除して終了する。名前で探して削除すると、入れ替わりに起動したヘルパーアプリのデバイスまで削除してしまうので、終了するときは自分が作成したものだけを削除する。
- 音声入力の経路を別のエージェントに読ませて修正したこと (2026-10-18)。
  - ヘルパーアプリが起動直後のチェック (約 1.5 秒) などで遅れ、音声入力の準備の応答がタイムアウト (1.5 秒) を過ぎると、その回は「iPad の音声を使っていない」とみなし、停止するときに発話の末尾を流し終えるのを待たずに Typeless を止めていた (バッファにためた発話の末尾が切れる)。タイムアウトを過ぎて届いた「準備完了」も、その音声入力の途中なら反映する。
  - Typeless のマイク設定のために Typeless を終了させてから再起動するまでの間に iPad から開始すると、終了しかけた Typeless にショートカットが届かないか、Host が別に起動してしまう。その間はショートカットを押すのを待たせ (最大 15 秒)、終了させる直前に音声入力が始まっていないかを再確認する。
  - 前の音声入力が停止したのに監視 (0.2 秒ごと) が気づく前に開始を押すと、あとから前の「停止」が届き、iPad が開始させたことを忘れていた。忘れると iPad が切断したときに Typeless を停止せず、音声入力が残る。押してから 1 秒の間に届いた「停止」では忘れない。単体テストで、修正前の判定にすると失敗することを確認した。
  - iPad のマイクを開始できなかったとき (電話のあと、ほかのアプリがマイクを使っているとき) は、黙って Mac に開始させていた。許可がないときと同じく「Mac のマイクで音声入力します」と通知する。
  - 新しく接続したら、「iPad の音声を使っている」を初期状態にする。前の接続の値で、Mac で直接話したときに Typeless の設定を確認しにいっていた。
  - Typeless・ヘルパーアプリ・マイクを実際に動かす確認は、ユーザーの音声入力と Mac のマイクを使うことになるので、単体テストとビルドまでにしている。
  - 修正していない指摘: 音声入力の途中でヘルパーアプリが接続したり再起動したりしたときに、ヘルパーアプリに音声入力を再依頼しないこと (Typeless は開始したときに開いたマイクを使い続けるので、再依頼してもその回には効かない)。iPad が切断してから 60 秒の間にヘルパーアプリが強制終了されたときのデバイスの残り (その間はヘルパーアプリを再起動し、起動したヘルパーアプリが残りを削除する)。
- ヘルパーアプリは Host とループバックの接続で接続する。Host は起動のたびにシークレットを渡し、シークレットを提示しない接続は切断する (10 秒待っても提示しない接続も切断する)。
- ヘルパーアプリと Host の起動・終了を読み直して修正したこと (2026-10-18、別のエージェントに読ませた指摘から):
  - 既定の出力の機器が変わってチャンネル数やサンプルレートが変わると、ヘルパーアプリの音声を再生するエンジンは自分で停止する (`AVAudioEngineConfigurationChange` の説明のとおり)。停止したままだとタップが無音になり、iPad で話しても Typeless に何も届かず、Host も気づかない。通知を受けたらエンジンを再起動する。出力の機器を切り替えるのは Mac 全体の設定を変えることになるので、ビルドまでにしている。
  - ヘルパーアプリが後始末をするのは、Host との接続が切れたときと SIGTERM だけだった。アクティビティモニタの「終了」やログアウト (Apple Event)、SIGINT・SIGHUP で終了するとデバイスとタップが残る。終了直前 (`applicationWillTerminate`) と SIGINT・SIGHUP でも削除する。Host の起動時にも、残ったデバイスとタップを探して削除する。探す処理を、何も削除しない形でこの Mac で実行し、どのデバイスの UID も読め、今は残りがないことを確認した。
  - Host が先に終了していると、ヘルパーアプリの接続は失敗ではなく待機 (`.waiting`) になり、ヘルパーアプリが残り続けうる。待機も終了の合図にした。
  - ヘルパーアプリを起動できなかったとき、iPad が再接続するまで再起動しなかった。3 秒おきに 3 回まで再起動する。ヘルパーアプリがクラッシュしたあとすぐ再起動していたので、クラッシュし続けると起動を繰り返し続けていた。2 秒待つ。
  - Typeless のマイク設定を書き換えるとき、ユーザーが自分で終了させていた Typeless まで起動していた。動作していたときだけ再起動する。
  - Host の「再起動」は、1 秒待ってから開いていた。古い Host の終了が遅れると、古い方を最前面に出すだけで終わり、Host が 1 つも残らない (蓋を閉じた Mac では iPad から接続できなくなる)。古い Host のプロセスが終了するのを待ってから開く。同じスクリプトを、代替のプロセスと `open` の代わりの echo で実行し、終了するまで (3 秒) 待ってから開くことを確認した。
    - それでも、終了した直後に開くと `open` が `_LSOpenURLsWithCompletionHandler() failed with error -600` で開けずに終わり、Host が 1 つも残らないことがある (2026-10-18、Host を更新したときに 1 度発生した)。開いて 1 秒後に `pgrep -x` で新しい Host が動いているかを確認し、動いていなければ 10 回まで開き直す。`open` の終了コードは man に書かれていないので、プロセスで確認する。自作の何もしない常駐アプリと、最初の 2 回は開かずに失敗するダミーの `open` でこのスクリプトを実行し、3 回目で開き直して新しいプロセスが動くことを確認した。
  - 修正していない指摘: シークレットが起動引数に含まれ、同じ Mac のほかのプロセスから読める (同じ Mac で動くものを信用しない設計にはしていない。iPad との通信もペアリングなし)。

### Typeless のショートカットは「押し続ける」のではなく「1 回押す」

- iPad の物理キーボードで Typeless のショートカットを押したときに、iPad のマイクで音声入力させる案は見送った (2026-10-18)。今は押したキーがそのまま Mac に届き、Typeless は Mac 側の入力で音声入力する。ただ、この Mac のショートカットは既定の「LeftCtrl+Fn」のままで (設定ファイルのショートカットの欄だけを読んだ)、iPadOS は Fn (地球儀キー) をアプリに渡さないので、iPad のキーボードからは押せず、不整合は起きない。ショートカットを Fn のない組み合わせに変更したユーザーのためには、iPad から送ったキーで Typeless が開始したら iPad のマイクを開始させる仕組みが必要になる。
- 設定ファイルのキー名は `keyboardShortcut.pushToTalk` だが、**押すたびに開始と完了が切り替わる**方式。押し続けると、音声入力は開始せず「Typeless ショートカット」の使い方の案内 (「話すには一度押してください…」) が表示されるだけ。
  - 最初はキーを押し続けて実装し、この案内を音声入力中と取り違えて「動いた」と判定していた。ユーザーには一度も正しく起動していなかった。
- Mac は、iPad から「開始」「完了」が届くたびに、ショートカットを 50ms だけ押して離す。iPad のボタンは、タップで開始と完了を切り替える使い方と、押している間だけ話す使い方の両方に対応する (どちらも Mac では 1 回押しになる)。
- 合成する修飾キーのイベントには、実際のキーボードと同じく次のビットを載せている。
  - 左右を区別するビット (左 Control は `0x1`)
  - 合成ではない実入力であることを示すビット (`0x100`)
- ショートカットは、押すたびに `~/Library/Application Support/Typeless/app-settings.json` を読み直す。書き換えはしない。
- Typeless が動作していなければ、押す前に起動する。Typeless はショートカットを本体プロセスのキーのイベントタップ (セッションと HID の 2 つ、キーの押下・解放・修飾キーの変化を監視する) で拾い、本体からレンダラー側へ `global-keyboard` として送っている。タップが作られるまでは押しても届かないので、`CGGetEventTapList` で Typeless のタップが現れるまで (最大 10 秒) 待ってから押す。初めは起動完了後に固定で 1.5 秒待っていた。
  - それでもレンダラー側の準備が間に合わずに届かなかったときは、音声入力が開始しないので押し直しで拾う。押し直しのカウントを開始するのは押したときから。初めは iPad から要求が届いたときからカウントしていて、Typeless の起動を待つ間に押し直しの 5 秒を使い切り、開始する前に iPad の表示を戻してしまう作りだった。

### Typeless の動作確認の方法

- ウィンドウが表示されたかどうかでは判定できない。音声入力中の小さなピル (✕・波形・✓) も使い方の案内パネルも、同じウィンドウ (750x500) に描画されるため。
- 2026-10-17 にウィンドウを撮影して比較したところ、不透明な暗い部分の高さは、ピルが 64px、案内パネルが 298px だった。
- 実際に文字になるかを、Mac の `say` で確認することはできない。Typeless の音声取得にかかるエコーキャンセルが、Mac 自身のスピーカーの音声を消してしまう。
- 1 回押すと Typeless のマイク入力が始まり、もう 1 回押すと止まることを、macOS の audiomxd のログ (`input_running`) で確認した (2026-10-17)。

### iPad のボタンの表示は、Typeless の実際の状態に合わせる

- 最初は iPad と Mac がそれぞれ「開始を送ったか」だけを記憶していた。Typeless が自分で音声入力を終了したり、Mac 側で ✕ を押したりすると記憶とずれる。次の「完了」でショートカットを押すと逆に音声入力が始まり、「Typeless の状態と iPad の赤・青が逆になる」と報告された (2026-10-17)。
- Typeless は音声入力の状態を外部に公開していない。そこで、音声入力している間だけマイクを使うことを利用して、CoreAudio のプロセスの入力状態 (`kAudioProcessPropertyIsRunningInput`) で判定する (`TypelessMonitor`)。
  - Typeless は Electron 製で、マイクを使うのは本体ではなく `now.typeless.desktop.helper` (Typeless Helper)。バンドル ID の先頭が `now.typeless.desktop` のプロセスをまとめて監視する。
  - CoreAudio のプロセス `now.typeless.desktop.helper` の PID は 2204 だった。audiomxd が音声入力中に `input_running: true`、完了後に `false` と記録した「Typeless Helper(2204)」と同じプロセスであることを、PID で照合した (2026-10-17)。
  - プロセスの入力・出力状態の値は正しく変わるが、`AudioObjectAddPropertyListenerBlock` の変化通知は来なかった。自プロセスで、音の出ない出力を 1 秒流して確認した (2026-10-17)。このため、iPad が接続している間だけ 0.2 秒ごとに読み直す。
- Mac はショートカットを押す前に実際の状態を確認し、すでに要求された状態なら押さない (`TypelessToggle`)。押してからマイクが動き出すまで 0.1〜0.2 秒かかる。押してから 1 秒の間は、押した結果を現在の状態とみなす。
- iPad は押した直後に、要求した状態を先に表示する。そのあと Mac から状態 (`voiceInputState`) が届いたら、それに合わせる。Typeless がショートカットに反応しなかった場合は状態が変わらず通知が来ないので、Mac は要求から 1 秒後に必ず現在の状態を送る。
- iPad がバックグラウンドに移ったときや接続が切れたときに停止するのは、iPad から開始した音声入力だけ。iPad が自動でロックされたときに、Mac で直接話している音声入力を止めてしまわないため。

## 通信: ペアリングも暗号化もしない

- 最初は TLS-PSK (Mac が発行する 10 文字のペアリングコード) で、暗号化と相互認証をしていた。
- ユーザーから「ペアリングコードは邪魔」と言われ、廃止した (2026-10-17)。認証の鍵をリポジトリに埋め込んでも公開リポジトリでは意味がないので、TLS ごと外して素の TCP にしている。**同じ LAN の誰でも Mac を操作できる**ことは README に明記した。
- Mac は Bonjour (`_padbridge._tcp`) で広告する。iPad は、前回接続した Mac か、見つかった Mac が 1 台だけならそこへ自動で接続する。
- iPad でこのアプリにローカルネットワークが許可されていないと、`NWBrowser` は `.waiting(.dns(kDNSServiceErr_PolicyDenied))` で停止し、Mac が 1 台も見つからない。そのときは「Mac が見つかりません」(Mac 側を疑わせる文) ではなく、許可が必要なことと iPad の設定を開くボタンを表示する。
  - 判定は [TN3179](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy) の `NWBrowser` の例と同じ。あとで許可されると、システムが自動でやり直す。初回の許可ダイアログを表示している間も、応答を待たずに拒否することがあるとされているので、そのときはダイアログの後ろにこの通知が表示され、許可すると消える。
  - 判定は `LocalNetworkAccess` にまとめ、TN3179 の値 (-65570) で停止したときだけ許可がないとみなすことを単体テストで確認した。値を別のエラーに変えるとテストが失敗する。
  - OS が実際に拒否したときの画面は表示していない。TN3179 のとおりシミュレータはこの許可に対応しておらず、この iPad は許可済みで、Mac で拒否させるとユーザーの画面に許可ダイアログが表示されて設定にも記録が残るため。表示するにはユーザーの iPad でこの許可をオフにする必要がある。
- 接続は**操作用と映像用の 2 本**に分けた。1 本にまとめると、映像の送信が輻輳したときにクリックやキー入力まで待たされるため。
- Mac は、送信待ちが 4 件以上溜まったら、キャプチャしたフレームをエンコードする前に破棄する。エンコードしたあとで破棄すると、参照フレームが欠けて映像が壊れる。
- 未知の種類のメッセージや、未知の操作 (JSON の未知のケース) が届いても、接続は閉じずにそのメッセージだけスキップし、ログに記録する。メッセージの区切りは framer が長さで切り出しているので、1 件を読み飛ばしても後続はずれない。初めは解釈できないものが来たら接続を閉じていたが、Mac と iPad の片方だけを新しいビルドにすると (2026-10-17 に Host だけが古いまま動いていたことがある)、新しい方が送るものを古い方が受け取るたびに切断され、再接続を繰り返すことになる。
- 相手が切断を通知せずに消えたとき (圏外、スリープ、iPadOS がバックグラウンドのアプリの通信を止めたとき) は、TCP のキープアライブと再送の打ち切りで検知する。無通信が 2 秒続いたら 2 秒おきに確認し、4 回応答がなければ切断する。送信中は確認が送られないので、再送に 10 秒応答がなければ切断する。初めはキープアライブを開始するまでの 2 秒だけを設定していたが、間隔と回数は macOS の既定 (`net.inet.tcp.keepintvl` 75 秒、`keepcnt` 8 回) のままで、検知まで約 10 分かかっていた。その間 iPad は停止した映像を表示したまま、再接続しない。

## 接続・再接続の流れを読み直して修正したこと (2 回目、2026-10-18)

- 別のエージェントに接続の流れを読ませ、指摘をコードと照合して修正した。
  - iPad は、接続した Mac の Bonjour 名を固定したまま再接続していた。前の Host の登録が残っている間に Host が再起動すると、Mac の名前が「 (2)」付きに変わり、消えた名前を待ち続けて「再接続中…」のまま復帰しなかった (以前は「(2) 付きに変わっても自動で再接続できる」と書いていたが、それはセッションがないときだけだった)。接続中の Mac の名前が一覧から消え、Bonjour が付けた番号だけが違う同じ名前の Mac が現れたら、そちらへ再接続する。名前の比較 (`PadBridgeService.baseName`) は単体テストで固めた。
    - シミュレータでエンドツーエンドで確認した。テスト用の Host をループバック上だけで Bonjour に広告し (`dns-sd -B` で、広告がループバック `if 1` だけに出て、Wi-Fi 側に出ないことを先に確認した。ユーザーの iPad に見せないため)、テスト用アプリには本物の AppModel を、名前が「ProbeMac」で始まる Mac だけを候補にして構成した (本物の Host に接続しないため)。「ProbeMac」に接続したあと、テスト用の Host を「ProbeMac (2)」として再起動すると、約 5 秒でそちらへ再接続した。名前を追う処理を外した構成では、20 秒待っても接続できなかった。
  - Mac を探す `NWBrowser` が失敗 (mDNSResponder の再起動など) しても作り直さず、アプリを再起動するまで Mac が見つからなかった。2 秒おいて作り直す。
  - 操作用の接続を張り直したあとに、前の接続から遅れて届いた「ようこそ」で、接続済みの扱いになりえた。現在の接続から届いたものだけ受け付ける。再接続の間隔 (0.6・1.0・2.1・4.3・5.1・5.2 秒) と、接続できないときの通知 (5 秒では出さず 14 秒で出し、接続したら消える) は、シミュレータのテストで修正前と同じだった。
  - 切断したあとも、前のセッションのマイクを停止する予約が残り、次のセッションでマイクを使っている間の Mac の音声の抑制を解除しえた。切断のときに取り消す。
  - バックグラウンドで接続を保つための無音の再生が、起動の失敗やオーディオの仕組みの再構築 (`mediaServicesWereReset`) で止まると、そのままだった。次にバックグラウンドに移ると iPadOS に停止されて接続が切れる。フォアグラウンドに戻ったときと再構築の通知で再生し直す。
  - Host は、作り直す前のリスナーから遅れて届いた「失敗」で、新しいリスナーを停止していた。現在のリスナーの通知だけ受け付ける。

## 接続・再接続の流れを読み直して修正したこと

- 2026-10-18 に、別のエージェントに接続の流れ (iPad の再接続、Host のリスナーとキャプチャ) を読ませ、指摘をコードと照合して修正した。
- キャプチャを開始している途中 (`startCapture` を待つ間) に停止されると、停止処理はまだ開始していないキャプチャに効かず、キャプチャが動き続けていた (画面収録の表示も消えない)。開始が完了した時点で停止されていたら止め直す。再作成したあとの古いキャプチャからの失敗の通知で、新しいキャプチャが使っている映像の接続を閉じないようにもした。キャプチャを実際に動かすとユーザーのディスプレイをキャプチャすることになるので、ビルドまでにしている。
- iPad は、接続した時点で再接続の間隔を 0.5 秒に戻していた。接続してすぐ Mac に切断されることが続くと、0.5 秒おきに再接続し続ける。welcome を受信したときに戻す。映像の接続も、再接続の間隔を 5 秒まで延ばしていき、映像の形式が届いたら戻す。シミュレータで、テスト用の Host が名乗りを受けてすぐ切断するようにして測定した。修正後の間隔は、操作の接続が 0.6・1.1・2.1・4.2・5.3・5.2 秒、映像の接続が 0.5・1.1・2.1・4.1・5.3・5.2 秒。
- Host のリスナー (`NWListener`) が失敗状態になると、Host を再起動するまで iPad から接続できなかった (蓋を閉じた Mac では致命的)。2 秒待って作り直す。
- iPad が映像の接続を張り直すとき、Host はディスプレイ構成の再読み込みの予約まで取り消していた。Mac がスリープから復帰してディスプレイ構成が変わったのと同じ頃に iPad が再接続すると、古いディスプレイの大きさのまま配信していた。映像を停止しても、再読み込みは取り消さない。
- 接続したまま名乗らない接続が、Host にいつまでも残っていた。10 秒で閉じる。実際の Host に、何も送らない TCP の接続を確立して、10.7 秒後に閉じられることを確認した (iPad が接続していないことを確認してから)。
- 受信したメッセージの値の検証 (2026-10-18)。ペアリングなしで同じ LAN の誰でも接続できるので、壊れたデータや極端な値で Host や iPad アプリが停止してはいけない。
  - スクロール量を、ディスプレイの幅を掛けてそのまま `Int32` にしていた。1e300 のような値が JSON で届くと、`Int32` に収まらずに Host が停止する (修正前の計算をそのまま小さなプログラムで実行し、終了コード 133 で停止することを確認した)。量を 1 回あたり ±10,000 ピクセルまでにし、有限でない値は破棄する (`ScrollWheel`)。
  - 映像の範囲 (`VideoRegion`) は、バイナリで届く値が NaN や無限大にもなりうるのに、そのまま iPad の表示位置や Mac の切り出しに使っていた。生成時と JSON の読み込み時に、有限でなければディスプレイ全体、幅と高さは刻み〜1、位置はディスプレイの範囲内に収める。
  - 単体テストで、どの種類にもランダムな中身を、正しいメッセージを途中で切ったものと 1 バイトずつ壊したものも読み取りに通し、停止しないことを確認した (`WireFuzzTests`)。
- 修正していない指摘: 前回の Mac が見つからず、ほかに Mac が 1 台だけ見つかると、そちらに自動で接続する (Mac を 2 台使う家に限る。今のままにする)。映像の接続の名乗りが現在の操作の接続と同じ iPad からかを確認していない (1 台で使う前提)。

## バックグラウンドに移っても切断しない

- ユーザーから「バックグラウンドで切れるのは論外」と言われた (2026-10-17)。
- iPadOS は、バックグラウンドに移ったアプリを数秒で停止する。そこで接続中は、`UIBackgroundModes: audio` と `.playAndRecord` + `.mixWithOthers` のオーディオセッションで、無音を流し続ける (Typeless で話すときに iPad のマイクも使うので、録音もできるカテゴリにしておく。あとから切り替えると流している無音が停止する)。音は出ず、他のアプリの音楽なども止めない。
- バックグラウンドにいる間は、映像用の接続だけ閉じる (電池と通信量を抑えるため)。フォアグラウンドに戻ったら、映像用の接続を張り直してキーフレームから描画し直す。
- 映像を送っている間だけ、Host が `PreventUserIdleDisplaySleep` のアサーションを持つ。iPad で見ているだけで操作しない間に、Mac のディスプレイが「ディスプレイをオフにする」の時間 (この Mac は 10 分) でスリープし、表示されなくなるのを防ぐ。Amphetamine などが動いていなくても見続けられる。iPad がバックグラウンドに移って映像の接続を閉じると解放する。
  - このアサーションは、すでにスリープしているディスプレイを復帰させない。iPad がバックグラウンドにいる間にディスプレイがスリープすると、フォアグラウンドに戻っても何も表示されない (ScreenCaptureKit は画面が変わらないとフレームを出さない)。配信を開始するときに `IOPMAssertionDeclareUserActivity` で操作があったと通知して復帰させる (この Mac は Amphetamine がディスプレイをスリープさせていないので、ふだんは発生しない場面)。
- 操作用の接続が切れたら、一覧画面に戻さず、その場で 0.5 秒から 5 秒までの間隔で張り直し続ける。
- 実機で、ホーム画面に 20 秒移っても Mac 側に切断が記録されず、戻ると映像だけが再要求されることを確認した (2026-10-17)。

## iPadOS に取られるハードウェアキーボードのショートカット

- シミュレータ (iPad Air 11 インチ M4、iOS 26.5) で、⌘ と英数字・記号の組み合わせ 44 通りを押し、Mac のディスプレイのビューに届くかを調べた (2026-10-18)。XCUITest の `typeKey` で押した。
  - 何もしていない状態では、⌘B・⌘E・⌘F・⌘G・⌘I・⌘M・⌘N・⌘O・⌘Q・⌘R・⌘U・⌘- の 12 通りで、⌘ だけが届いて文字が届かなかった (2 回とも同じ)。iPadOS 26 のメニューバーの項目 (太字・検索・新規・開く・しまう・終了など) と重なる。
  - `UIKeyCommand` を `wantsPriorityOverSystemBehavior` 付きで宣言すると、⌘B・⌘E・⌘F・⌘G・⌘I・⌘U・⌘- は押したキーがそのまま `pressesBegan` に届くようになった (宣言した動作は呼ばれない)。⌘M・⌘N・⌘O・⌘Q・⌘R は宣言しても届かない。⌘Tab・⌘Space・⌘H は iPadOS のアプリ切り替え・検索・ホームが受け取る。
  - ⌘M・⌘O・⌘Q・⌘R の文字のキーは、アプリへの入口 (`UIApplication.sendEvent`) にも来なかった (⌘ の押下と解放だけが来る。⌘Q では ⌘ も取り消しで終わる)。iPadOS がアプリの外で受け取っているので、アプリからは受け取れない。代わりに「…」の「Mac のショートカット」から送る。
  - アプリの標準メニューを `buildMenu` で外すと、かえって ⌘A・⌘C・⌘V・⌘X・⌘Z・⌘, も届かなくなり、宣言と組み合わせるとアプリがクラッシュした。外す方法は採用しない。
  - Mac のディスプレイのビューと直接入力のファーストレスポンダの両方で、⌘・⇧⌘・⌥⌘・⌃⌘ と英数字・記号の組み合わせを宣言している。宣言した動作が呼ばれたときは、そのキーを修飾キー付きで送る。
  - 1 回目の起動直後や、⌘Tab・⌘Space で iPadOS の画面が開いた直後は、次のキーが届かないことがある。比較するときは、起動後に通常のキーを 1 回押してから始め、iPadOS の画面を開くショートカットは最後に押す。
- ⌘. は届くが、iPadOS はキー情報から ⌘ を外して渡す (修飾キーが 0)。Mac では . だけが入力されていた。Host は修飾キーの押下と解放を記憶しているので、修飾キーでないキーには押されている修飾キーを載せる (`HeldModifiers.keyEvent`)。テスト用ビルドで、⌘ を押している間の . に ⌘ のフラグ (0x100000) が付き、離したあとは付かないことを確認した。
  - 修飾キーが押されたまま残ると、そのあとのキーがすべてショートカットになってしまう。⌘Tab と ⌘Space のあとも ⌘ の押下と解放が対になって届くことを、シミュレータで確認した。

## 英数・かなのどちらが有効かを表示する

- iPad のキーボードで日本語を入力するときに、Mac の日本語入力が英数とかなのどちらかを、キーボード上部のバーの英数・かなキーの色で示す。Host が現在の入力ソースを読み、変わるたびに `macInputMode` で通知する。
- 入力ソースの分類 (`MacInputMode`): キー配列そのもの (ABC など) と日本語入力の英字 (`com.apple.inputmethod.Roman`) は英数、日本語入力のひらがな・カタカナ・半角カナ (`com.apple.inputmethod.Japanese`・`.Katakana`・`.HalfWidthKana`) はかな、全角英字や他の言語の入力はどちらでもない。ID は、この Mac に入っている日本語入力 (ローマ字入力・かな入力) の入力ソースから読んだ (2026-10-18)。有効な入力ソースは ABC とローマ字入力のひらがなで、Host と同じ読み方でそれぞれ英数・かなになった。
- 入力ソースの変更通知 (`kTISNotifySelectedKeyboardInputSourceChanged`) は分散通知で届く。AppKit はアプリがフォアグラウンドにない間、分散通知を停止する ([suspended](https://developer.apple.com/documentation/foundation/distributednotificationcenter/suspended))。既定の登録では、停止している間の通知はフォアグラウンドに来るまでまとめて持ち越される (SDK のヘッダーの `NSNotificationSuspensionBehaviorCoalesce`)。Host はメニューバーの常駐アプリで、メニューを開いたあとフォアグラウンドから外れると停止するので、`deliverImmediately` で登録する。
  - テスト用アプリで確認した (2026-10-18)。一度もフォアグラウンドに来ていないアプリは停止していない (`suspended` が false) ので、AppKit がフォアグラウンドから外したときと同じく `suspended` を true にした (フォアグラウンドに出して外すと、ユーザーのアプリから入力を奪うため)。別のプロセスから通知を送ると、既定の登録には 3 秒待っても届かず、停止を解除したときに届いた。`deliverImmediately` の登録にはすぐ届いた。
  - 同じプロセスに両方の登録があると、`deliverImmediately` の側に届いた時点で持ち越していた通知もまとめて届く (SDK のヘッダーのとおり)。比較するときは 1 回に 1 通りだけ登録する。
- シミュレータで、テスト用の Host から「かな」、12 秒後に「英数」を通知すると、かなのキー、英数のキーの順に青くなった (VoiceOver の値も「入力中」が移る)。

## 音声入力の流れを読み直して修正したこと

- 2026-10-18 に、別のエージェントに音声入力の流れ (iPad のマイク、Host の押し直し、ヘルパーアプリ) を読ませ、指摘を一つずつコードと照合して修正した。
- Typeless が動作していないときに開始すると、Host は押すと決めた時刻を記憶してから Typeless の起動を待っていた (最大 20 秒)。待つ間に iPad で指を離すと、完了の判断のときには記憶した時刻から 1 秒を超えていて、まだ録音していない Typeless の状態を見て「停止する必要がない」と判断し、押さなかった。Typeless は録音したまま残る。起動を待つのを、押すと決める前に行うようにした。
  - テスト用ビルドで、Typeless の代替 (起動に 2 秒、開始の 0.3 秒後に録音が始まる) を使って確認した。修正前は 1 回しか押されず録音が残り、修正後は 2 回押されて停止した。キーは Mac へ送らず記録しただけ。
- iPad で指を離してすぐ (Typeless が停止したのを Host が検知するまでの 0.3〜0.6 秒以内に) また押すと、前の音声入力の終了通知が新しい要求のあとで iPad に届き、iPad は開始したばかりのマイクを停止していた。Host も同じ通知で、ヘルパーアプリの新しい音声入力の準備を消していた。iPad から開始させて、まだ Typeless が音声入力を開始していない間は、音声入力の終了を通知せず、準備も消さない。開始しなければ、押し直しのあとで通知する。
- ヘルパーアプリの応答を待つ間 (最大 1.5 秒) に指を離すと、遅れて届いた応答で Typeless を開始していた。押し直しの途中で切断したときも、残りの押し直しで開始していた。どちらも、その時点で新しい要求が来ていれば (切断したときも新しい要求とみなす) 何もしない。
  - 要求の番号と、開始させて確認していない要求は、Kit の `VoiceInputRequests` にまとめて単体テストで固めた。
- ヘルパーアプリの応答のタイムアウトが前の要求のものでも、次の要求の応答を待つのをやめていた。タイムアウトに要求の番号を持たせた。
- Typeless のマイクが「自動検出」のままのときに Host が設定を書き換える処理は、録音が停止した瞬間に Typeless を終了させていた。停止したあとに文字に変換して貼り付ける数秒の間で、その結果が失われる。8 秒続けて録音していないときだけ実行し、2 分録音が続くなら終了させない。同時に 2 つ実行されないようにもした。
- iPad のマイクのエンジンは、AirPods の接続・取り外しなどの経路の変更や、電話・Siri による中断で停止する。停止しても再開せず、話しても Mac に無音しか届いていなかった。停止したら同じ送信先で再開する。シミュレータのマイクは Mac の既定の入力 (この Mac では内蔵マイク) を録音するので、再開はビルドまでにしている。
- 停止したとき、ヘルパーアプリにバッファされている iPad の音声が再生開始のしきい値 (150ms) に届いていないと、残りは再生されないまま、再生完了を待つ処理が 7 秒のタイムアウトまで待ち、その間 Typeless は音声入力を続けていた (iPad をバックグラウンドに移した直後に停止したときなど)。停止したら、バッファが満たされていなくても残りを再生する (`PCMJitterBuffer.playRemaining`)。単体テストで、バッファが満たされる前に呼ぶと残りがすぐ再生されることを確認した。
- 修正していない指摘: ヘルパーアプリの処理キューが塞がっていると最初の 100ms が破棄されうること (Mac のマイクの音声を流しているときなどに限る)。
- 押し直しが Typeless の「開始処理の途中」に当たると停止してしまうのでは、という指摘は、Typeless の内部 (xstate の状態機械) を読んで当たらないと分かった。`idle` で押すと `initializingForTapOrHold` に移り、入ったときにマイクを起動する (`startRecording`)。この間の押下 (`PRIMARY_KEY.DOWN`) は受け取る処理がなく、解放の通知 (`PRIMARY_KEY.UP`) は「開始処理の途中に離した」を記憶するだけ。開始が完了すると音声入力 (`recording_active.handsFree`) に移り、そこで初めて押下が停止の操作になる。そのときはもうマイクが動作しているので、Host は押し直さない。

## Mac 側でテキストを入力する方法

- 第 1 候補は、アクセシビリティ API で入力欄の選択範囲 (`kAXSelectedTextAttribute`) に書き込む方法。クリップボードを使わないので、ユーザーのクリップボードやクリップボード履歴を汚さない。

## 映像

- ScreenCaptureKit で配信するディスプレイ (iPad で選択されたディスプレイ、なければメインディスプレイ) をキャプチャし、VideoToolbox の HEVC でエンコードする (利用できない Mac では H.264)。低遅延レート制御を使い、プロファイルは HEVC Main (H.264 は ConstrainedHigh)、フレームの並べ替えはしない。
- 2026-10-18 に H.264 から HEVC に変更した。1920x1080 で 1 フレームに 2 ピクセルずつ流れる文字の画面を 60 フレーム、同じ 8.3Mbps でエンコードしてデコードし、元との輝度の PSNR を比較すると、H.264 は平均 27.4dB、HEVC は 39.6dB だった (この Mac、M5)。1 フレームを渡してから出力されるまでは、60fps で渡して H.264 が平均 5.3ms・最大 24.0ms、HEVC が平均 5.6ms・最大 14.5ms で、遅延は変わらない。
  - 映像の形式 (`VideoFormat`) にコーデックを持たせ、パラメータセットは H.264 の SPS・PPS、HEVC の VPS・SPS・PPS を順に送る。iPad は届いたコーデックで `CMVideoFormatDescription` を作るので、Host が H.264 にフォールバックしても表示できる。iPadOS 26 が動く iPad はどれも HEVC をデコードできるので、iPad から対応状況を通知する仕組みは追加していない。
  - 送信する形式が変わったので、Host と iPad アプリは一緒に更新する (片方だけ古いと、映像の形式を読めない)。
  - 単体テストで、HEVC と H.264 のどちらも、実際に送るサイズでエンコードからデコードまで通ることを確認している。シミュレータでは、テスト用の Host が HEVC でエンコードしたテスト用の絵 (文字と四隅の色) が、iPad アプリの画面に向きも正しく表示された。
  - 低遅延のエンコーダを 10 個同時に作ると、`VTCompressionSessionCreate` から戻らなくなった (テストを並列に実行したとき。停止したプロセスのスタックで確認した)。Host は 1 つずつしか作らないので、テストを順次実行する。
- iPad 側は `AVSampleBufferDisplayLayer` に圧縮したまま渡してデコードさせる。
- ScreenCaptureKit は画面が変わらないとフレームを出さない。そのため、要求に応じたキーフレームと、念のための 30 秒ごとのキーフレームで復帰ポイントを作る。画面が停止している間に要求されたキーフレームは、保持している最後の絵から作る (下の「画面が停止したあとの再送」)。
  - 2026-10-18 までは 5 秒ごとだった。受信確認付きで送るようになり、途中で失われるフレームはなく、iPad は描画できなくなったら自分でキーフレームを要求するので、定期のものは保険でよい。大きなキーフレームは遅い回線で遅延のピークになる。途切れずにスクロールする模様を本物のエンコーダで 40 秒送り、受信側の速度を絞って比較した。10 Mbps・iPad のサイズでは、遅延が 100 ms を超えたフレームが 5 秒ごとで 34〜35 フレーム (最大 359 ms)、30 秒ごとで 14 フレーム (最大 231 ms)。5 Mbps・1920x1080 では 44 フレーム (最大 414 ms) と 16 フレーム (最大 290 ms)。届いたフレーム数も 30 秒ごとの方が 5% ほど多かった。
- 実機の iPad (2360x1640) では、2360x1532、14 Mbps で配信している。
- キャプチャのサイズは、iPad の画素数と長辺どうし・短辺どうしで比較して決める (`CaptureSize.fitting`)。以前は横向きの 2360x1640 と縦横そのままで比較していたので、縦に置いた 1080x1920 のディスプレイは 922x1640 に縮んでいた。iPad を縦にすれば 1080x1920 のまま表示できるので、縮めずに送る。古い比較方法に戻すと単体テストが失敗することを確認した。
- エンコードからデコードまでの単体テストは、実際に送るサイズ (1920x1080、2360x1532、1080x1920、1326x2360) と Host と同じビットレート (`CaptureSize.bitRate`) で行う。ビットレートを 4Mbps に固定していたときは、大きなディスプレイで 10 フレーム中 1〜2 フレームを低遅延のレート制御が破棄した (縦横どちらの向きでも同じ)。Host の式なら 10 フレームとも届いた。
- キャプチャのサイズは開始時に決まるので、Mac の解像度やメインディスプレイが変わると、映像が縮んだり別のディスプレイを配信したりして、タッチした位置とずれる (タッチの座標は毎回そのときのメインディスプレイで変換するため)。Host は `NSApplication.didChangeScreenParametersNotification` を受けたら、メインディスプレイの ID・サイズ・画素数がキャプチャ開始時と違うときだけ、同じ映像の接続のままキャプチャとエンコードを作り直す。iPad は新しいキーフレームと一緒に届く映像の形式でサイズを読み直す。蓋を閉じたこの Mac でも、メインディスプレイは内蔵の 1 台で、サイズ (1800x1169、3600x2338) は変わらないので、余計に作り直すことはない。
  - 外部ディスプレイに対応してからは、比較する対象をメインディスプレイではなく配信中のディスプレイにした。通知を受けたら 0.5 秒待ってからディスプレイの一覧を読み直し、配信するディスプレイを決め直す。

### 遅い回線での映像の送り方 (2026-10-18)

- 以前は、`MessageChannel` の送信待ち (`contentProcessed` がまだ来ていない数) が 4 以上のときに、エンコードする前にフレームを破棄していた。`contentProcessed` は OS の送信バッファに入った時点で来るので、バッファが何秒分も吸い込むまで破棄が始まらない。
  - ループバックで受信側が 10 Mbps でしか読まないようにし、60 KB のフレームを 60fps で送ると、遅延は 0.3 秒から 3.3 秒まで増え続けた。本物のエンコーダで重い映像 (毎フレーム全体が変わる模様) を iPad のサイズ (2360x1532、14.5 Mbps) で送っても、10 Mbps の回線で遅延が 2.3 秒まで増え続けた。
- 今は iPad が、映像用の接続で受信したフレームごとに受信確認 (ACK、`videoFrameReceived`) を返し、Host は受信確認の来ていないフレームが 3 フレーム (`VideoFlowControl.maxInFlight`) になったら、次のフレームをエンコードせずに破棄する。遅延は、およそその数のフレームを送る時間に収まる。
  - iPad は Host に要求されたとき (`acknowledgeVideoFrames`、映像の接続を受けたときに送る) だけ受信確認を返す。受信確認を知らない古い Host に、未知のメッセージを毎フレーム送らないため。受信確認が一度も来ない古い iPad アプリには、従来どおり送信待ちの数で破棄する。
  - 受信確認が 2 秒来なければ待つのをやめる (`stallTimeout`)。受信確認は描画する前に返し、描画時間で Host を待たせない。
  - シミュレータのテスト用アプリ (本物の iPad の画面のファイルをそのままビルドしたもの) で、テスト用の Host が要求したときは 5 フレームすべてに受信確認が来て、要求しないときは 1 つも来ないことを確認した。
- 破棄した割合からビットレートも変える (`BitRateController`)。輻輳したまま同じサイズで送ると、破棄されて動きがカクつくため。
  - 2 秒ごとに見直し、破棄した割合が 1 割以上なら 0.6 倍に下げ、破棄しないウィンドウが 3 つ続いたら 1.25 倍に上げる (上限は `CaptureSize.bitRate`、下限は 1.5 Mbps)。1 秒ごとだと、ウィンドウを切り替えたときのような大きな 1 フレームを送る間に破棄した分 (5 Mbps で約 9 フレーム、15%) だけで下げてしまった。キーフレームの受信確認を待っている間に破棄した分も数えない。
  - 回線が埋まっていた間に届いた量 (前の受信確認のときにはもう送信していたフレームの、前の受信確認からの時間) から回線の速度を見積もり、その 85% より下げない。それ以上縮まない映像では、ビットレートを下げてもエンコーダがフレームを落として合わせるだけで、フレーム数が減る (見積もりを入れる前は 5 Mbps の回線で 1.8 Mbps まで下げ、5〜6 fps になった)。
  - エンコードを続けたまま `kVTCompressionPropertyKey_AverageBitRate` を変えると、6 フレームほどで 1 フレームが小さくなることを単体テストで確認した (1280x720 で 20 Mbps から 2 Mbps に下げ、約 40 KB から 8〜12 KB)。
- ビットレートを上限の 7 割より下げたら「回線が遅いため、画質を下げています」、8.5 割まで戻したら「画質を戻しました」を iPad に 3 秒表示する (`videoQuality`)。通知は種類 (ディスプレイ・画質) ごとに持ち、ディスプレイを切り替えた通知で画質の通知が消えないようにした (同時に送ると両方表示され、2 秒と 3 秒でそれぞれ消えることをシミュレータで確認した)。Host は新しい映像の接続を受けたら、下げたかどうかを初期状態にする (新しいキャプチャは上限から始まるので、続けて下げたときの通知が出なくなっていた)。映像がぼやけた理由が分からないため。境界でジッターして何度も表示されないよう、下げたと判定する値と戻したと判定する値を離し、Host は同じことを続けて送らない。シミュレータのテスト用アプリで、テスト用の Host が送った 2 つの通知が表示され、3 秒で消えることを確認した。ディスプレイ切り替えの通知と同じ仕組みにまとめたので、そちらも表示されて消えることを再確認した。
- iPad の「…」の「接続状況」に、Mac が 2 秒ごとに送る映像の状態 (`videoStats`: 形式・サイズ・現在のビットレートと上限・往復遅延) と、その間に iPad に届いたフレーム数と量を表示する (2026-10-18)。ログを読むのは不具合の報告があったときだけにしているので、遅い・カクつくと感じたときに、回線のせいかを iPad で確認できるようにした。
  - Mac のメニューにも、iPad へ送っている映像の状態を 1 行で表示する (`VideoStats.summary`)。iPad で遅い・粗いと言われたときに、Mac の前でも回線のせいかを確認できるように。書式は単体テストで固め、メニューの見た目は画面に出さずに描画して、折り返しても読めることを確認した。
  - 接続している経路 (Wi-Fi のネットワーク、Wi-Fi の直接通信 awdl、有線、ループバック) も表示する (`ConnectionRoute`)。awdl はネットワークを経由しない分、ジッターの傾向が違う。awdl は種類としては Wi-Fi なので、インターフェース名 (`awdl`・`llw` で始まる) で見分ける。シミュレータではテスト用の Host にループバックで接続するので、「同じ機器の中 (ループバック)」と表示されることを確認した。
  - 往復遅延 (RTT) は、受信確認が届いたとき、届いたうちの最後のフレームを送信してからの時間を 2 割ずつ混ぜて平滑化したもの。受信確認を返さない古い iPad では表示しない。
  - シミュレータのテスト用アプリで、テスト用の Host が送った状態 (HEVC・1920x1080・8.0 Mbps・上限 14.5 Mbps・42 ms) がそのまま表示されることを確認した。
  - 別のエージェントの指摘で修正したこと。映像を停止すると、届いた量の集計の開始時刻が停止した時刻のまま残り、復帰した直後のフレーム数を停止していた時間で割っていた (1 分バックグラウンドにいると 1 fps ほどと表示される)。停止したら集計の開始時刻を空に戻す。映像を停止した直後に届いた状態で、停止前の値を表示し直していたので、映像がない間は破棄する。往復遅延は、キャプチャを作り直した直後は測定できていないだけなのに「この Mac は測らない」と表示されていたので、作り直しで引き継ぎ、測定できていない間は「測っています」と表示する。停止したキャプチャのエンコーダから遅れて出力されたフレームは、同じ接続で作り直したキャプチャの映像に混ぜない。
- iPad が低電力モードのときや、本体が熱い (`thermalState` が serious 以上) ときは、映像を 30 fps にしてもらう (`videoFrameRate`、2026-10-18)。長く使うときのデコードと描画の電池消費と発熱を抑えるため。iPad は接続したときに 60 でなければ要求し、状態が変わったら要求し直す。Mac はキャプチャの間隔とエンコーダの想定を作成時に決めるので、作り直す (受信確認の状態とビットレートは引き継ぐ)。「接続状況」にフレームレートの上限を表示する。
  - 熱の状態が serious と fair の境界でジッターすると、要求し直すたびに Mac がキャプチャを作り直し、映像が途切れる (別のエージェントの指摘)。減らすのは serious 以上になったとき、戻すのは nominal まで冷えたときにした。
  - シミュレータでは低電力モードを切り替えられないので、テスト用アプリのコピーだけ低電力モードとして動作させ、接続してすぐ (映像の接続より先に) 30 fps を要求することと、「接続状況」に減らしていると表示されることを確認した。Mac がキャプチャの間隔を変える部分は、ユーザーのディスプレイをキャプチャすることになるので、ビルドまでにしている。
- iPad を接続していない間の Host は、ほとんど何もしない (2026-10-18、動作中の Host を読み取っただけ)。起動から 16 分 48 秒で CPU 時間の合計が 0.20 秒、30 秒の間 0.0% のまま、メモリは約 60 MB で変化せず、`top` の CPU のウェイクアップ回数 (IDLEW) と電力 (POWER) はどちらも 0 だった。ヘルパーアプリも動作していない。
- 長時間接続したときの iPad アプリのメモリを、シミュレータで確認した (2026-10-18)。テスト用の Host から、黒い帯を動かした 1920x1080 の映像を 60 fps で 10 分送り続け (受信確認と 2 秒ごとの状態もやり取りする。音声は Mac のスピーカーから出るので流さない)、テスト用アプリのメモリ (RSS) を 30 秒ごとに読んだ。始めの 4 分ほどは約 341 MB、そのあと約 317 MB に下がって、終わりまで 317.2〜317.6 MB で横ばいだった。受信確認は 600 秒で 36,000 フレーム届き、60 fps を落とさずに受信して返していた。
- 別のエージェントに読ませて修正したこと (2026-10-18)。
  - キーフレームの受信確認を待つ間を数えない判断は、受信確認が来たことのある iPad だけにする。受信確認を返さない古い iPad アプリでは、記憶しているキーフレームが消えず、見直しがほぼ停止していた。最初の受信確認が来るまでは破棄しないので、最初のキーフレームで破棄したと数えることもない。
  - 配信するディスプレイを切り替えるたびにキャプチャを作り直すので、受信確認を返す iPad かどうかと、下げたビットレートが失われていた。遅い回線では、最初の受信確認を待つ間に送信待ちが積み上がる。同じ映像の接続なら、前のキャプチャから引き継ぐ。
  - 回線の限界付近では、6 秒ごとに 1.25 倍へ上げて輻輳し、下げる、を 8 秒周期で繰り返していた。下げたときに見積もった回線速度の 95% を上限にし、上限までは上げ、超えるのは破棄しないウィンドウが 6 つ (12 秒) 続いたときに 1.1 倍だけ試す。重い映像・iPad のサイズ・10 Mbps で 40 秒流すと、輻輳する回は 20 秒あまりに 1 度になり、それ以外は遅延 56〜66 ms・15 fps で安定した。
- 往復遅延が大きい回線で下げ続けていた (2026-10-18 に修正した)。受信確認を待つフレームを 3 フレームで止めていたので、帯域に余裕があっても毎秒「3 フレーム ÷ 往復遅延」しか送れず (往復遅延 80ms で 37 fps)、残りを破棄した分でビットレートを下げていた。下げても往復遅延は縮まないので破棄する割合は変わらず、下限の 1.5 Mbps まで下がる。
  - ユーザーの iPad (en0) の 2 回の接続 (21:17 と 22:05) は、どちらも外部ディスプレイの上限 8.3 Mbps から 0.6 倍ずつ 5.0、3.0、1.8、1.5 Mbps と下がり、3.7 Mbps まで戻してはまた下限に落ちることを繰り返していた。帯域が足りないなら、下げれば破棄するフレームが減って手前で安定するはずで、下限まで落ちる形は往復遅延かジッターで破棄していたことを示す。初めは「この時間帯の Wi-Fi が 2 Mbps しか出ない」と誤って結論しかけた。
  - 今は、受信確認を待つフレームが 3 フレーム以上でも、直近 0.15 秒 (60fps で 9 フレームほど) の受信確認の往復遅延の最小値が、ベースの往復遅延 (30 秒ごとのウィンドウの最小値) から 50ms 以内なら、輻輳していないとみなして送る (受信確認を待つのは 30 フレームまで)。超えたら、一番古いフレームの受信確認がベースの往復遅延 + 50ms より遅れたときだけ破棄する。Wi-Fi のジッターなら一部の受信確認だけが遅れて最小値は上がらず、回線が輻輳するとどの受信確認も遅れて最小値も上がる。往復遅延の見積もりがないうちは、従来どおり 3 フレームで止める。
  - 本物の `VideoFlowControl` と `BitRateController` を、設定した帯域・往復遅延・ジッター (指数分布) の回線で 60 秒動かして比較した (`VideoLinkSimulationTests`)。帯域 50 Mbps で往復遅延 80ms、120ms、40ms とジッター 20ms、80ms とジッター 30ms のとき、修正前は 4〜6 割を破棄して 1.5 Mbps まで下げたが、今はほぼ破棄せず上限の 14.5 Mbps のまま。帯域が足りない回線では、修正前と同じく帯域まで下げる (10 Mbps で 10.4 Mbps、5 Mbps で 5.2 Mbps)。帯域が足りずジッターもある回線 (10 Mbps と往復遅延 40ms・ジッター 30ms) は、7.9 Mbps で安定して下限まで下げない。
  - 帯域が足りない回線での、送信から受信確認までの遅延は、往復遅延 10ms で平均 43ms から 62ms、最大 52ms から 87ms に増えた (輻輳と判定するまでの 50ms の分)。往復遅延が大きいだけ、ジッターがあるだけの回線を下限まで落とさないためのトレードオフにした。
  - 値の決め方の比較。
    - 初めは、往復遅延を平滑化した平均 (1/8 ずつ混ぜる) で輻輳を判定した。往復遅延だけが大きい回線は解決したが、往復遅延 80ms・ジッター 30ms では 1 割を破棄して下限まで下げた (ジッターによる大きな遅延に平均が引かれる)。直近の最小値に替えると破棄しなくなった。
    - 直近のウィンドウは 0.1 秒だとジッターで全部が遅れたウィンドウを輻輳と判定し (往復遅延 80ms・ジッター 30ms で 3.1 Mbps)、0.2 秒だと輻輳に気づくまでに遅延が積み上がった (帯域 10 Mbps・往復遅延 80ms で最大 216ms)。0.15 秒にした (同じ回線で 208ms)。
    - 輻輳している間に許容する遅延を 30ms・20ms に分けても、遅延は数 ms しか変わらなかったので、値は 1 つにした。ベースの往復遅延を 10 秒のウィンドウで測ると、輻輳している間の値が混ざって膨らみ、遅延が最大 104ms まで延びたので 30 秒にした。
- 本物のエンコーダと Kit の部品を ScreenStreamer と同じ順に組み、受信側が設定した速度でしか読まないループバックで比較した結果 (毎秒届いたフレーム数、遅延の平均)。
  - 100 Mbps の回線: 修正前と同じ (1 フレームも破棄せず、ビットレートも変えない)。
  - 重い映像、iPad のサイズ、10 Mbps: 修正前は 17 fps・遅延 1.8〜2.1 秒で増え続けた。今は 15〜16 fps・57 ms。
  - 重い映像、1920x1080、5 Mbps: 修正前は 15 fps・遅延 2.6〜4.0 秒。今は 12〜13 fps・65〜97 ms。
  - スクロールする軽い映像、iPad のサイズ、10 Mbps: 修正前は 60 fps・10 ms。今は 56 fps・5 ms (大きな 1 フレームを送る間の数フレームを破棄する)。

### 画面が停止したあとの再送 (2026-10-18)

- ScreenCaptureKit は画面が変わらないとフレームを出さないので、次の 4 つは、次に Mac の画面が変わるまで解消しなかった。
  - 回線が輻輳して最後のフレームを破棄したとき。iPad に途中の絵が残り、Mac の画面とずれた見た目のまま操作することになる。
  - 画面が丸ごと切り替わってすぐ停止したとき (アプリの切り替え、ページの読み込み)。1 フレーム分のビット予算で描画した、にじんだ絵のままになる。
  - 画面が停止している間に iPad が要求したキーフレーム (描画できなくなったときの復帰ポイント) が届かない。
  - 拡大したまま表示位置を動かしても、新しい範囲の切り出しが届かない (要求する範囲の余白 15% を超えて動かすと、欠けたまま)。
- キャプチャした最後のフレームを 1 フレーム保持しておき、最後にキャプチャしてから 0.25 秒たったら、0.1 秒ごとに同じ絵を再エンコードして送る (`StillFrameRefresh`)。
  - 再送したフレームが 1000 バイトを下回ったら、描画が完了したとみなしてやめる。出力されたフレームが 8 フレームになったときと、要求したのが 16 回になったときもやめる。停止した画面で送り続けないため。
  - キーフレームや範囲を要求されたら、描画が完了していても 1 回送る。回線が輻輳している間は、回数を消費せずに待つ。
- 測定した値 (本物のエンコーダとデコーダ、文字のような模様、輝度の PSNR)。
  - 1920x1080 で絵が丸ごと切り替わってすぐ停止したとき、上限のビットレート (8.3 Mbps) では、切り替えた時点の 47.1dB が再送で 53.1dB になった。上限の 0.4 倍では、29.2dB が 6 回で 45.5dB になった。
  - 一様にスクロールして停止したときは、上限の 0.4 倍でも停止した時点で 51.4dB あり、再送は 1 回 (570 バイトほど) で停止した。動き補償で少ないビット数で描画できるため。
  - 最初のテストでは、0.4 倍のスクロールでも 42dB から上がって見えた。これは最初のキーフレームの借り (この模様で 300KB ほど。そのあと 1 秒ほどは、レート制御が絵を絞る) を含んでいた。テストは、前の絵を送り終えてから切り替える。
- 再送するフレームの時刻は、キャプチャと同じホストの時計の現在時刻にする (前のフレームより後)。1/60 秒ずつ詰めた時刻にすると、低遅延のレート制御がビット予算を回さず、下げたビットレートでは 24dB のまま上がらなかった。実際の経過どおりに空けると上がった。
- 大きなキーフレームのあとは、レート制御が借りを返すために、再送を 1 回おきに破棄した。そのため、回数は出力されたフレームで数え、要求する回数は別に打ち切る。
- 再送のタイマーはキャプチャと同じキューで動かし、キーフレームの要求もそのキューで予定を入れ直す。ほかのスレッドから入れると、古い「停止」の予定があとから上書きして、要求したキーフレームが届かないことがありうる。
- ScreenCaptureKit のフレームを 1 フレーム保持し続ける (`queueDepth` は 4 なので、キャプチャは止まらない)。停止したら解放する。
- キャプチャしたあとの流れ (破棄・ビットレート・切り出し・エンコード・再送) は、Kit の `VideoSender` に移した。ディスプレイをキャプチャせずに、作成した絵を渡して確認するため。ScreenStreamer は、ScreenCaptureKit のキャプチャと、拡大の有無に合わせたキャプチャサイズの切り替えだけを持つ。
  - 移すときに見つけて修正したこと。キャプチャを作り直すとき、ビットレートの見直しには前の値を引き継いでいたが、エンコーダは上限で作っていた。見直しが値を変えるまで (2 秒) 上限で送るので、遅い回線では輻輳する。640x360 で、上限から始めたときと 1/5 を引き継いだときのフレームのサイズが、修正前はどちらも 12,941 バイトで、修正後は 1/5 の方が 4,688 バイトになった。
  - 移したときに一度、停止したキャプチャから送信側を手放していた。Host は前のキャプチャを停止してから、受信確認の有無とビットレートを読んで引き継ぐので、作り直すたびに最初からになる。HostServer の呼び出しと突き合わせて気づき、停止しても手放さないようにした (停止したあとも読めることは、Kit の単体テストで確認する)。
- 確認したこと (`VideoSenderTests`、`StillFrameRefreshTests`)。受信確認を待つ 3 フレームで破棄した 4 フレーム目が、画面が停止したあとに届く (4 フレーム目と 30dB 以上、3 フレーム目より 10dB 以上近い)。停止した画面で要求したキーフレームと範囲が届く。描画が完了したら再送をやめ、そのあと 0.6 秒増えない。停止したら送らない。ScreenStreamer を通した部分は、ユーザーのディスプレイをキャプチャすることになるので、ビルドまでにしている。
- 別のエージェントに読ませて修正したこと。
  - 再送はホストの現在時刻で送るが、キャプチャしたフレームの時刻は画面に表示された時刻なので、再送の直後に届いたキャプチャの時刻がそれより前になることがあった。受信確認は時刻の順に突き合わせる (`VideoFlowControl`) ので、エンコードに渡す時刻を、前に渡した時刻より 1ms 以上後にそろえる。修正前は、再送より 5ms 前のキャプチャを渡すと、送るフレームの時刻が 5ms 戻ることを単体テストで再現した。
  - キャプチャを開始する途中で拡大の範囲が変わると、古い範囲を送信側へ後から渡して上書きしうる。範囲を記憶するのと渡すのを、同じロックの中で行う。
  - 修正していない指摘。拡大に切り替えた直後の再送は、等倍用の小さいフレームを切り出して引き伸ばしたものになる (iPad が手元で拡大していた絵と同じ細かさで、悪くはならない。元の解像度のフレームが届けば置き換わる)。ScreenCaptureKit のフレームを 1 フレーム保持し続ける (解放すると、停止した画面で要求されたキーフレームと範囲に応えられない)。回線が輻輳している間は 0.1 秒ごとに起動して確認する (受信確認の待ちは 2 秒で打ち切るので、続いても数秒)。
- 映像の停止で Host がデッドロックした (2026-10-20)。使っているうちに iPad が「接続中…」のまま戻らなくなり、Host を再起動すると少しの間だけ直った。
  - Host を `sample` で調べると、サーバーのキューが `VideoSender.stop()` の中で止まっていた。送信側のロックを持ったままエンコーダを破棄していた。破棄 (`VTCompressionSessionInvalidate`) は VideoToolbox 内部のロックを待つ。一方、VideoToolbox はその内部のロックを持ったまま出力を渡し、出力の処理 (`encoded`) は送信側のロックを待っていた。互いに相手のロックを待つ形になる。
  - サーバーのキューが止まると、iPad の再接続も、切断の後始末も処理されない。ログには「接続」のあと何も残らない。ディスプレイの切り替え、映像の張り直し、切断のいずれでも、キャプチャを停止するので起こりうる。
  - 送信側のロックの中ではエンコーダを取り出すだけにして、破棄はロックの外で行う。出力の処理は、停止済みかをロックで確認して何もせずに戻れるので、破棄が完了する。
  - 単体テスト (`stopsWhileEncoderIsOutputting`) は、Host と同じ 2360x1532 の絵を 8ms ごとに渡し、受信確認を返してビットレートの調整を続けさせながら、10 回停止する。修正前は、3 回とも最初の停止で 3 秒たっても戻らなかった。640x400 や、エンコーダの出力の途中で止めて待つだけの形では、修正前も再現しなかった。
  - Host が止まっている間も、接続中かの判定 (`pad-connected.sh`) は、最後の「接続」のログを見て接続中と判定する。止まった Host の入れ替えは、`sample` で止まっていることを確かめてから行った。

## 外部ディスプレイまわりを読み直して修正したこと (2026-10-18)

- 別のエージェントに外部ディスプレイまわりを読ませ、指摘をコードと照合して修正した。
  - 接続した直後のディスプレイは、CoreGraphics に見えても ScreenCaptureKit の一覧に載るまで少しかかり、キャプチャを開始できずにメインディスプレイへフォールバックしていた。そのあとディスプレイ構成の通知が来るまで、選択したディスプレイに戻らなかった。フォールバックしたあと 2 秒おきに 3 回までディスプレイを読み直し、載れば選択したディスプレイに戻す。
  - 最前面のウィンドウを移動するとき、Dock やメニューバーのサイズや自動非表示の設定を変えてもディスプレイ構成の通知は来ないので、使える範囲が古いままで、移動したウィンドウが Dock の下に入りえた。移動する直前に読み直す。
  - アクセシビリティの問い合わせのタイムアウトはアプリの要素にだけ設定していた。タイムアウトは要素ごとなので、ウィンドウの要素にも設定する (応答しないアプリでスレッドが長く塞がらないように)。
  - どのディスプレイにも重ならないウィンドウ (取り外したディスプレイに残ったもの) は移動できなかった。移動先のディスプレイの内側へ寄せて回収する。この計算は単体テストで固めた。
  - アプリ切り替えの直後に「表示するディスプレイ」で選択すると、待機していた「最前面になったウィンドウを追う」処理があとからディスプレイを切り替え直した。手動で選択したら、待機中の処理を取り消す。
  - iPad は選択したディスプレイを先に表示したことにしているので、Mac がすでに表示していたときも現在の一覧を再通知する。
  - ユーザーのディスプレイやウィンドウを動かす確認はしないので、ここまでは単体テストとビルドまで。
  - 修正していない指摘: 最前面になったウィンドウを追って切り替わったディスプレイも記憶すること (README のとおりの設計)。配信中のディスプレイを取り外すと映像の接続が閉じ、iPad が張り直すまで表示されないこと (0.5 秒からの再接続で復帰する)。

## Mac のロック画面 (2026-10-18)

- ロック中に iPad から操作できるかを、ユーザーの Mac をロックせずに一次情報で調べた。
  - Apple の DTS (Quinn) は、ScreenCaptureKit はログイン済みの GUI セッションで使えるので動くはずだが、ロック解除の画面には特別なセキュリティ制限がいくつもあり、それに該当するかもしれない、と答えている ([Apple Developer Forums 756908](https://developer.apple.com/forums/thread/756908))。ログイン前 (pre-login) では ScreenCaptureKit は使えない。
  - 開発者の報告では、ロックされると ScreenCaptureKit はキャプチャを停止し、解除しても自動では復帰しない ([opendisplay #296](https://github.com/peetzweg/opendisplay/issues/296))。ロック中は macOS がキャプチャを拒否する ([claude-human](https://github.com/drkostas/claude-human))。
  - ロック画面にパスワードを入力できている claude-human は、合成したキーイベントではなく、Karabiner の DriverKit の仮想キーボード (root で動くヘルパー) を使っている。合成したイベントが届かない場面でも、本物のキーボードとして扱われるから、としている。ドライバをインストールする設計は採用しない (Mac 全体の状態を変えるため)。
- そこで、ロック中に解除はできないものとして、次の 2 つを行う。
  - Host は loginwindow のロックと解除の通知 (`com.apple.screenIsLocked`・`com.apple.screenIsUnlocked`、分散通知を `deliverImmediately` で受ける) を受け、iPad に `macScreenLocked` で通知する。iPad は「Mac の画面がロックされています」を表示する。iPad が接続した時点のロック状態は、セッション情報 (`CGSessionCopyCurrentDictionary`) の `CGSSessionScreenIsLocked` で読む。ロックされていないこの Mac では、このキーはなかった。
  - 解除されたら、映像の接続があればキャプチャを作り直す。
- iPad の通知は、テスト用の Host が送ったロックと解除で表示されて消えることをシミュレータで確認した。
- Host の監視 (`ScreenLockMonitor.swift`) は、ファイルをそのままコピーして通知の名前だけテスト用の固有の名前に替え、分散通知を停止した状態 (フォアグラウンドにない常駐アプリと同じ) で、別のプロセスから送ったロックと解除がその順に届くことを確認した。本物の名前で送らないのは、ディスプレイのロックに合わせて自分もロックするアプリ (パスワード管理など) にも届くため。名前は、この Mac (macOS 26.2、25C56) の loginwindow の実行ファイルに `com.apple.screenIsLocked` と `com.apple.screenIsUnlocked` の両方が入っていることで確認した。解除での作り直しは、ディスプレイの切り替えやフレームレートの変更と同じ `startStreamer(on:)` を呼ぶ。実際にロックして解除する流れは、ユーザーの Mac をロックすることになるので実行していない。

## 外部ディスプレイ

- 2026-10-18 に「Mac が外部ディスプレイに接続されているときの対応」を求められた。このとき Mac は蓋を閉じて外部ディスプレイ 2 台に接続されていた (メインの VG258 と、その左の 1920x1080)。メインディスプレイしか送信しなかったので、左のディスプレイにあるものは iPad から見ることも操作することもできなかった。
- iPad の「…」に「表示するディスプレイ」を表示し、1 台ずつ選んで配信する。複数のディスプレイをまとめて 1 枚にする方式は採用しなかった。ScreenCaptureKit のフィルタは 1 台のディスプレイしかキャプチャできず、ディスプレイごとのキャプチャを合成することになる。しかも iPad では 2 台分が横に並んで小さくなるので、結局拡大して使うことになる。
- ディスプレイの一覧は Host が読み取って iPad に送る (`ControlMessage.displays`)。並べ方と配置の判定は Kit の `RemoteDisplay` にまとめ、単体テストで固めた。
  - 名前は `NSScreen.localizedName` から読む。この Mac の左のディスプレイは名前が空だったので (`system_profiler` でも「Display」とだけ表示される)、空なら「名称不明のディスプレイ」とし、メインディスプレイから見た配置 (中心どうしのずれが大きい方向) を必ず添えて見分けられるようにした。
  - `NSScreen` はメインスレッドで読む。Host のサーバーは自分のキューで動くので、メインスレッドで一覧を作ってから受け取る。
  - ミラーリングの 2 台目以降 (`CGDisplayMirrorsDisplay` が 0 でない) は同じものが表示されるので除く。
- 選択されたディスプレイは、`CGDisplayCreateUUIDFromDisplayID` の UUID で Host の設定に記憶する。取り外されているあいだはメインディスプレイを配信し、再接続されたらまた選択されたディスプレイを配信する。蓋を開閉して内蔵ディスプレイが出入りしても、外部ディスプレイを選んでいればそれを配信し続ける。
- タッチの位置は、配信中のディスプレイの `CGDisplayBounds` 上の割合として届く。この Mac で、送信する代わりにログに記録するテスト用ビルドに Host の `InputInjector.swift` を入れて確認した (2026-10-18)。左のディスプレイ (-1920, 0, 1920, 1080) の右端 (割合 1) は x=0 になり、メインの左端にあたるので、ポインタが隣のディスプレイへ移ってしまった。映像の外の黒い帯をタッチすると割合は 1 に丸められるので、実際に発生する。そこで右端と下端は、ディスプレイの内側に 1 ポイント入れる (修正後は -1 と 1079)。
- 選び直したときは、ポインタを新しいディスプレイの中央へ動かす。接続したときは動かさない。
  - ディスプレイごとに操作スペースを持つ設定 (この Mac は `com.apple.spaces` の `spans-displays` が 0) では、Mission Control はポインタのあるディスプレイにだけ効く ([MacMost](https://macmost.com/23-tips-for-using-desktop-spaces-on-your-mac.html))。
  - 3 本指のスワイプで合成する Dock のスワイプがどのディスプレイに効くかは、Apple の資料 ([操作スペース](https://support.apple.com/guide/mac-help/work-in-multiple-spaces-mh14112/mac)) に書かれていない。確認するにはユーザーの Mac で操作スペースを切り替えるしかないので、ポインタを配信中のディスプレイに置き、ポインタで決まる場合でも配信中のディスプレイに効くようにした。
- アプリが最前面になったら (`NSWorkspace.didActivateApplicationNotification`)、そのアプリの最前面のウィンドウ (`kAXFocusedWindowAttribute`) の位置を読み、重なりが一番大きいディスプレイが配信中のディスプレイと違えば、そちらを配信する。iPad のアプリ切り替えで選択したアプリが、配信していないディスプレイにあって見えないままになるのを防ぐ。
  - Mac を直接使っている人の操作でも最前面になるので、このときはポインタを動かさない。
  - 最前面のウィンドウがないとき (デスクトップを操作した Finder など) は追わない。別のディスプレイのウィンドウを代わりに選ぶと、操作したディスプレイから離れてしまうため。
  - 位置の読み取り方は、テスト用ビルドで確認した (2026-10-18)。自分の透明でマウスを受けないウィンドウを両方のディスプレイに置き、Host と同じ読み方で読むと、置いた位置 (左のディスプレイの (-1720, 150, 400, 300) と、メインの (200, 150, 400, 300)) がそのまま返り、15 と 16 に割り当たった。最前面にしていないアプリは最前面のウィンドウを持たない (`kAXErrorNoValue`) ので、確認にはウィンドウ一覧から取得したものを使った。`NSApplication` の起動を済ませていないビルドでは、AppKit がアクセシビリティの問い合わせに応答しない (`kAXErrorNotImplemented`)。
- 配信するディスプレイが切り替わったら、iPad の上に「(ディスプレイ名) を表示中」を 2 秒だけ表示する。最前面になったウィンドウを追って Mac が切り替えたときに、操作していないディスプレイが急に切り替わった理由が分かるように。接続したときは表示しない。テスト用の Host から Mac が切り替えた通知を送り、シミュレータで表示されて 2 秒で消えることを確認した (2026-10-18)。
- 一度に配信するのは 1 台なので、ディスプレイをまたいでウィンドウをドラッグできない。代わりに「…」の「最前面のウィンドウを移動」で、最前面のアプリの最前面のウィンドウ (システム全体の `kAXFocusedApplicationAttribute` から) を選択したディスプレイへ移動し、そのディスプレイを表示する。
  - 新しい位置とサイズは Kit の `RemoteDisplay.moved` で決める。元のディスプレイでの寄せ方の割合を保ち、移動先に収まらなければ縮める。範囲は `NSScreen.visibleFrame` (メニューバーと Dock を除く) をディスプレイ座標に変換したもの。サイズを先に変えてから移動する。
  - アプリの「ウインドウ」メニューの「(ディスプレイ名)に移動」を押す方法もあるが、項目の名前が言語やアプリによって違い、持たないアプリもあるので、ウィンドウの位置を直接変更する。
  - テスト用ビルドで、自分の透明なウィンドウを Host と同じ方法で移動して確認した (2026-10-18)。メインの (1020, 368, 800, 532) は左のディスプレイの (-900, 368) へ、左のディスプレイの (-1820, 68, 600, 432) はメインの (100, 68) へ移動した。自分のウィンドウをアクセシビリティで動かすと AppKit が呼び出したスレッドで処理するので、テストではメインスレッドから動かす (別のスレッドからだと AppKit のチェックで停止する。Host が動かすのは別のアプリのウィンドウなので該当しない)。

- 外部ディスプレイの確認の途中で、「…」を開くとソフトウェアキーボードが表示されてメニューを隠すことが分かった (2026-10-18、上と同じシミュレータ)。実機の iPad でも発生していたかは、ユーザーの iPad を操作しないと分からない。

## Mac のサウンドを iPad で再生する

- 初めは「Mac のサウンドは iPad に送らない」を既知の制約にしていた。2026-10-18 に、iPad の「…」から切り替えられる機能として追加した。既定はオフにしてあり、オンにしなければ従来と同じ動作になる。
- Host は、iPad が要求している間だけ、ヘルパーアプリを除く全プロセスの出力をまとめる非公開のプロセスタップ (`CATapDescription(stereoGlobalTapButExcludeProcesses:)`) を作り、タップだけを入力に持つ非公開の機器セットを IOProc で読み取る。
  - `muteBehavior` は `.mutedWhenTapped`。読み取っている間だけ Mac で再生しないので、Host がクラッシュしてタップが残っても Mac のサウンドは消えない。
  - ヘルパーアプリは、iPad の音声と、Mac で直接話すときの Mac のマイクの音声を再生している。除外しないと、Mac で話した声が iPad で再生される。ヘルパーアプリのプロセスのオブジェクトは音声を出し始めるまで現れず、再起動すると変わるので、プロセス一覧が変わるたびに見直してタップを作り直す。macOS 26 の `bundleIDs` で除外する方法もあるが、除外する側のタップでの効き方を確認していないので使っていない。
  - 出力先の機器が変わるとタップの形式 (サンプルレート) も変わるので、`kAudioTapPropertyFormat` が変わっても作り直す。出力デバイスは機器セットに入れず、出力先が変わるたびに作り直さずに済むようにした。
- 送る形式は 48kHz・ステレオ・16 ビット (約 1.5Mbps) で、20ms ごとのチャンクにする。すべて 0 のチャンクは送らないので、何も再生されていない間は通信しない。映像の送信が輻輳しても待たされないよう、操作用の接続で送る。送信待ちが 25 件 (0.5 秒分) を超えたら破棄する。
  - 2026-10-18 から、iPad が要求したらチャンクごとに Opus の 1 パケット (128 kbps、平均 320 バイトほど) にして送る (`macAudioCodec(.opus)` → `macAudioOpus`)。無圧縮の 1.5 Mbps は 5 Mbps の回線の 3 割にあたり、映像の帯域を削るうえ、送信バッファでの遅延も大きくなるため。
    - AudioToolbox の Opus は、1 パケットを 20ms (960 フレーム) にでき、チャンク 1 つを渡すとその場で 1 パケットが出力される。先頭の遅延は 312 フレーム (6.5ms)。AAC-ELD (10ms・先頭 240 フレーム) も作れたが、チャンクの長さと合う Opus にした。AAC-LC は先頭の遅延が 2112 フレーム (44ms) あるので使わない。
    - 要求する形式は、iPad が「再生」を送る前に毎回送る。未知の古い Host は読み飛ばして無圧縮で送り、要求しない古い iPad アプリには Host が無圧縮で送る。iPad は Opus をデコードできないときは無圧縮を要求する。
    - iPad は、切断したときもバッファにためた音声を破棄し、次に接続したときに前の音声が再生されないようにする。デコーダを作り直せなかったときは前のものを使い続ける (Mac にはもう Opus を要求しているので、なくすと無音になる)。
    - 単体テストで、左だけに出力した 440Hz を 1 秒、チャンクごとにエンコードしてデコードし、左の実効値が元と 0.05 以内、右がほぼ無音になることを、macOS と iOS のシミュレータの両方で確認した (iPad でデコードできるかを確認するため)。再生の部品 (`MacAudioPlayer`) にパケットを渡し、手動で回すエンジンで描画した音声も、左の実効値が元と 0.05 以内、右がほぼ無音で、再生を停止して再開したあとも同じだった (macOS と iOS のシミュレータ。`feedOpus` を止めると左が 0 になってテストが失敗することも確認した)。シミュレータのテスト用アプリは、「Opus で」を「再生」の前に送った。音声を流すテストはしない (シミュレータの音声は Mac のスピーカーから出る)。
- iPad は、バックグラウンドに移っても停止されないよう無音を流しているのと同じエンジンに `AVAudioSourceNode` を接続して再生する。awdl のジッターで途切れないよう 100ms 溜まってから再生し、0.5 秒より遅れたら古い音声から破棄する。
- iPad のマイクで音声入力している間は再生しない。iPad のスピーカーの音声をマイクが拾い、Mac のサウンドが Typeless に入るため。
- iPad がバックグラウンドに移っている間は Mac で再生する。接続はバックグラウンドでも続くので、iPad をしまったまま Mac を開くと、Mac が無音のままになるため。
- 2026-10-18 に、iPad が接続していない間に検証用のクライアントで確認した。
  - タップの形式は 48kHz・2ch・Float32 (インターリーブ) で、変換は形式を変えるだけだった。要求してから最初のチャンクが届くまで 0.13 秒。
  - 聞こえない 20kHz・0.01 の音を再生すると、届いた音声の最大は 0.0102 だった。
  - ヘルパーアプリが起動してチェック用の音 (0.01) を 1.5 秒再生している間に、届いたチャンクは 0 だった。ヘルパーアプリは起動から約 0.2 秒で、デバイスを作る前に除外されていた。何も再生されていない間も届かなかった。
  - iPad 側は、AVAudioEngine を手動で回す単体テストで、左右の振り分け、バッファにためてから再生すること、マイクを使っている間は再生しないことを確認した。左右を入れ替えるとテストが失敗することも確認した。
  - iPad のアプリ全体は、画面なしで起動した iOS シミュレータ (iPad Air 11-inch (M4)) で確認した。起動引数 `-playsMacAudio YES` でオンにした状態にすると、接続してすぐ Mac のサウンドを要求した。チェック用の音は 0.5 秒 (約 25 チャンク) しか再生していないのに、停止するまでの約 4.6 秒で 212 チャンクを送った。シミュレータのアプリが再生した音声を Host の全体のタップがまた拾い、ループし続けたためで、受信して再生するところまで動作していると分かる (Mac のスピーカーは読み取っている間はミュートされるので、聞こえない)。
  - 久しぶりに起動した直後のシミュレータで、一度だけ `BackgroundAudio` のエンジンの開始が失敗した (`AURemoteIO::Initialize` でオーディオサーバーへの問い合わせがタイムアウトし、`abort`)。Mac のサウンドを追加する前のビルドと今のビルドを、起動直後のシミュレータで 2 回ずつ実行しても再現しなかったので、変更によるものではない。

### Mac のサウンドと Host の起動を読み直して修正したこと (2 回目、2026-10-18)

- 別のエージェントに Mac のサウンドのキャプチャと Host の起動・許可を読ませ、指摘をコードと照合して修正した。
  - Mac のサウンドのキャプチャを 5 回作り直しても読み取れないとあきらめるが、そのあとも「キャプチャ中」のままで、Host のメニューは「Mac のスピーカーからは再生されません」と表示し続けていた (実際はタップがないので Mac で再生されている)。あきらめたら Host に通知して停止し、表示を戻す。
  - Host は起動のたびに、画面収録とアクセシビリティの許可が足りなければシステム設定を開いていた。ログイン時に起動すると、ログインのたびに最前面に出てくる。起動時は macOS の確認ダイアログだけにし、システム設定はメニューのボタンからだけ開く。
  - メニューの「システムオーディオの録音」とログイン時の起動の表示は、ヘルパーアプリの通知やトグルの操作でしか変わらず、システム設定で変更しても古いままだった。ほかの許可と一緒に 3 秒ごとに読み直す。録音の許可の読み取り (`AudioCapturePermission`、TCC の関数) はヘルパーアプリから Kit に移して、Host でも使う。ヘルパーアプリは Host の中から起動されるので、同じ Host の許可として扱われる。
  - IOProc はキャプチャした音声のコピーを処理のキューへ送るが、キューが滞留するとコピーが際限なく溜まっていた。処理を待っているコピーを数え、50 (約 0.5 秒分) 以上なら複製せずに破棄する。同じ書き方の小さなプログラムで、キューを停止して 1,000 回送ると溜まる数が 50 で止まり (950 を破棄する)、停止を解除すると 50 をすべて処理して 0 に戻ることを確認した。
  - 修正していない指摘: ヘルパーアプリが音声を出し始めてから、除外するプロセスに入るまでの短い間に、その音声が iPad に混ざりうること (ヘルパーアプリのプロセスは音声を出し始めるまで現れないので、作り直すまで待つしかない)。

### Mac のサウンドとヘルパーアプリの音声の経路を読み直して修正したこと

- 2026-10-18 に、別のエージェントに Mac のサウンドとヘルパーアプリの音声の経路を読ませ、指摘をコードと照合して修正した。
- 浮動小数点の音声を 16 ビットに変換するとき、`min(max(x, -1), 1)` は NaN をそのまま通し、`Int16(NaN)` で実行時にクラッシュする。Host は Mac のすべてのアプリの音声を読むので、どこかのアプリが NaN を出力すると Host がクラッシュする。ヘルパーアプリが Mac のマイクの音声を流す部分も同じ。`PadAudio.int16` で NaN を無音にした。クラッシュすることは単独のビルドで確認し (`Fatal error: Float value cannot be converted to Int16 because it is either infinite or NaN`)、ガードを外すと単体テストが同じ理由で失敗することも確認した。
- 通信が輻輳して一度に届くと、バッファが 0.5 秒分であふれる。古い音声を 1 つずつ破棄していたので、そのあと送信速度と再生速度が同じなら 0.5 秒遅れたままだった。Mac のサウンドだけ、あふれたら再生開始のしきい値 (100ms) まで一気に減らす。iPad の音声は Typeless に全部聞かせたいので、従来どおり 1 つずつ破棄する。
- オフにしたあとやバックグラウンドに移ったあとも、送信途中の音声 (最大 25 チャンク、0.5 秒分) が届き、溜まると再生されていた。再生する設定のときだけ受信する。
- 出力先を切り替えた直後などに作り直しが失敗すると、キャプチャは動かないまま、Mac のスピーカーにも iPad にも音が出なくなる (切り替えも直らない)。2 秒おきに 5 回まで作り直す。作り直しを確認するにはキャプチャを実際に失敗させる必要があり、この Mac でキャプチャを作ると Mac のサウンドが再生されなくなるので、ビルドまでにしている。
- 修正していない指摘: 何も再生されていないチャンクを送らないので短い無音が縮む (設計どおり、通信量を優先)。IOProc のスレッドでメモリを確保している (今のところ途切れは発生していない)。ヘルパーアプリが許可の確認で 1.5 秒停止する間のチェック音の混入 (許可が操作中に付与された場合に限る)。

## タッチの変換

- 指の操作は UIKit のジェスチャー認識を並べず、`TouchInterpreter` という 1 つの状態機械で判定する。認識器を並べていた頃、実機で次の 2 つが発生した。
  - `isMultipleTouchEnabled` が既定の false のままで 2 本目の指が届かず、2 本指スクロールが成立しなかった。
  - 長押しの成立と同時に右クリックしていたため、「押して少し待ってからドラッグ」が右クリックになった。
- ユーザーの指摘で、長押しせずにスワイプする操作はドラッグではなくスクロールにした (iPad の通常の操作に合わせた)。ドラッグは長押ししてから動かす。
  - 指を離したあとの慣性スクロール (`ScrollMomentum`、1 秒に 4% まで減速) は、2026-10-18 に「スクロールの感度が高すぎる。まともに操作できん。最初の動作に戻せ」と言われて取り除いた。指を動かした分だけ動かす量 (映像の幅に対する割合を Mac のディスプレイのサイズに掛ける) は最初から変わっておらず、最初の動作との違いは慣性だけだった。慣性は頼まれずに追加したもので、スワイプするたびに離したあとも流れる (2000 pt/秒で弾くと数百 pt)。映像は Mac から遅れて届くので、見えている位置より先まで流れて、思った位置で止められない (このときはビットレートを 1.8 Mbps まで下げていた。回線の遅さではなく、上の「往復遅延が大きい回線で下げ続けていた」破棄の誤りによる)。Host が作るホイールのイベントは「連続」の扱いで、ピクセルの値がそのままポイントの量になり、Mac 側で増幅されることはない (送信せずに作ったイベントのフィールドを読んで確認した)。
  - 慣性を取り除いたあとも「スクロール治ってねぇ」と言われ、ユーザーが原因は Mac で動作している LinearMouse だと突き止めた (2026-10-18)。Host が `.cghidEventTap` に送るホイールのイベントにも、LinearMouse のスクロール速度と加速がかかる。指を動かした分だけ動かす計算は最初から変わっていなかった。
- トラックパッドやマウスのクリック (`UITouch.type == .indirectPointer`) は状態機械を通さず、押下と解放をそのまま送る。マウスのつもりで長押しして右クリックになるのを防ぐため。
- 入力の経路を別のエージェントに読ませて修正したこと (2026-10-18)。
  - 2 本指でしばらくスクロールしてから親指や手のひらが触れると、3 本指のスワイプ (Mission Control や操作スペースの切り替え) になっていた。スクロールの開始から 0.25 秒を過ぎて触れた 3 本目は無視してスクロールを続ける。指をずらして置く人の 3 本指のスワイプ (1 本目が動き出した直後に残りの指が触れる) は従来どおり。修正前の動作にすると単体テストが失敗することを確認した。
  - ペンやマウスのボタンを押している間に触れた指や手のひらを、離すまで無視する。押したままのボタンに、指の位置への移動やクリックが割り込んでいた。UI テストからはペンと指を同時に触れさせられないので、ビルドまで。
  - 押したままのキーを離すよう Mac に依頼するのを、バックグラウンドに移ったときだけでなく、フォアグラウンドのままファーストレスポンダを失ったとき (`.inactive`: コントロールセンター、Spotlight など) にもする。キーの解放がこのアプリに届かず、⌘ が Mac に残ると、以降のキーがすべてショートカットになる。シミュレータの UI テストからはコントロールセンターも Siri も表示できなかったので、ホームに戻るとき (active → inactive → background) に、inactive でも依頼が届くことで確認した。
  - テキストの挿入を、値か選択位置のどちらかが変われば成功とみなす。選択した文字を同じ文字で置き換えると値が変わらず、失敗とみなして入力し直し、二重に入力されていた。試すとユーザーが使っているアプリの入力欄に文字が入るので、ビルドまで。
  - 押したキーを、Host のログ (debug) に中身ごと出力していた。パスワードも入力するので出力しない。
  - 受信した位置 (`NormalizedPoint`) も 0〜1 に丸める。iPad は送信前に丸めているが、範囲外の値が届くと Mac は隣のディスプレイの見えない位置を押す。
  - 修正していない指摘: キーボードを表示したまま回転すると、キーボードの位置が回転前のサイズで計算されうること (回転するとキーボードの位置の通知も届き直す)。ディスプレイを切り替えた直後の一瞬、前のディスプレイの縦横比でタッチした位置を変換しうること (新しいディスプレイの形式が届けば直る)。
- トラックパッドやマウスを使うと、iPadOS の丸いポインタと、映像に描画された Mac のポインタが両方見えていた。Mac のディスプレイの上では iPadOS のポインタを隠す (`UIPointerInteraction` で `UIPointerStyle.hidden()`)。形 (I ビーム・手など) は Mac 側にしかないため。上下や左右の黒い帯と、拡大した映像がキーボードの下に回り込んだ部分では、iPadOS のポインタを表示する。映像を配信していない間 (接続した直後、ディスプレイの切り替えや映像の張り直しの間) も表示する (2026-10-18)。
  - 映像が届く前は、映像の範囲がディスプレイ全体として計算される (サイズが分からないので画面いっぱいに置く)。範囲だけで決めていたので、Mac のポインタがまだ見えないのに iPadOS のポインタも消えていた (別のエージェントの指摘)。iPad のセッションに「映像を表示しているか」を持たせ、映像の形式が届いたら true にし、映像の接続を張り直す・停止するときに false に戻す。
  - UI テストの `hover()` はホバーのイベントを作るだけで (ダミーの Host に届いた位置は、重ねた位置によらず左上の 1 点だった)、ポインタの範囲を問い合わせる処理は呼ばれない。シミュレータで iPadOS のポインタを動かすには Mac のマウスをキャプチャする設定が必要で、ユーザーのポインタを奪うので使わない。代わりに、テスト用アプリのコピーの中で範囲の要求 (`UIPointerRegionRequest`) を作って位置を入れ、本物の画面のレイアウトで委譲先に渡した。映像があると中央は映像の範囲 (1180x820 の画面で y=78〜742) を返して形は `hidden`、上下の帯は範囲なし。映像が来ないテスト用の Host では、中央も範囲なしだった。実機のポインタでは試していない。
- Apple Pencil (`.pencil`) も同じく、押下と解放をそのまま送る (2026-10-18)。初めは指と同じ状態機械を通しており、触れて動かすとスクロールになり、文字の範囲選択や描画操作には長押しが必要だった。Sidecar も Pencil はクリックとドラッグで、指はスクロールなので、それに合わせた。クリックの回数は Host の `ClickCounter` が数えるので、続けて触れるとダブルクリックになる。
- Typeless ボタンは UIKit の `UIButton` にしている。SwiftUI の `GestureState` は、システムに押下を奪われたキャンセルと指を離したことを区別できないため。キャンセルされたときは、押しっぱなしに切り替えて音声入力を続ける。
- 合成したクリックには macOS がクリック回数を付けてくれないので、`ClickCounter` で自前で数える。
- 修飾キーを単体で送るときは、イベントの種類を `flagsChanged` にしないと、アプリが Command などを認識しない。
- 合成するキーイベントのフラグは、実際の Mac のキーボードに合わせる (`KeyboardMapping.eventFlags`)。
  - 矢印キーには Fn (`0x800000`) とテンキー (`0x200000`) のビットを付ける。この Mac の Mission Control のショートカットは、修飾キー `0x240000` (Control+テンキー) で登録されていて、テンキーのビットがない Control+↑ には反応しない。
  - Home・End・F キーなどには Fn のビットを、修飾キーには左右を区別するビットを付ける。
- 2 本指で広げたり縮めたりすると、iPad の上で Mac のディスプレイを拡大する (`ScreenZoom`、5 倍まで)。Mac の文字は iPad では小さいため。
  - 2 本指の間隔の変化が 24pt を超え、かつ中心の移動より大きいときだけ拡大とみなす。それ以外は従来どおりスクロール。いったんスクロールと決まったら、途中で拡大には変えない。
  - 指の中心の下にある映像の位置が動かないよう拡大し、指が動いた分だけずらす。映像がディスプレイより大きい方向では、端に余白が出ないよう押さえる。1.05 倍まで縮めたら等倍に戻す。
  - タップやスクロールは、拡大した映像の位置を基準に Mac の座標へ変換する。シミュレータで 2 倍のピンチ 1 回分を流し込み、映像の位置 (-790,-410、2360x1640) とタップの座標 (中央 0.585, 0.500、右寄り 0.710, 0.500) が計算どおりになることを確認した (2026-10-17)。
  - XCUITest の `pinch` は、2 本の指を 4pt ほどの間隔から 28pt ほどまでしか広げず、実際の指の動きと違う。判定は単体テストで、画面への反映は動作を直接流し込んで確認する。
  - 拡大しても文字がぼやけないよう、拡大が 0.2 秒落ち着いたら、見えている範囲 (余白 15%、ディスプレイと同じ縦横比、1/128 刻み) を Mac に要求する (`VideoRegion`)。Mac は拡大している間だけディスプレイを元の解像度でキャプチャし、その範囲を切り出して iPad の解像度で送る。映像のサイズは変わらないので、エンコードをやり直さずに済む。
    - 切り出しは `VTPixelTransferSession` で行う。切り出す範囲を直接指定する項目はなく、元のフレームに clean aperture を付けて `kVTScalingMode_CropSourceToCleanAperture` で使わせる。範囲はディスプレイの中心からのずれで、右と下が正。四隅を塗り分けたフレームで確認した (2026-10-17)。
    - フレームごとに写っている範囲を付けて送り、iPad はそのとおりの位置に置く。キャプチャの設定を変更している途中のフレームも、その範囲で正しく配置できる。タッチの座標はディスプレイ全体を基準に変換するので、切り出しとは関係なく変わらない。
    - 本物の ScreenStreamer をループバックで接続して確認した。範囲を変えると、その範囲を付けたフレームがキーフレームから届き、映像のサイズは 2360x1532 のまま変わらなかった。iPad 側は、範囲付きのフレームが届いたときの配置と、2 倍に拡大したときに要求する範囲が計算どおりになることをシミュレータで確認した。
- 3 本指でスワイプすると、トラックパッドと同じ操作をする。iPadOS の 4・5 本指のジェスチャーとぶつからないよう、3 本指にしている。
  - 左右は操作スペースの切り替え。トラックパッドが出すのと同じ Dock スワイプのイベント (種類 30、HID 種別 23) を、開始・途中・終了の 3 つ合成して切り替える。フィールドの番号と値は [InstantSpaceSwitcher](https://github.com/jurplel/InstantSpaceSwitcher) (MIT) の macOS 26 以前向けの実装に合わせた。macOS 27 では追加のフィールドが必要になる。
    - 最初は Control+←/→ を送っていて、2026-10-17 18:23 に「3 本指スワイプで画面が動かない」と報告された。Dock のログでは、このとき切り替えは発生していない。原因は、ユーザーが使っていた Host が、矢印キーに Fn とテンキーのビットを付ける修正の前のビルドのまま動いていたこと (iPad アプリだけ更新して Host を再起動していなかった)。修正後の Host では、18:39 にバーの ⌃+→/← でも約 1 秒かけてスペースが移ることを Dock のログで確認した。
    - それでも Dock スワイプのままにしているのは、切り替えが 0.05〜0.17 秒と速く、ショートカットの設定にも左右されないため。
    - 教訓: Host と iPad アプリの片方だけを更新すると、古い側の動作を見て誤った原因を推定してしまう。変更をデプロイしたら、ユーザーが使っている Host も必ず更新する。
  - 上は Mission Control、下はアプリケーションウインドウ。この 2 つは登録値 (`[65535, 126/125, 2359296]`) があり、Control+↑/↓ で動作することを確認したので、ショートカットのまま送る。
- Dock は、iPad で Dock を表示するのと同じく、ディスプレイの下端 (24pt 以内) から上へ 30pt スワイプすると表示する。
  - この Mac は Dock を自動的に隠している。カーソルをディスプレイの下端に置けば表示されるが、指のタップはクリックになり、カーソルを下端に置いたままにする操作がない。「Dock にアクセスできない」と報告された (2026-10-17)。
  - 表示するのには「Dock にフォーカスを移動」のショートカット (登録値 8、`[65535, 99, 262144]` = Control+F3、有効) を送る。Mission Control の Control+↑ と同じシステムのショートカットの仕組みで動作する。
    - Control+F3 は、自動的に隠している Dock も表示する ([macmost](https://macmost.com/using-the-mac-dock-with-only-your-keyboard.html))。
    - SDK の `NSEvent.h` では、Fn のビット (`1 << 23`) は「いずれかのファンクションキーが押されている」ときに付く。実際のキーボードで Control+F3 を押したときと同じく、合成する F3 にも Fn のビットを付けている。
  - 下端の近くでも、タップと横方向のスワイプはいつもどおりクリックとスクロールにする。キーボードを表示してビューが縮んでいる間は、ビューの下端がディスプレイの下端ではないので受け付けない。
- 合成したキーの押下は macOS がリピートしてくれない。そのため、iPad のハードウェアキーボードで ⌫ や矢印を押し続けても 1 回しか効かなかった。Mac 側で、押されたまま離されていないキーを、Mac のキーリピートの設定 (`NSEvent.keyRepeatDelay`・`keyRepeatInterval`) どおりに繰り返す (`KeyRepeat`)。実際のキーボードと同じく、最後に押したキーだけを繰り返し、リピートのイベントには自動リピートの印 (`keyboardEventAutorepeat`) を付ける。
  - この Mac の値は、リピート開始まで 0.25 秒、間隔 0.033 秒だった。Host と同じ手順で ⌫ のリピートのイベントを作り (送信せずに) 調べた。AppKit からは、押し続けによる入力 (`isARepeat` が true) で、文字は U+007F に見える。
- ハードウェアキーボードの Command+Tab は iPadOS が先に受け取るので、バーのボタンで代替する。タップのたびに Command を押したまま Tab を送り、1 秒タップがなければ Command を離して確定する。
- Mac 側は押されている修飾キーを記憶しておき (`HeldModifiers`)、クリック・ドラッグ・スクロールのイベントにも載せる。載せないと、ハードウェアキーボードの ⌘ を押しながらタップしても ⌘クリックにならない。
- バーの修飾キー (`ModifierLatch`) は、押すと次の 1 回にだけ効き、続けて 2 回押すと固定される。クリックやドラッグには `PointerModifierHold` で、押す前に修飾キーを押し、離したあとで離す。
- 直接入力では、英数字と空白はキーとして送り、記号は文字として挿入する。記号は Mac 側の配列 (US と JIS) でキーの位置が違うので、キーで送ると別の記号になる。
  - ただし、どちらの配列でも同じ位置にある - , . / (と Shift の ! ?) はキーとして送る。この Mac の ABC 配列でキーコードを変換し、それぞれ - , . / ! ? になることを確認した。macOS のローマ字入力の規則 (`CoreJapaneseEngine.framework` の `RomajiRule_Default.txt`) では、- は「ー」になる。文字として挿入すると Mac の日本語入力を通らず、かなモードでも「ー」「、」「。」にならない (「伸ばし棒が打てない」と報告された、2026-10-17)。
  - 英字配列のキーボードでは - が記号の面にしかないので、キーボード上部のバーに「ー」(- のキー) を置いた。
- キーボード上部のバーは、横にスクロールできる `UIScrollView` の中にある。既定 (`delaysContentTouches`) では、スクロールかどうかを見極める間キーの押下が遅延する。そのため、短く押すと押した表示がほとんど出ず、「押した感覚がない」と言われた (2026-10-17)。押下はすぐに届くようにし、押している間は色とサイズを変え、キーボードのクリック音 (`playInputClick`) も再生する。iPad には触覚フィードバックの仕組みがないので、振動は使えない。
  - 押下をすぐに届けると、バーを横へスクロールしようとキーの上から触れただけで、押した瞬間のキーが送られてしまう (シミュレータで確認した)。そのため、キーを送るのは指を離したとき (押し続けたら 0.4 秒後からリピート) にし、押した瞬間は表示と音だけにする。横へスクロールするとタッチは取り消されるので、キーは送られない。
- ソフトウェアキーボードの削除キーを押し続けても、1 回しか消えなかった (2026-10-17 の報告)。直接入力の受け口が `UIKeyInput` だけだと、キーボードが削除をリピートしないため。`hasText` を常に true にしても変わらない。
  - 画面を出さないシミュレータ (iOS 26.5) で、本体とは別のテスト用アプリを使い、削除キーを 3 秒押し続けて確認した (2026-10-17)。`UIKeyInput` だけの受け口では `deleteBackward` は 1 回だった。`UITextInput` を備えて中身の変わらないドキュメントを見せると 25 回で、どれも 1 文字分の `deleteBackward` だった。隠した `UITextView` にセンチネルの文字を入れる方式も試した。こちらもリピートするが、途中から単語単位でまとめて削除するので、Mac へ送る削除の数に変換する手間が必要になる。
  - そこで、受け口に `UITextInput` を追加し、ドキュメントは保持せずに常に同じものを見せる。`editingInteractionConfiguration` は `.none` にして、iPadOS の 3 本指の編集ジェスチャーが Mac のデスクトップ切り替えとぶつからないようにする。
  - 見せるドキュメントは改行の繰り返しにする。最初に試した「a 」の繰り返しでは、キーボードが末尾を単語と空白とみなした。そのため空白を 2 回入力すると、ドキュメントの空白をピリオドに置き換えようとした (`replace`)。改行だけのドキュメントでは、入力したとおりの `insertText` と `deleteBackward` しか届かないことを、同じシミュレータで確認した。
- iPad のキーボードは英字配列に固定し、日本語は Mac 側の日本語入力で変換する。iPad 側で変換して文字を送る入力欄は、操作が二重になるのでやめた。iPad のソフトウェアキーボードには Mac の日本語入力を切り替えるキーがないので、キーボード上部のバーに JIS キーボードの英数・かなを置いている。

### 入力の層を読み直して修正したこと

- 2026-10-18 に、別のエージェントに入力の層 (タッチの変換、拡大、キーボード、テキストの挿入) を読ませ、指摘を単体テストやシミュレータで再現してから修正した。
- 長押しでドラッグしている間に、別の指 (手のひらやディスプレイの端のシステムのジェスチャー) だけが取り消されると、判定をやめていた。ドラッグしている指を離しても左ボタンを離さず、Mac で押されたまま残る (以後の移動がすべてドラッグになる)。単体テストで再現し、ドラッグしている指でない指が取り消されたときはドラッグを続けるようにした。
- 指を大きく開いた位置から始めたピンチは、1 回ごとの倍率が小さく (指の間隔が約 480pt を超えると 1.05 未満)、等倍に戻す判定に毎回かかって拡大が始まらなかった。2% ずつ 10 回広げても等倍のままだったのを単体テストで再現した。等倍に戻すのは縮めているときだけにした。
- キーボード上部のバーで ⇧ を 1 回だけ効かせて ← を押し続けると、最初の 1 回でラッチが外れ、リピートは修飾キーなしの ← になって選択が解除されていた。シミュレータで、修正前は 16 回中 1 回だけ ⇧ 付き、修正後は 16 回とも ⇧ 付きだった。押し始めに効いていた修飾キーを記憶してリピートにも使う。
- iPadOS に取られて解放の通知が届かなかったキーがあると、Host は離すまでリピートし続ける。リピートは 30 秒で打ち切る。iPad はバックグラウンドに移るときに `releaseHeldInput` を送り、Host は押したままのキーとボタンを離す (Typeless は止めない)。
  - 最初は映像の接続が閉じたら離していた。映像の接続は、キャプチャの失敗や iPad の張り直しのように、iPad がフォアグラウンドのまま閉じることもあり、ドラッグや ⌘ を押している途中で Mac 側だけが離れてしまう (今日の変更をまとめて読み直させたときの指摘)。バックグラウンドに移ったことを iPad から通知するようにした。シミュレータでホームに戻すと、テスト用の Host に `releaseHeldInput` が届いた。テスト用ビルドで、打ち切り (ビルドでは 1 秒に縮めた) のあと押下が出ないこと、離す処理で左ボタン・←・⇧ が離されることを確認した。
- 拡大している間にキーボードの表示と非表示や回転で表示範囲が変わっても、見えている範囲を要求し直していなかった (縁が黒くなりうる)。表示範囲が変わったら要求し直す。
- テキストの挿入のアクセシビリティの問い合わせにタイムアウトがなく、応答しないアプリで入力のキュー (マウス・キー) ごと何秒も停止しえた。0.5 秒にした。
- 再接続したときに、iPad がクリックに付ける修飾キーを押したつもりのまま残していた。切断されたら忘れる。
- 今日の変更をまとめて別のエージェントに読み直させ、次の取りこぼしを修正した。
  - 「操作一覧」を表示している間に押したキーは送らないようにしたが、⌘ との組み合わせは優先して受け取ると宣言したショートカットの動作に回り、Mac に届いていた (シミュレータで ⌘W が届いた)。宣言した動作の側でも、上に何かを表示している間は送らない。
  - 少しだけ広げた途中で、指を動かすだけの更新 (倍率 1) が来ると等倍に戻っていた。広げているか動かすだけのときは戻さない。
  - Host を停止したあとでも、リスナーの作り直しの予約が残っていると作り直していた (「再起動」で新旧が Bonjour の名前を取り合う)。停止したあとは作り直さない。作り直しでリスナーを作れなかったときも、もう一度作り直す。
- 修正していない指摘: キーと文字の挿入 (記号や日本語) が混じった一度の入力で、アクセシビリティの挿入がキーより先に反映されうること (通常の入力速度では発生しない。キーとアクセシビリティは経路が別で、順序を揃えるには挿入の実装を変える必要がある)。Electron 系のアプリで挿入の反映が遅れたときに二重に入力されうること (今のところ二重入力は報告されていない)。ペンでドラッグ中に手のひらがタップになったとき。Caps Lock の切り替え。

## 画面の構成

- 最初は画面下に、キー・修飾キー・入力欄・送信・Typeless などのボタンを 1 列に並べていた。使う頻度も場面も違うものが同じ重さで並び、Mac のディスプレイも狭くなるので、ユーザーから強く否定された (2026-10-17)。
- 今は使う場面ごとに配置を分けている。
  - Mac のディスプレイは全面に表示する。
  - いつでも使うもの (Enter・Typeless・キーボード・アプリ切り替え・切断) は、隅に浮かぶ小さな操作パネルにまとめる。
    - Enter は、Typeless で話したあとにキーボードを表示せずに送れるよう、パネルの先頭に置いた (ユーザーの要望、2026-10-17)。
    - アプリ切り替えのアイコンは、最初の `square.on.square` がコピーのボタンに見えると言われたので、`rectangle.2.swap` にした。
  - パネルのボタンでキーボードを閉じると、キーボードは消えるが、Mac のディスプレイの表示領域が縮んだまま戻らないと報告された (2026-10-17)。OS のキーボードを閉じるキーでは戻る。
    - ファーストレスポンダを外すのが SwiftUI の更新 (`updateUIView`) の途中だからと考え、ファーストレスポンダの付け外しを `DispatchQueue.main.async` で更新のあとへ回した。
    - ところが、画面を出さないシミュレータ (iPad Air 11 インチ、iOS 26.5、実機と同じ 820x1180pt) で本物の画面をビルドして確認すると、元のコードでも SwiftUI の余白は戻った (縦 1180 → 829 → 1180)。
    - 映像の範囲を UIKit の `keyboardLayoutGuide` から決めるように変更して調べた。すると、パネルのボタンで閉じたあと、ガイドはキーボード上部のバーの高さ 52pt を残したまま (1128) 戻らなかった。同じときのキーボードの通知 (`keyboardWillHide` など) は、正しくディスプレイの外 (上端 1180) を通知していた。キーボード上部のバー (`inputAccessoryView`) を付けた入力欄をプログラムから外すと、キーボードの位置の追跡にこの食い違いが残る。実機の SwiftUI の余白が戻らなかったのも、これと同じとみている。
    - そこで、Mac のディスプレイのビューはキーボードの余白を無視して全面に置き、映像の範囲はキーボードの通知が示す位置から自分で決める。シミュレータで、横・縦とも表示と非表示を 3 回ずつ繰り返し、閉じるたびに全面に戻ることを確認した (横 820 → 346 → 820、縦 1180 → 791 → 1180)。
  - この変更で、`updateUIView` の中で `isActive` を読まず、後で実行される処理の中でだけ読むようにしてしまった。SwiftUI は読み取られた値にしか依存を記録しないので、ボタンで切り替えても `updateUIView` が呼ばれず、**キーボードがまったく表示されなくなった**。
    - 「キーボードが出なくなった」と報告された (2026-10-17)。本物の画面をビルドしたシミュレータで、開く操作 3 回がすべて失敗することを再現した。
    - `updateUIView` の中で値を読んで後の処理へ渡すように修正した。そのあと、横向き・縦向きとも開く・閉じるを 3 回ずつ繰り返し、高さが戻ることを確認した (横 820 → 346 → 820、縦 1180 → 791 → 1180)。
    - 最初に作った簡略な再現では発生しなかった。親の画面がボタンの文字のために同じ値を読んでいて、依存が記録されていたため。再現は本物の画面で行う。
  - シミュレータでは、OS の「キーボードを非表示」を一度押すと、そのあとはどの入力欄を有効にしてもキーボード本体が画面の外に置かれたままになった。通常の `UITextField` をタップしても、`reloadInputViews` を呼んでも戻らない。実機の iPad では、キーボードを隠したあとに入力欄をタップすれば表示されるので、シミュレータ側の現象とみている。
  - キーを入力するときだけ使うもの (esc・Tab・修飾キー・矢印・英数/かな) は、キーボード上部のバー (`inputAccessoryView`) に表示する。
  - iPhone では、縦向きは操作パネルが下の黒い帯に収まる。横向きは Mac のディスプレイ (16:9) の左右に約 80pt の帯ができるが、横長のパネル (約 250pt) は入らず、Mac のディスプレイの隅に重なる。パネルを縦に並べて帯に入れる案は見送った (2026-10-18)。帯のうち約 62pt は Dynamic Island 側の安全領域で、縦に並べたパネル (約 248pt) はその側では Dynamic Island に隠れる。パネルはドラッグで隅を切り替えられる。iPhone 17 のシミュレータとテスト用の Host で、横向き・縦向きとメニューを撮影して確認した。
- iPad から送るキーの並び (`RemoteKeys`・`AppSwitcher`) と、Mac で合成するキーの種類とフラグ (`MacKeyEvent`) は Kit にまとめ、単体テストで固めている。実際の端末を操作するテストは、ユーザーの作業を乗っ取るので実行しない。
- Mission Control の開閉は、Dock 自身のログ (`com.apple.dock:missioncontrol` の mode の変化) で確認できる。

## iPad の画面の部品を読み直して修正したこと (2026-10-18)

別のエージェントに、操作パネル・キーボード上部のバー・直接入力・Typeless ボタン・画面の表示を読ませ、指摘をシミュレータのテスト用アプリ (本物の iPad の画面のファイルと、127.0.0.1 でだけ待ち受けるテスト用の Host) で確認した。

- 名前の変わった Mac を追って再接続すると (`followRenamedHost`)、セッションが nil を挟まずに切り替わり、SwiftUI は `SessionView` を作り直さなかった。映像のレイヤーと、`weak` で捕捉した入力 (タッチ・キー・Typeless ボタン) が前のセッションのまま残り、前の接続の最後の絵が表示されたまま、タッチしても何も届かない。
  - テスト用アプリを起動して 10 秒後に同じ接続先へ再接続させ、テスト用の Host が映像の接続ごとに番号を書いた絵を送るようにして確認した。修正前は、差し替えたあとも「映像 1」が表示され、タップは入力のクロージャの中でセッションが nil になって破棄された。`makeUIView` は差し替えたあと 1 度も呼ばれなかった。
  - `SessionView` にセッションの識別子 (`.id(ObjectIdentifier(session))`) を付けた。修正後は「映像 2」が表示され、差し替えの前と後のタップがどちらもテスト用の Host に届いた。前のセッションが残っている間に新しいセッションを作るのでアドレスは重ならず、切断してから選び直すときは一覧を挟むので、識別子が同じになって作り直さないことはない。
- ソフトウェアキーボードを閉じるとファーストレスポンダがなくなり、画面にタッチするまでハードウェアキーボードのキーが破棄された。修正前は、閉じたあとに押した c がアプリには届くが Mac へは送られなかった (ファーストレスポンダ「なし」)。直接入力を終えた通知で画面がファーストレスポンダに戻るようにし、c が届くことと、戻ったときにソフトウェアキーボードが表示されないことを確認した。シートを表示している間と、直接入力を続けている間は戻らない。
- キーボードを開いたまま「操作一覧」などのシートを表示すると、ファーストレスポンダは直接入力のまま残り、シートの裏で押したキーが Mac に届いた (画面側にはシートの間は送らない判定があったが、直接入力の側になかった)。シートを閉じようと押した esc も Mac に届く。押したキーと、ソフトウェアキーボードの文字・削除・ペーストは送らないようにした。離したキーは、シートを表示する前に押していたキーを押しっぱなしにしないよう、画面側と同じく送る (押していないキーを離した通知は、Mac では何も起こさない)。
- 操作パネルのドラッグをシステムに奪われると、SwiftUI は `onEnded` を呼ばず、ずらした位置に残る。ドラッグ中かを `@GestureState` で持ち、終わったのにずれが残っていたら元の隅へ戻す。奪われる場面は UI テストから起こせないので、通常どおり離したときに隅へ吸着し、戻すと元の位置 (1068, 759) にぴったり戻ることを確認した。
- 指摘されたが修正しなかったこと。
  - 音声入力中に切断すると、Typeless ボタンの声の輪の `CADisplayLink` がボタンを保持したまま残る、という指摘。テスト用の Host から音声入力中の通知を送り (iPad のマイクは開始させない)、切断すると、更新は停止しボタンも解放された。SwiftUI は部品を外すとき、部品の最外のビュー (このボタン) の `removeFromSuperview` を呼ぶ。
  - ほかのアプリのキーボードの通知でも映像の領域が縮む、という指摘。Split View や Stage Manager でも、キーボードは画面の下に全幅で表示され、このアプリのウィンドウも隠す。隠れた部分に Mac のディスプレイを描画しないよう縮めるのは正しく、タッチの位置も同じ領域から変換するのでずれない。画面に表示されるキーボードは 1 つなので、自分のキーボードを表示している間に、ほかのアプリの「隠れる」が届くこともない。

## Swift 6 とオーディオのスレッド

- アプリのターゲットは既定でメインアクターに属する (`SWIFT_DEFAULT_ACTOR_ISOLATION: MainActor`)。メインアクターのメソッドの中で書いた処理 (クロージャ) もメインアクターに属するとみなされる。
- それを AVFAudio の `installTap` に渡すと、AVFAudio が自分のスレッドから呼んだ時点で、Swift の実行時チェック (`dispatch_assert_queue`) に引っかかってアプリがクラッシュする。「マイクボタンを押したらクラッシュする」と報告された (2026-10-17)。
- オーディオのスレッドから呼ばれる処理は、`nonisolated` な場所 (静的メソッドや `nonisolated` なクラス) で作る。シミュレータで、修正前のコードでは Typeless のボタンを押すとアプリが停止し、修正後は停止しないことを確認した。マイクの許可の応答のように別のスレッドから返る完了処理も、メインアクターの上で `await` して受け取る。

## 権限

- Mac 側に必要なのは、アプリ単位の許可 3 つ (ローカルネットワーク・画面収録・アクセシビリティ) だけ。
- Host の実行ファイルをターミナルから直接起動すると、画面収録とアクセシビリティの許可はターミナル (Ghostty) から引き継がれる。ただしローカルネットワークの許可は引き継がれず、mDNSResponder がアプリのバンドル ID ごとに判断する。許可が保留の間は Bonjour の広告が停止する。

## 検証の方針

- Kit のテストは Thread Sanitizer 付きでも実行する (`just test-tsan`)。2026-10-18 に 194 件すべてが通り、データ競合の報告は出なかった (受信した量を数える部品、受信確認、Mac のサウンドの再生と Opus のデコード、接続の送受信を含む)。Host・iPad アプリ・Kit を最初からビルドし直して、コードの警告が 0 件であることも確認した。
- iPad アプリ全体も、テスト用アプリを Thread Sanitizer 付きでビルドして確認した (2026-10-18)。テスト用の Host から 60 fps の映像と 2 秒ごとの状態を受信しながら、「接続状況」を 3 回開閉し、拡大し、Mac が切り替えたディスプレイの通知を受けた (約 1 分、受信確認 4,200 フレーム)。報告は `TSAN_OPTIONS` の `log_path` でファイルに書き出させ、1 件も出なかった。テスト用アプリのコピーにだけわざと競合を入れると、同じビルド設定で報告のファイルに「Swift access race」と場所が出たので、報告が出ないのは仕組みが機能していないからではない。
- 検証は単体テスト (`just test`) とビルドで行う。判断の中身 (タッチの変換、キーの並び、修飾キー、ショートカットの解釈、通信、映像のエンコードとデコード) は Kit の純粋なロジックにして、そこをテストする。
- 変更のあとは `just check` でまとめて確認する (Kit のテストを macOS・Thread Sanitizer・iOS のシミュレータで、Host と iPad アプリのビルドを警告 0 件で)。ビルドは毎回 `clean` してから行う。前のビルドが残っていると、変更していないファイルは再コンパイルされず警告も出ないので、2 回目に警告を見落とす (2026-10-18 に、わざと置いた未使用の変数の警告が `clean` なしの 2 回目で消え、`clean` ありでは 2 回とも検出されることで確認した)。`clean` を挟んでもビルドは 1 回 7 秒ほど。
- ユーザーの Mac や iPad のマウス・キー・ウィンドウ・アプリを動かすテスト (端末を操作する E2E、実機の UI テスト) と、ユーザーの操作を監視して確認する方法はとらない。ユーザーの作業を乗っ取るので、2026-10-17 に強く否定された。以前置いていた `Tools/E2E`・`Tools/DeviceProbe`・`Apps/PadUITests` は削除した。
  - 「次に使われたらログを読む」ためにログを繰り返し読む監視を常駐させるのも、ユーザーの操作の監視にあたる。2026-10-18 に、監視で Mac のサウンドが使われたのを検知し、そのとき再生していたプロセスを調べようとして、強く否定された。実機でしか分からないことは、シミュレータや iPad が接続していない時間のプローブで再現できる形にして確認する。
- Host の入力の処理は、`InputInjector.swift` などをテスト用にビルドし、Mac へ送る `post(tap:)` だけをログ記録に差し替えて確認する。そこへ iPad から届く操作を流し込めば、Mac を動かさずに、作られるイベントの並び・時刻・フラグが分かる。2026-10-17 に、キーリピート、Dock の ⌃F3、Typeless のショートカットを押すかどうかをこの方法で確認した。
