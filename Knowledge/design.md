# PadBridge の設計判断

既存ソフトの調査は [existing-solutions.md](existing-solutions.md) にある。ここには、自作する中で決めたことと、その理由を残す。

## 音声入力は Mac の Typeless を iPad から起動する

- ユーザーの要件は「Typeless で音声入力すること」。Apple の音声認識などで代わりにしてはいけない。
  - 2026-10-17 に一度、合意なく iPad 側の SpeechAnalyzer (Apple の音声認識) に置き換えて強く叱責された。
- iPad のマイクの音を Mac の Typeless に入れるには、仮想オーディオデバイス (BlackHole や自作の AudioServerPlugIn) が要る。これは端末全体を汚すので不可。
- iOS 版の Typeless は App Store で「iPhone 専用」と表示されている (2026-10 時点)。
- ユーザーが選んだ方式は次のとおり (2026-10-17)。
  - iPad の Typeless ボタンで、Mac の Typeless の音声入力ショートカットを押す。
  - 録音は Mac 側のマイクで行う。
  - Mac に何も入れずに、Typeless の全機能 (文脈の読み取りなど) が使える。
- iPad 版の Typeless に切り替える案は、Mac の Typeless を使うという取り決めに反するので出さない (2026-10-17 に調べかけて強く否定された)。

### 蓋を閉じた Mac では、iPad のマイクを一時的な入力デバイスにする

- Mac を閉じたまま iPad から操作すると、Typeless が「マイクがない」と言って録音が始まらない (2026-10-17 の報告)。Apple silicon と T2 の Mac のノートは、蓋を閉じると内蔵マイクをハードウェアで切り離し、root 権限のソフトでも戻せない ([Apple Platform Security](https://support.apple.com/guide/security/hardware-microphone-disconnect-secbbd20b00b/web))。このとき、この Mac の入力デバイスは内蔵マイクしかなかった。
- ユーザーが選んだのは、iPad のマイクの音を「Host が動いている間だけの一時的なマイク」として Mac に見せる方式 (2026-10-17)。ドライバ (HAL プラグイン) は入れない。
  - iPad は Typeless のボタンを押している間だけマイクの音を取り、48kHz・モノラル・16 ビットのまま操作用の接続で送る (`WireMessage.audio`)。
  - Mac では、届いた音を自分のプロセスで鳴らし、自分の出力だけを取り出すミュートのプロセスタップ (`CATapDescription`、`muteBehavior = .muted`) を作る。タップだけを入力に持つ集約デバイス「PadBridge iPad マイク」を作ると、他のアプリから入力デバイスとして見える。出力のサブデバイスを入れると、出力デバイスとしても一覧に出てしまう。
  - **このデバイスは Mac の既定の入力になれない**。タップだけの集約デバイスは `kAudioDevicePropertyDeviceCanBeDefaultDevice` が 0 で、既定の入力に設定しても、ほかのアプリからは内蔵マイクのままに見える (2026-10-17 に確かめた)。既定の入力は切り替えない。
  - 利用者に Typeless の設定を変えさせる作りは「ゴミ仕様」「こっちに指示を出すな」と否定された (2026-10-17)。そこで Host が、iPad がつながった 5 秒後に、Typeless の `selectedMicrophoneDevice` をこのデバイスにする (`TypelessMicrophoneSetup`)。
    - Typeless の中身 (app.asar) を読んで確かめたこと: 設定は electron-store で、外からの書き換えを読み直す `watch` は使っていない。動いている間に書き換えても上書きされるので、Typeless を終了させてから書き換え、起動し直す。選んだマイクは今のマイクの一覧から deviceId で探し、なければ null (自動検出) に戻るので、iPad がつながっていないときは内蔵マイクで聞き取れる。
    - 蓋を閉じると Typeless が「マイクがない」と言う理由も中身で分かった: マイクが「自動検出」のときだけ蓋の開閉を 3 秒ごとに見ており、閉じていると既定の入力 ('default') を使わず、録音するデバイスがなくなる。特定のマイクを選んでいれば、蓋の開閉に関係なくそれを使う。
    - 選んだマイクが一覧にないときは自動検出として扱うだけで、`selectedMicrophoneDevice` を null に書き戻さない。一覧は `devicechange` のたびに取り直す。そのため、Typeless が iPad のつながっていないときに起動しても、補助アプリがデバイスを作り直しても、選んだままになる。
    - 値は、Typeless 自身が設定に書いたマイクの一覧の項目をそのまま使う (deviceId は Chromium が作る値なので、自分では作れない)。書き換えるのはこの 1 項目だけで、ほかの項目が変わらないことを写しで確かめた。
    - 聞き取りの途中では終了させない。選ぶのは、選んだマイクが自動検出 (null か deviceId が `default`) のときだけ (`TypelessMicrophoneChoice`)。利用者が特定のマイクを選んでいれば、その選択として残す。初めは一度だけ設定して UserDefaults に記録していたが、それだと Typeless を入れ直したり設定が消えたりしたあと二度と選ばれず、iPad に設定の手順を出すことになるのでやめた。
    - 最初は聞き取りの間だけ既定の入力を切り替えていたが、Typeless は内蔵マイクで録音していた。coreaudiod の記録では、既定の入力をこのデバイスにした直後に、Typeless の入力は BuiltInMicrophoneDevice で始まっていた。
    - 内蔵マイクをサブデバイスに加えた集約デバイスなら既定になれるが、チャンネル 1 が内蔵マイク、2〜3 がタップの順に並ぶ。Chromium が先頭のチャンネルを読むと、蓋を閉じた内蔵マイクの無音を拾うので採らなかった。
    - Host は、iPad から聞き取りを始めたあと、Typeless が録音しているデバイスを `kAudioProcessPropertyDevices` (入力側) で読む。このデバイスでなければ、Typeless の設定をし直し (自動検出のときだけ)、利用者が別のマイクを選んでいれば iPad に知らせる。
      - Typeless がこのデバイス (タップだけの集約デバイス) で録音しているときは、この一覧が空になる (内蔵マイクのときは BuiltInMicrophoneDevice が入る)。空を「別のマイク」と見なして、正しく聞き取れているのに iPad に警告を出していた (2026-10-17 に利用者が気づいた)。空のときは分からないものとして知らせない。
    - Typeless がこのデバイスを選んだままなので、iPad がつながったまま Mac で直接 Typeless を使うと、無音で録音されてしまう (補助アプリは iPad から話している間しか音を流さないため)。そこで補助アプリは、iPad から話していない間にこのデバイスが読まれたら (`kAudioDevicePropertyDeviceIsRunningSomewhere`)、Mac の既定の入力の音を別の `AVAudioEngine` で取り込んで流す。この通知は集約デバイスでもすぐ届く (プロセスの入力状態と違い、待たずに使える) ことを確かめた。
      - iPad からの聞き取りのあと Typeless がまだ読んでいる間に流し始めると、その続きに Mac のマイクの音が混ざる。読むのが一度止まるまでは流さない (`PassThroughGate`)。
      - 録音の許可がないとタップのミュートが効かず、Mac のマイクの音がスピーカーから流れるので、そのときは流さない。
      - 常に Mac のマイクを取り込んでおけば話し始めが欠けないが、マイク使用中の表示が出続けるので、読まれている間だけ取り込む。
      - 取り込みはタップではなく `AVAudioSinkNode` で行う。この Mac で測ると、タップは 4800 フレーム (100ms) ごとに 1 秒 10 回、シンクは 512 フレーム (約 10ms) ごとに 1 秒 94 回渡し、エンジンの開始はどちらも 0.04 秒だった。Typeless は自分のショートカットで止めた瞬間に読むのをやめるので、ためている分が話し終わりから切れる。シンクにして、ためる量を 30ms にした。Mac の内蔵マイクは 48kHz・モノラルで送る形と同じなので変換しない。
      - 蓋を閉じていると、内蔵マイクは形式 (48kHz・1 チャンネル) は見えるが、値はすべて 0 になる。
      - 一時的な読み手でこのデバイスを 1.5 秒読み、読み始めた瞬間に流し始め、読み終えたらやめること、48kHz で途切れずに届くことを確かめた (2026-10-17)。
  - iPad がつなぎ直すたびに補助アプリを止めて起動し直すと、デバイスを作り直して点検し終えるまで (約 1.5 秒) iPad のマイクを使えず、Typeless もマイクの一覧を取り直す。接続が切れても 60 秒は補助アプリを残し、その間につなぎ直したらそのまま使う。
  - 2026-10-17 の時点で、iPad との接続は Wi-Fi のネットワーク (en0) ではなく Wi-Fi の直接通信 (awdl0) を通っていた (`includePeerToPeer`)。awdl はチャンネルを行き来するので遅れが揺れやすく、切れることもある。ただ、ルーターが端末どうしの通信を遮る設定だと awdl でしかつながらないので、外してはいない。つなぎ直しの原因を追えるよう、Host は接続ごとに経路を記録する。
    - 同じ日の 23:58 のつなぎ直しでは en0 を通った。この環境ではどちらの経路でもつながり、接続ごとに Network.framework が選ぶ (Mac の en0 から `_companion-link._tcp` で iPad が見えなかったのは、iPad がそれを出していなかっただけだった)。
  - `AVAudioNode` のタップは 100〜400ms ごとにしか音を渡さない (ヘッダーの `installTapOnBus` の説明。1024 フレームを頼んでも 100ms になる) ので、iPad の音は 100ms の塊で届く。初めは 80ms たまったら鳴らしていたが、塊より短いと少し遅れて届くたびに途切れる。今は 150ms たまってから鳴らし、3 秒を超えたら古い音を捨てる (`PCMJitterBuffer`)。途切れた回数は聞き取りごとに記録に出す。
  - 初めは聞き取りを始めたらすぐ鳴らしていたので、Typeless がデバイスを読み始めるまで (ショートカットを押してから数百 ms) の声が誰にも届かず、話し始めが切れていた。今は、デバイスが読まれている間 (`kAudioDevicePropertyDeviceIsRunningSomewhere`。別のプロセスが読み始めても通知はすぐ届くことを確かめた) だけ鳴らし、それまではためておく。そのため補助アプリは、聞き取りの間は自分でデバイスを読まない。
  - 完了のショートカットは初め 0.25 秒待って押していたが、ためている音が多いと話し終わりが切れる。今は、iPad で止めたら Host が補助アプリに知らせ (`microphoneRelayFinish`)、補助アプリは止めた直前の塊が届くまで 0.2 秒待ってから、そこまで書き込んだ音を鳴らし終えたら返す (`microphoneRelayFinished`)。Host はそれを受けてから押す。iPad は Mac で Typeless が止まるまでマイクの音を送り続ける。
- 許可について、次のことが分かった (2026-10-17)。
  - プロセスタップには「システムオーディオの録音」(`kTCCServiceAudioCapture`) の許可が要る。ターミナルから動かした Host では Ghostty の許可として求められ、Ghostty は理由の説明 (`NSAudioCaptureUsageDescription`) を持たないので、macOS は尋ねずに断る。このとき、タップのミュートも効かない (試した音がスピーカーから鳴った可能性がある)。
  - Host のバンドルの中に入れた補助アプリ「PadBridge Mic」を LaunchServices で起動すると、許可は「PadBridge Host」のものとして求められる。Host をターミナルから動かしたままでよく、Host 自身をアプリとして起動し直して画面収録などの許可を取り直す必要がない (蓋が閉じているので、取り直す間に画面が映らないと何もできなくなる)。
  - 画面を持たない補助アプリでは、Core Audio は許可の有無を確かめるだけで尋ねない (`preflight=yes`)。公開の API がないので、AudioCap などと同じく TCC の `TCCAccessPreflight` と `TCCAccessRequest` を直接呼んで尋ねる。
  - **タップを含む入力デバイスを読むには、読む側のアプリにも「マイク」と「システムオーディオの録音」の両方の許可が要る。** 2026-10-17 に次のとおり確かめた。
    - マイクだけ許可された Ghostty から読むと、`AudioDeviceStart` が `nope` で失敗した (coreaudiod が Ghostty の `kTCCServiceAudioCapture` を確かめ、未許可だった)。
    - システムオーディオの録音だけ許可された補助アプリから読むと、無音だった (`kTCCServiceMicrophone` が未許可)。
    - Typeless の Info.plist にはマイクの説明しかないので、Typeless は自分ではこの許可を求めない。システム設定の「画面とシステムオーディオの録音」→「システムオーディオ録音のみ」に、利用者が Typeless を加える必要がある。
    - 許可がないとき、Typeless は「PadBridge iPad マイク」を開けはするが、中身は無音になり、聞き取りは続く (2026-10-17 の「音声入力が動かない」の原因)。tccd は Typeless の確認に authValue=0、authReason=8 (理由の説明がない) を返し、「Refusing authorization request for service kTCCServiceAudioCapture and subject Sub:{now.typeless.desktop}」を記録した。断ったことは許可の一覧に残らないので、Typeless は一覧に自動では載らず、「＋」で加える必要がある。
    - アプリから他のアプリの許可を前もって読む方法はない。`TCCAccessPreflightWithAuditToken` は、権限のない呼び出し元には実際の許可と違う値 (許可されているマイクも「拒否」) を返した。
    - そこで Host は、iPad のマイクで聞き取りが始まった 1 秒後に、直近 5 秒の tccd の記録から上の拒否の行を探す。あれば iPad に手順を知らせ、Mac で「画面とシステムオーディオの録音」の設定を開く。なければ知らせを消す。
    - 初めは「iPad から始めたのに 1 秒たっても聞き取りが始まらない」ことも読めない印にしていたが、誤りだった。Typeless は聞き取りを止めてから文字にして貼り付け終えるまで (数秒) ショートカットを受け付けず、続けて話し始めるとこれに当たる。2026-10-17 に、止めて 3.7 秒後に始めたときに設定の画面を開いてしまい、ミラーリングの画面に出た。今は読めない印は tccd の拒否の行だけにし、始まらないときは 1 秒ごとに 4 回まで押し直す。その間は iPad にマイクを止めさせず、補助アプリが声を 6 秒までためておくので、遅れて始まっても話し始めは落ちない。
      - Typeless の中身 (xstate の状態機械) で確かめた: 止めたあとの `finishing` (文字起こしの仕上げ) では、ショートカット (`PRIMARY_KEY.DOWN`) は「まだ仕上げ中」の知らせ (`showFinishingAlert`) を出すだけで、ためて後で始めはしない。仕上げが終わる (`WEBSOCKET.REFINE_COMPLETED`) と `idle` に戻り、押せば始まる。そのため押し直しても余計に始まったり止まったりしない。
        - この知らせは「前の聞き取りを処理中」の警告を 5 秒出すもので、前の聞き取りを取り消す (`ESC`、記録は `dismissed`) のは、知らせの中の「キャンセル」を人が押したときだけ。押し直しても、前に話した分は消えない。
        - 仕上げの長さの上限は、文字起こしで 20 秒、音声コマンドで 30 秒 (`VOICE_TRANSCRIPT_REFINE_TIMEOUT_MS`・`VOICE_COMMAND_REFINE_TIMEOUT_MS`、長い録音は録音の長さ) で、過ぎると `FATAL_TRANSCRIPTION_TIMEOUT` になる。押し直すのは約 5 秒までで、補助アプリがためておける声 (6 秒) に合わせている。それより仕上げが長引いたときは、iPad の表示を戻して押し直してもらう。
      - 同じく、聞き取りを始めて 1 秒後から 5 秒間、声があるかを見ており、なければ自分で止める (`RECOVERABLE_NO_SPEECH_DETECTED`)。声とみなすのは、8 ビットの波形で 128 から 1 以上離れた値 (振れ幅で約 0.0078、-42dBFS) が 1 つでもあるとき。iPad の声は話すと最大 0.12〜0.25 で十分に上回り、話していないときの雑音 (約 0.0006) は下回る。iPad の声を Typeless が読み始めるまでためておくのは、この点でも要る (読み始めたときに話し始めから流れる)。
      - ショートカットを押し続けると `long_pressing` (「押し続けず押すだけ」の知らせ) になり録音を止めるので、Host は押してすぐ離す。
  - Typeless (Chromium) にこのデバイスをマイクとして数えさせるには、次の 2 つが要った (2026-10-17、「使えない」と報告されて調べた)。聞き取りの間に Typeless の「システムオーディオの録音」の確認が一度も起きず、Typeless の設定のマイクの一覧にもこのデバイスがなかったことから、内蔵マイクを開いていたと分かった。
    - タップを公開にする (`isPrivate = false`)。既定の非公開のタップは作ったプロセスにしか見えず、ほかのアプリからは集約デバイスの入力が 0 本に見える。
    - 補助アプリの出力を止めない。出力を止めたまま作ったタップや、出力が止まっている間は、集約デバイスが入力を持たない。Typeless は聞き取りの間だけ入力が現れても、マイクの一覧を作り直さない。iPad の声を鳴らすのは聞き取りの間だけにし、それ以外は無音を流す。
    - 直したあと、Typeless の設定のマイクの一覧に「PadBridge iPad マイク」が加わった。
  - 補助アプリは、終わる前にデバイスを消し終えるのを待つ。待たずに終わると、デバイスが Mac に残る。
  - 補助アプリが無音を流し続けている間は、coreaudiod が Mac のアイドルスリープを止める (`pmset -g assertions` に `BuiltInSpeakerDevice.context.preventuseridlesleep` が出る)。iPad がつながっている間だけなので、閉じた Mac を iPad から使う用途ではそのままにしている。
  - 最初は、補助アプリが自分で鳴らした小さな音 (20kHz) を自分で読んで経路を確かめていた。上のとおり補助アプリにはマイクの許可がなく必ず無音になるので、この点検はやめた。
- 作った集約デバイスとタップは、作ったプロセスが終わっても HAL に残る。補助アプリは、起動したときに前の残りを消し、Host との接続が切れたら自分のものを消して終わる。名前で探して消すと、入れ替わりに起動した補助アプリのデバイスまで消してしまうので、終わるときは自分が作ったものだけを消す。
- 補助アプリは Host とループバックの接続でつなぐ。Host は起動のたびに合言葉を渡し、合言葉を言わない接続は切る。

### Typeless のショートカットは「押し続ける」のではなく「1 回押す」

- 設定ファイルのキー名は `keyboardShortcut.pushToTalk` だが、**押すたびに開始と完了が切り替わる**方式。押し続けると、聞き取りは始まらず「Typeless ショートカット」の使い方の案内 (「話すには一度押してください…」) が出るだけ。
  - 最初はキーを押し続けて実装し、この案内を聞き取り中と取り違えて「動いた」と判定していた。ユーザーには一度も正しく起動していなかった。
- Mac は、iPad から「開始」「完了」が届くたびに、ショートカットを 50ms だけ押して離す。iPad のボタンは、タップで開始と完了を切り替える使い方と、押している間だけ話す使い方の両方に対応する (どちらも Mac では 1 回押しになる)。
- 合成する修飾キーのイベントには、実際のキーボードと同じく次のビットを載せている。
  - 左右を区別するビット (左 Control は `0x1`)
  - 合成ではない実入力であることを示すビット (`0x100`)
- ショートカットは、押すたびに `~/Library/Application Support/Typeless/app-settings.json` を読み直す。書き換えはしない。
- Typeless が動いていなければ、押す前に起動する。Typeless はショートカットを本体のプロセスのキーのイベントタップ (セッションと HID の 2 つ、キーの押下・離し・修飾キーの変化を見る) で拾い、本体から画面側へ `global-keyboard` として送っている。タップができるまでは押しても届かないので、`CGGetEventTapList` で Typeless のタップが現れるまで (最大 10 秒) 待ってから押す。初めは起動を終えてから決め打ちで 1.5 秒待っていた。
  - それでも画面側の用意が間に合わずに届かなかったときは、聞き取りが始まらないので押し直しで拾う。押し直しを数え始めるのは押したときから。初めは iPad から要求が届いたときから数えていて、Typeless の起動を待つ間に押し直しの 5 秒を使い切り、始まる前に iPad の表示を戻してしまう作りだった。

### Typeless の動作確認の方法

- 窓が出たかどうかでは判定できない。聞き取り中の小さなピル (✕・波形・✓) も使い方の案内パネルも、同じ窓 (750x500) に描かれるため。
- 2026-10-17 に窓を撮影して比べたところ、不透明な暗い部分の高さは、ピルが 64px、案内パネルが 298px だった。
- 実際に文字になるかを、Mac の `say` で確かめることはできない。Typeless の音声取得にかかるエコーキャンセルが、Mac 自身のスピーカーの音を消してしまう。
- 1 回押すと Typeless のマイク入力が始まり、もう 1 回押すと止まることを、macOS の audiomxd の記録 (`input_running`) で確かめた (2026-10-17)。

### iPad のボタンの表示は、Typeless の実際の状態に合わせる

- 最初は iPad と Mac がそれぞれ「開始を送ったか」だけを覚えていた。Typeless が自分で聞き取りを終えたり、Mac 側で ✕ を押したりすると覚えとずれる。次の「完了」でショートカットを押すと逆に聞き取りが始まり、「Typeless の状態と iPad の赤・青が逆になる」と報告された (2026-10-17)。
- Typeless は聞き取りの状態を外へ公開していない。そこで、聞き取っている間だけマイクを使うことを利用して、CoreAudio のプロセスの入力状態 (`kAudioProcessPropertyIsRunningInput`) で判定する (`TypelessMonitor`)。
  - Typeless は Electron 製で、マイクを使うのは本体ではなく `now.typeless.desktop.helper` (Typeless Helper)。バンドル ID の先頭が `now.typeless.desktop` のプロセスをまとめて見る。
  - CoreAudio のプロセス `now.typeless.desktop.helper` の PID は 2204 だった。audiomxd が聞き取り中に `input_running: true`、完了後に `false` と記録した「Typeless Helper(2204)」と同じプロセスであることを、PID で照らし合わせた (2026-10-17)。
  - プロセスの入力・出力状態の値は正しく変わるが、`AudioObjectAddPropertyListenerBlock` の変化の通知は来なかった。自分のプロセスで、音の出ない出力を 1 秒流して確かめた (2026-10-17)。このため、iPad がつながっている間だけ 0.2 秒ごとに読み直す。
- Mac はショートカットを押す前に実際の状態を見て、すでに求められた状態なら押さない (`TypelessToggle`)。押してからマイクが動き出すまで 0.1〜0.2 秒かかる。押してから 1 秒の間は、押した結果を今の状態とみなす。
- iPad は押した直後に求めた状態を先に見せる。そのあと Mac から状態 (`voiceInputState`) が届いたら、それに合わせる。Typeless がショートカットに反応しなかった場合は状態が変わらず知らせが来ないので、Mac は要求から 1 秒後に必ず今の状態を送る。
- iPad が裏に回ったときや接続が切れたときに止めるのは、iPad から始めた聞き取りだけ。iPad が自動でロックされたときに、Mac で直接話している聞き取りを止めてしまわないため。

## 通信: ペアリングも暗号化もしない

- 最初は TLS-PSK (Mac が発行する 10 文字のペアリングコード) で、暗号化と相互認証をしていた。
- ユーザーから「ペアリングコードは邪魔」と言われ、廃止した (2026-10-17)。認証の鍵をリポジトリに埋め込んでも公開リポジトリでは意味がないので、TLS ごと外して素の TCP にしている。**同じ LAN の誰でも Mac を操作できる**ことは README に明記した。
- Mac は Bonjour (`_padbridge._tcp`) で広告する。iPad は、前回つないだ Mac か、見つかった Mac が 1 台だけならそこへ自動でつなぐ。
- 接続は**操作用と映像用の 2 本**に分けた。1 本にまとめると、映像の送信が詰まったときにクリックやキー入力まで待たされるため。
- Mac は、送信待ちが 4 件以上たまったら、取り込んだフレームを符号化する前に捨てる。符号化したあとで捨てると、参照フレームが欠けて映像が壊れる。
- 知らない種類のメッセージや、知らない操作 (JSON の知らないケース) が届いても、接続は閉じずにそのメッセージだけ飛ばし、記録に残す。メッセージの区切りは framer が長さで切り出しているので、1 件を読み飛ばしても後ろはずれない。初めは解釈できないものが来たら接続を閉じていたが、Mac と iPad の片方だけを新しいビルドにすると (2026-10-17 に Host だけが古いまま動いていたことがある)、新しい方が送るものを古い方が受け取るたびに切れ、つなぎ直しを繰り返すことになる。
- 相手が切断を知らせずに消えたとき (圏外、スリープ、iPadOS が裏のアプリの通信を止めたとき) は、TCP のキープアライブと再送の打ち切りで気づく。無通信が 2 秒続いたら 2 秒おきに確かめ、4 回返事がなければ切る。送っている最中は確かめが送られないので、再送に 10 秒返事がなければ切る。初めはキープアライブを始めるまでの 2 秒だけを決めていたが、間隔と回数は macOS の既定 (`net.inet.tcp.keepintvl` 75 秒、`keepcnt` 8 回) のままで、気づくまで約 10 分かかっていた。その間 iPad は止まった映像を映したまま、つなぎ直さない。

## 裏に回っても切らない

- ユーザーから「バックグラウンドで切れるのは論外」と言われた (2026-10-17)。
- iPadOS は、裏に回ったアプリを数秒で止める。そこで接続中は、`UIBackgroundModes: audio` と `.playAndRecord` + `.mixWithOthers` のオーディオセッションで、無音を流し続ける (Typeless で話すときに iPad のマイクも使うので、録音もできる種類にしておく。あとから切り替えると流している無音が止まる)。音は出ず、他のアプリの音楽なども止めない。
- 裏にいる間は、映像用の接続だけ閉じる (電池と通信量を抑えるため)。前面に戻ったら、映像用の接続を張り直してキーフレームから描き直す。
- 映像を送っている間だけ、Host が `PreventUserIdleDisplaySleep` のアサーションを持つ。iPad で見ているだけで操作しない間に、Mac の画面が「ディスプレイをオフにする」の時間 (この Mac は 10 分) で眠り、映らなくなるのを防ぐ。Amphetamine などが動いていなくても見続けられる。iPad が裏に回って映像の接続を閉じると放す。
  - このアサーションは、もう眠っている画面を起こさない。iPad が裏にいる間に画面が眠ると、前面に戻っても何も映らない (ScreenCaptureKit は画面が変わらないとフレームを出さない)。映し始めるときに `IOPMAssertionDeclareUserActivity` で操作があったと知らせて起こす (この Mac は Amphetamine が画面を眠らせていないので、ふだんは起きない場面)。
- 操作用の接続が切れたら、一覧画面に戻さず、その場で 0.5 秒から 5 秒までの間隔で張り直し続ける。
- 実機で、ホーム画面に 20 秒移っても Mac 側に切断が記録されず、戻ると映像だけが再要求されることを確かめた (2026-10-17)。

## Mac 側で文字を入れる方法

- 第 1 候補は、アクセシビリティ API で入力欄の選択範囲 (`kAXSelectedTextAttribute`) に書き込む方法。クリップボードを使わないので、ユーザーのクリップボードやクリップボード履歴を汚さない。
- 書き込みが成功を返しても、実際には反映しないアプリがある (Electron 製など)。そのため値が変わったかを読み直し、変わっていなければ `CGEvent` の Unicode 文字列によるキー入力に切り替える。
- Mac が日本語入力モード (ことえり) でも、キー入力で送った文字が変換待ちにならず、そのまま確定して入ることを確かめた (2026-10-17)。

## 映像

- ScreenCaptureKit でメインディスプレイを取り込み、VideoToolbox の H.264 で符号化する。低遅延レート制御を使い、プロファイルは ConstrainedHigh、フレームの並べ替えはしない。
- iPad 側は `AVSampleBufferDisplayLayer` に圧縮したまま渡して復号させる。
- ScreenCaptureKit は画面が変わらないとフレームを出さない。そのため、5 秒ごとのキーフレームと、要求に応じたキーフレームで回復点を作る。
- 実機の iPad (2360x1640) では、2360x1532、14 Mbps で配信している。
- 取り込みの大きさは始めたときに決まるので、Mac の解像度やメインディスプレイが変わると、映像が縮んだり別の画面を映したりして、触った位置とずれる (タッチの座標は毎回そのときのメインディスプレイで直すため)。Host は `NSApplication.didChangeScreenParametersNotification` を受けたら、メインディスプレイの ID・大きさ・画素数が取り込みを始めたときと違うときだけ、同じ映像の接続のまま取り込みと符号化を作り直す。iPad は新しいキーフレームと一緒に届く映像の形式で大きさを読み直す。蓋を閉じたこの Mac でも、メインディスプレイは内蔵の 1 台で、大きさ (1800x1169、3600x2338) は変わらないので、余計に作り直すことはない。

## Mac の音を iPad で鳴らす

- 初めは「Mac の音は iPad に送らない」を既知の制約にしていた。2026-10-18 に、iPad の「…」から入れる切り替えとして加えた。既定は切ってあり、入れなければ前と同じ動きになる。
- Host は、iPad が頼んでいる間だけ、補助アプリを除く全プロセスの出力をまとめる非公開のプロセスタップ (`CATapDescription(stereoGlobalTapButExcludeProcesses:)`) を作り、タップだけを入力に持つ非公開の集約デバイスを IOProc で読む。
  - `muteBehavior` は `.mutedWhenTapped`。読んでいる間だけ Mac で鳴らさないので、Host が落ちてタップが残っても Mac の音は消えない。
  - 補助アプリは、iPad の声と、Mac で直接話すときの Mac のマイクの音を鳴らしている。除かないと、Mac で話した声が iPad で鳴る。補助アプリのプロセスのオブジェクトは音を出し始めるまで現れず、起動し直すと変わるので、プロセスの一覧が変わるたびに見直してタップを作り直す。macOS 26 の `bundleIDs` で除く方法もあるが、除く側のタップでの効き方を確かめていないので使っていない。
  - 出力先の機器が変わるとタップの形式 (サンプルレート) も変わるので、`kAudioTapPropertyFormat` が変わっても作り直す。出力デバイスは集約デバイスに入れず、出力先が変わるたびに作り直さずに済むようにした。
- 送る形は 48kHz・ステレオ・16 ビット (約 1.5Mbps) で、20ms ごとの塊にする。すべて 0 の塊は送らないので、何も鳴っていない間は通信しない。映像の送信が詰まっても待たされないよう、操作用の接続で送る。送信待ちが 25 件 (0.5 秒分) を超えたら捨てる。
- iPad は、裏に回っても止められないよう無音を流しているのと同じエンジンに `AVAudioSourceNode` をつないで鳴らす。awdl の揺れで途切れないよう 100ms たまってから鳴らし、0.5 秒より遅れたら古い音から捨てる。
- iPad のマイクで聞き取っている間は鳴らさない。iPad のスピーカーの音をマイクが拾い、Mac の音が Typeless に入るため。
- iPad が裏に回っている間は Mac で鳴らす。接続は裏でも続くので、iPad をしまったまま Mac を開くと、Mac が無音のままになるため。
- 2026-10-18 に、iPad がつながっていない間に検証用のクライアントで確かめた。
  - タップの形式は 48kHz・2ch・Float32 (交互) で、変換は形式を変えるだけだった。頼んでから最初の塊が届くまで 0.13 秒。
  - 聞こえない 20kHz・0.01 の音を鳴らすと、届いた音の最大は 0.0102 だった。
  - 補助アプリが起動して点検の音 (0.01) を 1.5 秒鳴らしている間に、届いた塊は 0 だった。補助アプリは起動から約 0.2 秒で、デバイスを作る前に除かれていた。何も鳴っていない間も届かなかった。
  - iPad 側は、AVAudioEngine を手で回す単体テストで、左右の振り分け、たまってから鳴らすこと、マイクを使っている間は鳴らさないことを確かめた。左右を入れ替えるとテストが落ちることも確かめた。

## タッチの読み替え

- 指の操作は UIKit のジェスチャー認識を並べず、`TouchInterpreter` という 1 つの状態機械で判定する。認識器を並べていた頃、実機で次の 2 つが起きた。
  - `isMultipleTouchEnabled` が既定の false のままで 2 本目の指が届かず、2 本指スクロールが成立しなかった。
  - 長押しの成立と同時に右クリックしていたため、「押して少し待ってからドラッグ」が右クリックになった。
- ユーザーの指摘で、長押しせずに払う操作はドラッグではなくスクロールにした (iPad の普段の操作に合わせた)。ドラッグは長押ししてから動かす。指を離したあとは `ScrollMomentum` で慣性スクロールする。
- トラックパッドやマウスのクリック (`UITouch.type == .indirectPointer`) は状態機械を通さず、押下と解放をそのまま送る。マウスのつもりで長押しして右クリックになるのを防ぐため。
- Apple Pencil (`.pencil`) も同じく、押下と解放をそのまま送る (2026-10-18)。初めは指と同じ状態機械を通しており、触れて動かすとスクロールになり、文字の範囲選択や描く操作には長押しが要った。Sidecar も Pencil はクリックとドラッグで、指はスクロールなので、それに合わせた。クリックの回数は Host の `ClickCounter` が数えるので、続けて触れるとダブルクリックになる。
- Typeless ボタンは UIKit の `UIButton` にしている。SwiftUI の `GestureState` は、システムに押下を奪われたキャンセルと指を離したことを区別できないため。キャンセルされたときは、押しっぱなしに切り替えて聞き取りを続ける。
- 合成したクリックには macOS がクリック回数を付けてくれないので、`ClickCounter` で自前で数える。
- 修飾キーを単体で送るときは、イベントの種類を `flagsChanged` にしないと、アプリが Command などを認識しない。
- 合成するキーイベントのフラグは、実際の Mac のキーボードに合わせる (`KeyboardMapping.eventFlags`)。
  - 矢印キーには Fn (`0x800000`) とテンキー (`0x200000`) のビットを付ける。この Mac の Mission Control のショートカットは、修飾キー `0x240000` (Control+テンキー) で登録されていて、テンキーのビットがない Control+↑ には反応しない。
  - Home・End・F キーなどには Fn のビットを、修飾キーには左右を区別するビットを付ける。
- 2 本指で広げたり縮めたりすると、iPad の上で Mac の画面を拡大する (`ScreenZoom`、5 倍まで)。Mac の文字は iPad では小さいため。
  - 2 本指の間隔の変化が 24pt を超え、かつ中心の移動より大きいときだけ拡大とみなす。それ以外は今までどおりスクロール。いったんスクロールと決まったら、途中で拡大には変えない。
  - 指の中心の下にある映像の位置が動かないよう拡大し、指が動いた分だけずらす。映像が画面より大きい向きでは、端に余白が出ないよう押さえる。1.05 倍まで縮めたら等倍に戻す。
  - タップやスクロールは、拡大した映像の位置を基準に Mac の座標へ直す。シミュレータで 2 倍のピンチ 1 回分を流し込み、映像の位置 (-790,-410、2360x1640) とタップの座標 (中央 0.585, 0.500、右寄り 0.710, 0.500) が計算どおりになることを確かめた (2026-10-17)。
  - XCUITest の `pinch` は、2 本の指を 4pt ほどの間隔から 28pt ほどまでしか広げず、実際の指の動きと違う。判定は単体テストで、画面への反映は動作を直接流し込んで確かめる。
  - 拡大しても文字がぼやけないよう、拡大が 0.2 秒落ち着いたら、見えている範囲 (余白 15%、画面と同じ縦横比、1/128 刻み) を Mac に頼む (`VideoRegion`)。Mac は拡大している間だけ画面を元の解像度で取り込み、その範囲を切り出して iPad の解像度で送る。映像の大きさは変わらないので、符号化をやり直さずに済む。
    - 切り出しは `VTPixelTransferSession` で行う。切り出す範囲を直接指定する項目はなく、元のフレームに clean aperture を付けて `kVTScalingMode_CropSourceToCleanAperture` で使わせる。範囲は画面の中心からのずれで、右と下が正。四隅を塗り分けたフレームで確かめた (2026-10-17)。
    - フレームごとに写っている範囲を付けて送り、iPad はそのとおりの位置に置く。取り込みの設定を変えている途中のフレームも、その範囲で正しく置ける。タッチの座標は画面全体を基準に直すので、切り出しとは関係なく変わらない。
    - 本物の ScreenStreamer をループバックでつないで確かめた。範囲を変えると、その範囲を付けたフレームがキーフレームから届き、映像の大きさは 2360x1532 のまま変わらなかった。iPad 側は、範囲付きのフレームが届いたときの置き場所と、2 倍に拡大したときに頼む範囲が計算どおりになることをシミュレータで確かめた。
- 3 本指で払うと、トラックパッドと同じ操作をする。iPadOS の 4・5 本指のジェスチャーとぶつからないよう、3 本指にしている。
  - 左右は操作スペースの切り替え。トラックパッドが出すのと同じ Dock スワイプのイベント (種類 30、HID 種別 23) を、開始・途中・終了の 3 つ合成して切り替える。欄の番号と値は [InstantSpaceSwitcher](https://github.com/jurplel/InstantSpaceSwitcher) (MIT) の macOS 26 以前向けの実装に合わせた。macOS 27 では追加の欄が要る。
    - 最初は Control+←/→ を送っていて、2026-10-17 18:23 に「3 本指スワイプで画面が動かない」と報告された。Dock の記録では、このとき切り替えは起きていない。原因は、利用者が使っていた Host が、矢印キーに Fn とテンキーのビットを付ける修正の前のビルドのまま動いていたこと (iPad アプリだけ入れ替えて Host を再起動していなかった)。修正後の Host では、18:39 にバーの ⌃+→/← でも約 1 秒かけてスペースが移ることを Dock の記録で確かめた。
    - それでも Dock スワイプのままにしているのは、切り替えが 0.05〜0.17 秒と速く、ショートカットの設定にも左右されないため。
    - 教訓: Host と iPad アプリの片方だけを入れ替えると、古い側の動作を見て誤った原因を立ててしまう。変更を入れたら、利用者が使っている Host も必ず入れ替える。
  - 上は Mission Control、下はアプリケーションウインドウ。この 2 つは登録値 (`[65535, 126/125, 2359296]`) があり、Control+↑/↓ で動くことを確かめたので、ショートカットのまま送る。
- Dock は、iPad で Dock を出すのと同じく、画面の下端 (24pt 以内) から上へ 30pt 払うと出す。
  - この Mac は Dock を自動的に隠している。カーソルを画面の下端に置けば出るが、指のタップはクリックになり、カーソルを下端に止めておく操作がない。「Dock にアクセスできない」と報告された (2026-10-17)。
  - 出すのには「Dock にフォーカスを移動」のショートカット (登録値 8、`[65535, 99, 262144]` = Control+F3、有効) を送る。Mission Control の Control+↑ と同じシステムのショートカットの仕組みで動く。
    - Control+F3 は、自動的に隠している Dock も出す ([macmost](https://macmost.com/using-the-mac-dock-with-only-your-keyboard.html))。
    - SDK の `NSEvent.h` では、Fn のビット (`1 << 23`) は「いずれかのファンクションキーが押されている」ときに付く。実際のキーボードで Control+F3 を押したときと同じく、合成する F3 にも Fn のビットを付けている。
  - 下端の近くでも、タップと横への払いはいつもどおりクリックとスクロールにする。キーボードを出してビューが縮んでいる間は、ビューの下端が画面の下端ではないので受けない。
- 合成したキーの押下は macOS が繰り返してくれない。そのため、iPad のハードウェアキーボードで ⌫ や矢印を押し続けても 1 回しか効かなかった。Mac 側で、押されたまま離されていないキーを、Mac のキーのリピートの設定 (`NSEvent.keyRepeatDelay`・`keyRepeatInterval`) どおりに繰り返す (`KeyRepeat`)。実際のキーボードと同じく、最後に押したキーだけを繰り返し、繰り返しのイベントには自動リピートの印 (`keyboardEventAutorepeat`) を付ける。
  - この Mac の値は、繰り返し始めるまで 0.25 秒、間隔 0.033 秒だった。Host と同じ手順で ⌫ の繰り返しのイベントを作り (送らずに) 調べた。AppKit からは、押し続けによる入力 (`isARepeat` が true) で、文字は U+007F に見える。
- ハードウェアキーボードの Command+Tab は iPadOS が先に受け取るので、バーのボタンで代わりにする。タップのたびに Command を押したまま Tab を送り、1 秒タップがなければ Command を離して確定する。
- Mac 側は押されている修飾キーを覚えておき (`HeldModifiers`)、クリック・ドラッグ・スクロールのイベントにも載せる。載せないと、ハードウェアキーボードの ⌘ を押しながらタップしても ⌘クリックにならない。
- バーの修飾キー (`ModifierLatch`) は、押すと次の 1 回にだけ効き、続けて 2 回押すと固定される。クリックやドラッグには `PointerModifierHold` で、押す前に修飾キーを押し、離したあとで離す。
- 直接入力では、英数字と空白はキーとして送り、記号は文字として挿入する。記号は Mac 側の配列 (US と JIS) でキーの位置が違うので、キーで送ると別の記号になる。
  - ただし、どちらの配列でも同じ位置にある - , . / (と Shift の ! ?) はキーとして送る。この Mac の ABC 配列でキーコードを変換し、それぞれ - , . / ! ? になることを確かめた。macOS のローマ字入力の規則 (`CoreJapaneseEngine.framework` の `RomajiRule_Default.txt`) では、- は「ー」になる。文字として挿入すると Mac の日本語入力を通らず、かなモードでも「ー」「、」「。」にならない (「伸ばし棒が打てない」と報告された、2026-10-17)。
  - 英字配列のキーボードでは - が記号の面にしかないので、特殊キーの列に「ー」(- のキー) を置いた。
- 特殊キーの列は、横にずらせる `UIScrollView` の中にある。既定 (`delaysContentTouches`) では、スクロールかどうかを見極める間キーの押下が遅れる。そのため、短く押すと押した表示がほとんど出ず、「押した感覚がない」と言われた (2026-10-17)。押下はすぐに届くようにし、押している間は色と大きさを変え、キーボードのクリック音 (`playInputClick`) も鳴らす。iPad には触覚フィードバックの仕組みがないので、振動は使えない。
  - 押下をすぐに届けると、列を横へずらそうとキーの上から触れただけで、押した瞬間のキーが送られてしまう (シミュレータで確かめた)。そのため、キーを送るのは指を離したとき (押し続けたら 0.4 秒後から繰り返し) にし、押した瞬間は表示と音だけにする。横へずらすとタッチは取り消されるので、キーは送られない。
- ソフトウェアキーボードの削除キーを押し続けても、1 回しか消えなかった (2026-10-17 の報告)。直接入力の受け口が `UIKeyInput` だけだと、キーボードが削除を繰り返さないため。`hasText` を常に true にしても変わらない。
  - 画面を出さないシミュレータ (iOS 26.5) で、本体とは別の試験アプリを使い、削除キーを 3 秒押し続けて確かめた (2026-10-17)。`UIKeyInput` だけの受け口では `deleteBackward` は 1 回だった。`UITextInput` を備えて中身の変わらない文書を見せると 25 回で、どれも 1 文字分の `deleteBackward` だった。隠した `UITextView` に番兵の文字を入れる方式も試した。こちらも繰り返すが、途中から単語単位でまとめて消すので、Mac へ送る削除の数に直す手間が要る。
  - そこで、受け口に `UITextInput` を足し、文書は手元に持たずに常に同じものを見せる。`editingInteractionConfiguration` は `.none` にして、iPadOS の 3 本指の編集ジェスチャーが Mac のデスクトップ切り替えとぶつからないようにする。
  - 見せる文書は改行の繰り返しにする。最初に試した「a 」の繰り返しでは、キーボードが末尾を単語と空白とみなした。そのため空白を 2 回打つと、文書の空白をピリオドに置き換えようとした (`replace`)。改行だけの文書では、打ったとおりの `insertText` と `deleteBackward` しか届かないことを、同じシミュレータで確かめた。
- iPad のキーボードは英字配列に固定し、日本語は Mac 側の日本語入力で変換する。iPad 側で変換して文字を送る入力欄は、操作が二重になるのでやめた。iPad のソフトウェアキーボードには Mac の日本語入力を切り替えるキーがないので、特殊キーの列に JIS キーボードの英数・かなを置いている。

## 画面の構成

- 最初は画面下に、キー・修飾キー・入力欄・送信・Typeless などのボタンを 1 列に並べていた。使う頻度も場面も違うものが同じ重さで並び、Mac の画面も狭くなるので、ユーザーから強く否定された (2026-10-17)。
- 今は使う場面ごとに置き場所を分けている。
  - Mac の画面は全面に出す。
  - いつでも使うもの (Enter・Typeless・キーボード・アプリ切替・切断) は、隅に浮かぶ小さな操作パネルにまとめる。
    - Enter は、Typeless で話したあとにキーボードを出さずに送れるよう、パネルの先頭に置いた (ユーザーの要望、2026-10-17)。
    - アプリ切替のアイコンは、最初の `square.on.square` がコピーのボタンに見えると言われたので、`rectangle.2.swap` にした。
  - パネルのボタンでキーボードを閉じると、キーボードは消えるが、Mac の画面の表示領域が縮んだまま戻らないと報告された (2026-10-17)。OS のキーボードを閉じるキーでは戻る。
    - 入力先を外すのが SwiftUI の更新 (`updateUIView`) の途中だからと考え、入力先の付け外しを `DispatchQueue.main.async` で更新のあとへ回した。
    - ところが、画面を出さないシミュレータ (iPad Air 11 インチ、iOS 26.5、実機と同じ 820x1180pt) で本物の画面を組んで確かめると、元のコードでも SwiftUI の余白は戻った (縦 1180 → 829 → 1180)。
    - 映像の範囲を UIKit の `keyboardLayoutGuide` から決めるように変えて調べた。すると、パネルのボタンで閉じたあと、ガイドは特殊キーの列の高さ 52pt を残したまま (1128) 戻らなかった。同じときのキーボードの通知 (`keyboardWillHide` など) は、正しく画面の外 (上端 1180) を知らせていた。特殊キーの列 (`inputAccessoryView`) を付けた入力欄をプログラムから外すと、キーボードの位置の追跡にこの食い違いが残る。実機の SwiftUI の余白が戻らなかったのも、これと同じとみている。
    - そこで、Mac の画面のビューはキーボードの余白を無視して全面に置き、映像の範囲はキーボードの通知が知らせる位置から自分で決める。シミュレータで、横・縦とも開く・閉じるを 3 回ずつ繰り返し、閉じるたびに全面に戻ることを確かめた (横 820 → 346 → 820、縦 1180 → 791 → 1180)。
  - この変更で、`updateUIView` の中で `isActive` を読まず、後で動く処理の中でだけ読むようにしてしまった。SwiftUI は読まれた値にしか依存を記録しないので、ボタンで切り替えても `updateUIView` が呼ばれず、**キーボードがまったく出なくなった**。
    - 「キーボードが出なくなった」と報告された (2026-10-17)。本物の画面を組んだシミュレータで、開く操作 3 回がすべて失敗することを再現した。
    - `updateUIView` の中で値を読んで後の処理へ渡すように直した。そのあと、横向き・縦向きとも開く・閉じるを 3 回ずつ繰り返し、高さが戻ることを確かめた (横 820 → 346 → 820、縦 1180 → 791 → 1180)。
    - 最初に作った簡略な再現では起きなかった。親の画面がボタンの文字のために同じ値を読んでいて、依存が記録されていたため。再現は本物の画面で行う。
  - シミュレータでは、OS の「キーボードを非表示」を一度押すと、そのあとはどの入力欄を有効にしてもキーボード本体が画面の外に置かれたままになった。普通の `UITextField` をタップしても、`reloadInputViews` を呼んでも戻らない。実機の iPad では、キーボードを隠したあとに入力欄をタップすれば出るので、シミュレータ側の現象とみている。
  - キーを打つときだけ使うもの (esc・Tab・修飾キー・矢印・英数/かな) は、キーボードの上の列 (`inputAccessoryView`) に出す。
- iPad から送るキーの並び (`RemoteKeys`・`AppSwitcher`) と、Mac で合成するキーの種類とフラグ (`MacKeyEvent`) は Kit にまとめ、単体テストで固めている。実際の端末を操作するテストは、利用者の作業を乗っ取るので走らせない。
- Mission Control の開閉は、Dock 自身の記録 (`com.apple.dock:missioncontrol` の mode の変化) で確かめられる。

## Swift 6 とオーディオのスレッド

- アプリのターゲットは既定でメインアクターに属する (`SWIFT_DEFAULT_ACTOR_ISOLATION: MainActor`)。メインアクターのメソッドの中で書いた処理 (クロージャ) もメインアクターに属するとみなされる。
- それを AVFAudio の `installTap` に渡すと、AVFAudio が自分のスレッドから呼んだ時点で、Swift の実行時の検査 (`dispatch_assert_queue`) に止められてアプリが落ちる。「マイクボタンを押したらクラッシュする」と報告された (2026-10-17)。
- オーディオのスレッドから呼ばれる処理は、`nonisolated` な場所 (静的メソッドや `nonisolated` なクラス) で作る。シミュレータで、直す前のコードでは Typeless のボタンを押すとアプリが止まり、直したあとは止まらないことを確かめた。マイクの許可の返事のように別のスレッドから返る完了処理も、メインアクターの上で `await` して受け取る。

## 権限

- Mac 側に必要なのは、アプリ単位の許可 3 つ (ローカルネットワーク・画面収録・アクセシビリティ) だけ。
- Host の実行ファイルをターミナルから直接起動すると、画面収録とアクセシビリティの許可はターミナル (Ghostty) から引き継がれる。ただしローカルネットワークの許可は引き継がれず、mDNSResponder がアプリのバンドル ID ごとに判断する。許可が保留の間は Bonjour の広告が止まる。

## 検証の方針

- 検証は単体テスト (`just test`) とビルドで行う。判断の中身 (タッチの読み替え、キーの並び、修飾キー、ショートカットの解釈、通信、映像の符号化と復号) は Kit の純粋なロジックにして、そこをテストする。
- 利用者の Mac や iPad のマウス・キー・窓・アプリを動かすテスト (端末を操作する E2E、実機の UI テスト) と、利用者の操作を見張って確かめるやり方はとらない。利用者の作業を乗っ取るので、2026-10-17 に強く否定された。以前置いていた `Tools/E2E`・`Tools/DeviceProbe`・`Apps/PadUITests` は取り除いた。
- Host の入力の処理は、`InputInjector.swift` などを試験用に組み、Mac へ送る `post(tap:)` だけを記録に差し替えて確かめる。そこへ iPad から届く操作を流し込めば、Mac を動かさずに、作られるイベントの並び・時刻・フラグが分かる。2026-10-17 に、キーのリピート、Dock の ⌃F3、Typeless のショートカットを押すかどうかをこの方法で確かめた。
- iPad の画面の不具合は、画面を出さないシミュレータで、本物の画面のファイルをそのまま組んだ試験アプリで再現する。接続先はどこにもつながらない宛先に差し替えて、利用者の Host には接続しない。部品を簡略にした再現では、起きる条件が変わってしまうことがある (キーボードが出なくなった件)。
- 補助アプリや Host を入れ替える前に、聞き取りの最中でないことを記録で確かめる。2026-10-17 22:59 に、利用者が話し始めた 2 秒後に補助アプリを起動し直してしまい、既定の入力が途中で戻ってその回の聞き取りが無駄になった。
- Mac の中の音の経路は、補助アプリが起動のたびに自分で点検して記録に出す (聞こえない 20kHz の小さな音を鳴らし、タップと「PadBridge iPad マイク」に届くかを測る)。聞き取りのたびにも、iPad から届いた音の長さ、鳴らした音の最大、デバイスの入力の最大を記録に出すので、どこで音が消えたかは利用者に試してもらわずに記録から分かる。
- 変更を入れたら、利用者が使っている Host と iPad アプリの両方を入れ替える。片方だけ入れ替えると、古い側の動作を見て誤った原因を立ててしまう (3 本指スワイプで一度起きた)。
